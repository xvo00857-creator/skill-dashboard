## 1. 版本与依赖检查（安装前，需集群）

以下命令来自 SKILL.md 第 1、2.1 节，需在能访问 KubeSphere 集群的环境执行。

### 1.1 确认扩展与目标版本存在

```bash
# 扩展资源是否存在
kubectl get extension whizard-monitoring

# 目标版本资源是否存在（CRITICAL：必须确认版本存在再创建 InstallPlan）
kubectl get extensionversion whizard-monitoring-1.2.1

# 查看版本详情：installationMode、namespace、ksVersion、externalDependencies
kubectl describe extension whizard-monitoring
kubectl describe extensionversion whizard-monitoring-1.2.1
```

重点核对 `ExtensionVersion` 的以下字段（SKILL.md「Core Concepts」表）：

| 字段 | 核对内容 |
|------|----------|
| `spec.version` | 必须为 `1.2.1`（精确版本，不用 `recommendedVersion`/`latest`） |
| `spec.chartURL` | Helm chart 地址可访问 |
| `spec.namespace` | 目标命名空间（如 `kubesphere-monitoring-system`） |
| `spec.installationMode` | `Multicluster` 或 `HostOnly`；若为 `Multicluster` 需补 `clusterScheduling`（见第 2.2 节） |
| `spec.ksVersion` | 当前 KubeSphere 版本需满足约束（如 `>=4.2.0-0`） |
| `spec.externalDependencies[]` | 依赖扩展（如 `whizard-telemetry`）必须**已安装且版本满足** |

### 1.2 依赖检查

```bash
# 若 externalDependencies 列出了依赖扩展（例如 whizard-telemetry），逐个确认已安装
kubectl get extension <依赖扩展名>
kubectl get extension <依赖扩展名> -o jsonpath='{.status.installedVersion}{"\n"}'
kubectl get extension <依赖扩展名> -o jsonpath='{.status.state}{"\n"}'   # 期望 Installed
```

> 约束影响：按"不新增非必要依赖"要求，若依赖扩展缺失，应安装该扩展声明的依赖，而不是自行引入集群外组件；不满足前置条件时**停止安装**，不绕过。

### 1.3 集群前置条件

```bash
# KubeSphere 版本是否满足 ksVersion 约束
kubectl get kubesphere -o jsonpath='{.items[0].status.version}{"\n"}' 2>/dev/null || \
kubectl get deployment -n kubesphere-system ks-apiserver -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'

# 各节点 NTP 时钟同步（SKILL.md Issue 2：时钟漂移会导致 Job 已完成但状态不更新）
# 在每个节点上执行：
timedatectl status 2>/dev/null || ntpstat 2>/dev/null || date
```

## 2. 配置

### 2.1 InstallPlan manifest（默认配置，已生成）

文件：`installplan-whizard-monitoring.yaml`

```yaml
apiVersion: kubesphere.io/v1alpha1
kind: InstallPlan
metadata:
  name: whizard-monitoring
spec:
  enabled: true
  extension:
    name: whizard-monitoring
    version: 1.2.1
  upgradeStrategy: Manual
```

该 manifest 严格遵循 SKILL.md 的 CRITICAL 规则：

- `metadata.name` = `spec.extension.name` = `whizard-monitoring`（必须一致）
- `spec.extension.version` = `1.2.1`（用户指定的精确版本，不用 latest/recommendedVersion）
- `enabled: true`
- `upgradeStrategy: Manual`（生产环境）
- **省略 `spec.config`**：用户未要求自定义配置，使用扩展默认值（SKILL.md 最佳实践："Use default config (omit spec.config) unless custom values are needed"）
- **省略 `spec.clusterScheduling`**：默认按单集群/HostOnly 处理；若 1.1 步查到 `installationMode=Multicluster`，需按 2.2 节补充后再 apply

### 2.2 仅当 installationMode=Multicluster 时补充 clusterScheduling

若 `kubectl describe extensionversion whizard-monitoring-1.2.1` 显示 `installationMode: Multicluster`，需在 `spec` 下加入（示例：部署到 host 和 member 两个集群）：

```yaml
spec:
  clusterScheduling:
    placement:
      clusters:
      - host
      - member
```

> 注意：本方案为默认配置安装，不包含 `overrides`（每集群自定义覆盖）。仅当确有某集群需要差异化配置时才加 `overrides`，避免引入非必要配置。

### 2.3 应用（确认前步骤，需集群）

```bash
# 建议先做客户端 dry-run（不触达集群，仅校验 manifest 结构，需 kubectl）
kubectl apply -f installplan-whizard-monitoring.yaml --dry-run=client

# 确认无误后正式应用
kubectl apply -f installplan-whizard-monitoring.yaml
```

## 3. 安装后验证（需集群）

```bash
# 1) 跟踪 InstallPlan 状态，直到 state=Installed
kubectl get installplan whizard-monitoring -w
kubectl describe installplan whizard-monitoring

# 2) 确认 Extension 状态
kubectl describe extension whizard-monitoring
# 期望：status.state=Installed、status.enabled=true、status.installedVersion=1.2.1

# 3) 检查目标命名空间下 Pod/Service 是否正常
NAMESPACE=$(kubectl get installplan whizard-monitoring -o jsonpath='{.status.targetNamespace}')
echo "目标命名空间: $NAMESPACE"
kubectl get pods,svc -n $NAMESPACE
# 期望：相关 Pod 均为 Running/Ready，Service 已创建

# 4) 确认 Helm Job 已成功完成
JOB_NAME=$(kubectl get installplan whizard-monitoring -o jsonpath='{.status.jobName}')
kubectl get job $JOB_NAME -n $NAMESPACE
# 期望：COMPLETIONS 为 1/1
```

多集群模式下额外检查：

```bash
kubectl get installplan whizard-monitoring -o jsonpath='{.status.clusterSchedulingStatuses}' | python3 -m json.tool
# 每个集群的 state 均应为 Installed
```

## 4. 故障处理（来自 SKILL.md「Troubleshooting」）

### 4.1 InstallPlan 失败（Job 执行失败）

现象：InstallPlan 卡在 `Installing`/`Upgrading`，Job Pod 为 Error/Failed。

```bash
# 步骤 1：查看 InstallPlan 状态与 conditions
kubectl describe installplan whizard-monitoring

# 步骤 2：查看 Helm Job Pod 日志
NAMESPACE=$(kubectl get installplan whizard-monitoring -o jsonpath='{.status.targetNamespace}')
JOB_NAME=$(kubectl get installplan whizard-monitoring -o jsonpath='{.status.jobName}')
kubectl logs -n $NAMESPACE -l job-name=$JOB_NAME --tail=100

# 步骤 3：多集群时检查各集群调度状态
kubectl get installplan whizard-monitoring -o jsonpath='{.status.clusterSchedulingStatuses}' | python3 -m json.tool
```

排查方向（SKILL.md「Solutions」）：
- 确认扩展版本资源存在（`kubectl get extensionversion whizard-monitoring-1.2.1`）
- 确认 `externalDependencies` 中的依赖扩展已安装
- 若自定义了 config，检查 YAML 语法

### 4.2 Job 已完成但 InstallPlan 状态不更新

现象：Job Pod 成功完成，但 InstallPlan 停留在 `Installing`/`Upgrading`。

```bash
NAMESPACE=$(kubectl get installplan whizard-monitoring -o jsonpath='{.status.targetNamespace}')
JOB_NAME=$(kubectl get installplan whizard-monitoring -o jsonpath='{.status.jobName}')
kubectl get pods -n $NAMESPACE -l job-name=$JOB_NAME
kubectl get job $JOB_NAME -n $NAMESPACE -o jsonpath='{.status.completionTime}{"\n"}'
```

原因：节点间时钟漂移（NTP 未同步）。处理：检查并同步所有集群节点的 NTP。

## 5. 回滚步骤

SKILL.md 中卸载通过删除 InstallPlan 触发（第 5 节）。安装失败或需回滚时：

### 5.1 安装失败/未完成时回滚

```bash
# 删除 InstallPlan，控制器会触发 helm uninstall 清理已部署资源
kubectl delete installplan whizard-monitoring

# 确认目标命名空间下相关 Pod/Service/Job 已清理
NAMESPACE=kubesphere-monitoring-system   # 替换为实际 targetNamespace
kubectl get pods,svc -n $NAMESPACE
```

### 5.2 升级场景的回滚（若本次是升级而非全新安装）

若为从旧版本升级到 1.2.1 后需回退：

```bash
# 取回当前 InstallPlan
kubectl get installplan whizard-monitoring -o yaml > installplan-whizard-monitoring.yaml.bak

# 将 spec.extension.version 改回原版本号（精确版本），重新 apply
#   spec.extension.version: <原版本>
kubectl apply -f installplan-whizard-monitoring.yaml
kubectl get installplan whizard-monitoring -w
```

> 注意：回滚前确认旧版本的 ExtensionVersion 资源仍存在于集群中；若已被清理则无法直接回退。本方案为全新安装，回滚以 5.1 为准。

## 6. 新增约束导致的方案变化说明

| 新增约束 | 对方案的影响 |
|----------|--------------|
| 不新增非必要依赖 | 未在本地安装 kubectl/helm 等工具；静态校验仅用系统已有 python3+PyYAML；集群侧只安装扩展声明的 `externalDependencies`，不引入额外组件 |
