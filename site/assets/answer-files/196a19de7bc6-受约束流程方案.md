## 二、Skill 能力边界（严格遵循，不扩张）

**在范围内：**

- 通过 `InstallPlan` 安装/升级 OpenKruise 扩展
- 查询扩展状态、CRD、Pod、日志
- 生成 `SidecarSet`（sidecar 注入与滚动更新）
- 生成 `CloneSet`（高级无状态负载、原地升级、分批发布）
- 卸载扩展
- 排查 Pod 失败、CRD 缺失、webhook 故障

**默认不在范围内（SKILL.md 明确排除）：**

- `BroadcastJob`、`NodeImage`、`UnitedDeployment`、`AdvancedPodAutoscaler` 等用户未请求的高级 CRD
- 无集群证据的深度 chart values 设计

如用户后续明确请求上述 CRD，按 SKILL.md 要求作为后续任务处理，不并入本次默认流程。

## 三、通用约束：预检 / 幂等 / 重试 / 人工确认

以下四条贯穿后续所有阶段：

### 1. 预检（执行前必做）
- 确认当前 kubeconfig 指向预期集群：`kubectl config current-context`
- 确认扩展资源与版本存在（见各阶段具体命令）
- 生成 CR 前先查已安装 API 版本：`kubectl api-resources --api-group apps.kruise.io`

### 2. 幂等
- 所有创建/更新统一使用 `kubectl apply -f <file>`，不使用 `create`（重复执行安全）
- apply 前先 `kubectl get <resource> <name> -o yaml` 导出当前状态做基线，避免覆盖他人变更
- InstallPlan 已存在时，`apply` 即更新；不重复生成同名资源

### 3. 重试
- 仅对瞬时性错误（网络超时、`connection refused`、apiserver 限流）做有限重试（建议 3 次，指数退避）
- 对确定性错误（版本不存在、YAML 校验失败、权限不足、webhook 拒绝）**不重试**，直接进入排查
- 重试前重新读取资源最新状态，不基于旧状态盲目重试

### 4. 人工确认点（以下操作必须等待用户明确同意后才执行）
- 首次 `kubectl apply` 任何 InstallPlan / SidecarSet / CloneSet
- 修改 `partition` 推进分批发布的每一步
- `kubectl delete installplan openkruise`（卸载）
- 任何 CRD 删除操作（SKILL.md 规定：除非用户明确要求完全清理，否则不建议删除 CRD）
- 变更 `spec.config` 等非默认配置

## 四、受约束流程方案

### 阶段 1：安装 OpenKruise

**预检（只读，可直接执行）：**

```bash
kubectl config current-context
kubectl get extension openkruise
kubectl get extensionversions.kubesphere.io -l kubesphere.io/extension-ref=openkruise
kubectl describe extensionversion openkruise-1.0.3
```

预检确认项：扩展资源存在、`1.0.3` 版本存在、单集群/多集群形态、是否需要自定义 config、用户给的是扩展版本还是仅运行时版本。

> 版本规则（SKILL.md）：本环境默认扩展版本 `1.0.3`（对应运行时 `1.4.0`）；若用户只提供运行时版本，必须先确认匹配的扩展版本；**绝不编造版本**。

**人工确认点 A：** 向用户出示预检结果与拟 apply 的 InstallPlan，确认版本与目标集群列表后再继续。

**执行（幂等 apply）：**

```bash
kubectl apply -f installplan-openkruise.yaml
```

对应 manifest（已交付，见 `installplan-openkruise.yaml`）：

```yaml
apiVersion: kubesphere.io/v1alpha1
kind: InstallPlan
metadata:
  name: openkruise
spec:
  enabled: true
  extension:
    name: openkruise
    version: 1.0.3
  upgradeStrategy: Manual
  clusterScheduling:
    placement:
      clusters:
      - host
```

> 关键规则：`metadata.name` 必须等于 `spec.extension.name`；InstallPlan 为集群作用域，**不写 namespace**；`upgradeStrategy` 默认 `Manual`；未要求自定义 config 时省略该字段，不猜测取值。

**安装后验证（只读）：**

```bash
kubectl get installplan openkruise -w
kubectl describe installplan openkruise
kubectl get installplan openkruise -o jsonpath='{.status.clusterSchedulingStatuses}'
TARGET_NS=$(kubectl get installplan openkruise -o jsonpath='{.status.targetNamespace}')
kubectl get pods -n "${TARGET_NS:-kruise-system}"
kubectl logs -n "${TARGET_NS:-kruise-system}" deploy/kruise-manager --tail=200
kubectl get crd | grep -E 'clonesets.apps.kruise.io|sidecarsets.apps.kruise.io'
```

重试策略：仅当 InstallPlan 状态长时间无变化且日志显示瞬时错误时重试；若 conditions 显示版本不存在/权限拒绝，停止并排查。

### 阶段 2：状态查询（只读，无副作用）

```bash
# 扩展与版本
kubectl get extensions.kubesphere.io | grep -i kruise
kubectl get extensionversions.kubesphere.io | grep -i kruise
kubectl get installplans.kubesphere.io

# 运行时资源
kubectl api-resources --api-group apps.kruise.io
kubectl get crd | grep -E 'clonesets.apps.kruise.io|sidecarsets.apps.kruise.io'
kubectl get pods -A | grep -i kruise
kubectl get sidecarsets.apps.kruise.io -A
kubectl get clonesets.apps.kruise.io -A
```

多集群场景按 SKILL.md 区分：扩展状态走 KubeSphere API（curl + token），主机集群资源走 `kubectl`，成员集群资源先从 Cluster 资源提取 kubeconfig 再查询。本次无集群访问，上述命令均未执行。

### 阶段 3：SidecarSet 管理

**预检：**

```bash
kubectl api-resources --api-group apps.kruise.io   # 确认 API 版本
kubectl get namespace demo-project --show-labels   # 确认 namespaceSelector 能匹配
```

> 集群版本未知且仅作示例时，SKILL.md 规定使用 `apps.kruise.io/v1alpha1`。

**人工确认点 B：** 确认 selector 匹配目标 Pod 标签、namespaceSelector 匹配目标命名空间标签、镜像可拉取。

**执行（幂等）：**

```bash
kubectl apply -f sidecarset-log-agent.yaml
```

对应 manifest（已交付，见 `sidecarset-log-agent.yaml`）：注入 `fluent/fluent-bit:2.2` 到标签 `app: demo` 且命名空间标签 `kubernetes.io/metadata.name: demo-project` 的 Pod，滚动更新 `maxUnavailable: 1`。

**验证注入：**

```bash
kubectl get sidecarset log-agent -o yaml
kubectl get pods -n demo-project -l app=demo
kubectl get pod <pod-name> -n demo-project -o jsonpath='{.spec.containers[*].name}'
```

排查要点：selector/namespaceSelector 是否匹配、镜像能否拉取、`kruise-manager` webhook 是否健康。

---

### 阶段 4：CloneSet 管理

**预检：**

```bash
kubectl api-resources --api-group apps.kruise.io
kubectl get namespace demo-project
```

**人工确认点 C：** 确认副本数、镜像、更新策略后 apply。

**执行（幂等）：**

```bash
kubectl apply -f cloneset-sample-app.yaml
```

对应 manifest（已交付，见 `cloneset-sample-app.yaml`）：3 副本、`nginx:1.25`、`updateStrategy.type: InPlaceIfPossible`、`partition: 0%`、`maxUnavailable: 1`。

**验证：**

```bash
kubectl get cloneset sample-app -n demo-project
kubectl get pods -n demo-project -l app=sample-app -o wide
kubectl get events -n demo-project --sort-by=.lastTimestamp
```

#### 4.1 原地升级（nginx:1.25 → 1.26）

保持 `type: InPlaceIfPossible`，仅改镜像后重新 apply：

```bash
kubectl get cloneset sample-app -n demo-project -o yaml > cloneset.yaml
# 编辑 image: nginx:1.26
kubectl apply -f cloneset.yaml
kubectl describe cloneset sample-app -n demo-project
kubectl get pods -n demo-project -l app=sample-app -o wide
```

注意：某些字段变更（如 CPU/内存与镜像同时变更在不支持的环境）仍会触发 Pod 重建，需拆分为多次变更。

#### 4.2 分批发布（partition 灰度）

`partition` 控制保留在旧版本的副本比例：`100%` 全部旧版、`50%` 半数新版、`0%` 全部新版。

- **人工确认点 D（每一步都需确认）：**
  1. 改镜像并设 `partition: 100%` → apply → 验证无 Pod 移动
  2. 降到 `partition: 50%` → apply → 验证半数 Pod 迁至新版本并就绪
  3. 降到 `partition: 0%` → apply → 验证全部完成

```bash
kubectl get cloneset sample-app -n demo-project -o yaml   # 每步查看 partition 与 status
kubectl get pods -n demo-project -l app=sample-app -o wide
```

每一步若新版本 Pod 未就绪，不推进下一步（不盲目重试，先 `describe` + `events` 排查）。

### 阶段 5：卸载

**预检（必做，检查依赖）：**

```bash
kubectl get sidecarsets.apps.kruise.io -A
kubectl get clonesets.apps.kruise.io -A
```

若仍存在 SidecarSet/CloneSet，先告知用户迁移或删除，不直接卸载。

**人工确认点 E（高风险）：** 卸载会移除扩展组件，需用户明确确认。

```bash
kubectl delete installplan openkruise
kubectl get installplan openkruise
kubectl get pods -n kruise-system | grep -i kruise
```

> SKILL.md 规定：删除 CRD 或 CR 实例可能删除应用配置；除非用户明确要求完全清理，否则**不建议删除 CRD**。完全清理前需先处理应用资源并确认业务方不再依赖 OpenKruise 行为。

### 阶段 6：故障排查（只读诊断优先）

| 现象 | 诊断命令 | 可能原因 | 安全下一步 |
|------|----------|----------|------------|
| InstallPlan/扩展失败 | `kubectl describe installplan openkruise`；`kubectl get installplan openkruise -o jsonpath='{.status.conditions}'` | 版本不存在、权限不足、安装 Job 失败 | 查看 conditions 与安装 Job 日志，不重复 apply |
| kruise Pod 不健康 | `kubectl get pods -A \| grep -i kruise`；`kubectl describe pod -n kruise-system <pod>`；`kubectl logs -n kruise-system deploy/kruise-manager --tail=200` | 镜像拉取失败、资源不足、调度失败 | 依事件定位，不手动删 Pod |
| CRD 缺失/未建立 | `kubectl get crd clonesets.apps.kruise.io sidecarsets.apps.kruise.io`；`kubectl api-resources --api-group apps.kruise.io` | 安装未完成、CRD 被 apiserver 拒绝、controller 启动失败 | 复查 InstallPlan 与日志，CRD 就绪前不创建业务 CR |
| Webhook 失败 | `kubectl get mutatingwebhookconfigurations,validatingwebhookconfigurations \| grep -i kruise`；检查 Service/Endpoints、controller 日志中的 x509 错误 | manager 未 Ready、endpoints 缺失、证书过期/不匹配、apiserver 不通 | 检查 Pod 就绪与证书，不绕过 webhook |
| Sidecar 未注入 | `kubectl get sidecarset -A`；`kubectl get namespace <ns> --show-labels`；对比 Pod/命名空间标签 | selector/namespaceSelector 不匹配、webhook 异常 | 修正选择器或排查 webhook |
| CloneSet 发布卡住 | `kubectl describe cloneset <name> -n <ns>`；`kubectl get events -n <ns> --sort-by=.lastTimestamp` | 新镜像拉取失败、探针失败、maxUnavailable 限制 | 依事件处理，不强制推进 partition |

## 八、实际影响交付结果的 SKILL.md 规则（至少一条）

**规则："`InstallPlan.metadata.name` MUST equal `InstallPlan.spec.extension.name`"（SKILL.md 第 40 行）。**

该规则直接决定了 `installplan-openkruise.yaml` 中 `metadata.name` 与 `spec.extension.name` 必须同为 `openkruise`，并被编码为校验脚本的强制检查项（"InstallPlan: metadata.name == spec.extension.name"）。若违反，校验会失败并阻断交付。

其他同样影响交付的规则包括：InstallPlan 为集群作用域不得加 namespace（第 41 行）、默认 `upgradeStrategy: Manual`（第 42 行）、省略可选字段而非猜测（第 43 行）、集群版本未知时 SidecarSet/CloneSet 使用 `v1alpha1`（第 50-52 行）、卸载时不主动建议删除 CRD（第 53 行）。
