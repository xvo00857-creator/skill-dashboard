## 2. 风险分级（Risk Classification）

分级标准：**严重 (Critical)** = 疑似已发生数据泄露/外传；**高 (High)** = 凭据/权限异常，可能被利用；**中 (Medium)** = 针对性探测但未成功；**低 (Low)** = 完整性/加固类问题；**信息 (Info)** = 基线事件。

| 编号 | 风险 | 等级 | 受影响资产 | 证据（行号） | 置信度 |
|---|---|---|---|---|---|
| R1 | 疑似数据外传：异常 DB 导出，用户 `unknown`，与同 IP 的 token 越权事件紧邻 | **严重** | 数据库、服务账号 service-a | #5，关联 #4 | 中（单日志源，需复核） |
| R2 | 服务凭据越权/疑似盗用：`token_scope_mismatch` | **高** | API 服务、service-a 令牌 | #4 | 中高 |
| R3 | admin 账户口令猜测/暴力尝试（4 秒内 2 次失败） | **中** | web 管理入口、admin 账户 | #2、#3 | 中 |
| R4 | 日志完整性缺陷：畸形记录、关键字段缺失，可能掩盖痕迹或管线故障 | **低** | 日志管线/审计可信度 | #6 | 中 |
| R5 | 正常登录基线 | 信息 | web | #1 | 高 |

### 2.1 R1 严重：疑似数据外传

- **证据**：`db,critical,unexpected_export,unknown,203.0.113.8`（#5）；3 分 28 秒前同一 IP 出现 `api,high,token_scope_mismatch,service-a,203.0.113.8`（#4）。
- **推断**：`unknown` 用户触发数据库导出本身即异常；与同 IP 的令牌权限异常形成时序与源双重关联，疑似利用服务令牌越权读取并导出数据。
- **不确定性**：无法确认导出内容、数据量、是否成功落盘外传；缺少 DB 审计与网络出站日志。

### 2.2 R2 高：服务令牌权限域不匹配

- **证据**：`api,high,token_scope_mismatch,service-a,203.0.113.8`（#4）。
- **推断**：service-a 持有的令牌请求了超出其授权域的资源。可能原因：配置错误（令牌签发 scope 与业务需要不一致）或令牌被盗用/被重放。鉴于 3 分钟后同 IP 出现 DB 导出，**盗用/重放假设优先级更高**。

### 2.3 R3 中：admin 登录失败聚集

- **证据**：09:03:45 与 09:03:49，同一 IP 198.51.100.23，同一账户 admin，间隔 4 秒（#2、#3）。
- **推断**：短间隔重复失败符合自动化尝试特征，但样本仅 2 次，未达常见锁定阈值，且与 R1/R2 无 IP 关联。定为中风险，需拉长时间窗统计。

### 2.4 R4 低：畸形日志记录

- **证据**：`2026-08-12T09:09:00Z,web,,malformed_record,,`（#6），severity/user/source_ip 均空。
- **推断**：两种可能——(a) 日志采集/解析管线故障；(b) 攻击者尝试注入或抑制日志字段。无论哪种，都削弱审计可信度，需修复并核实该时刻前后是否有缺失事件。

## 3. 约束、冲突与关键取舍

1. **Skill 范围 vs 任务范围（已在第 0 节详述）**：SKILL.md 是 Shopify 性能优化技能，不含安全方法。取舍：忠实采用其输出骨架（评估→优先级行动→工具对比→时间线→KPI），内容改用通用安全实践，并全程标注，不虚构"Skill 授权了安全分析"。
2. **授权测试范围 vs 处置力度**：任务明确"禁止破坏性操作"，且数据为模拟数据。取舍：所有修复均以**建议/待执行清单**形式给出，不实际封禁 IP、不轮换真实令牌、不删除/修改日志；复测清单设计为可在测试环境复现验证的步骤。
3. **证据完整性 vs 结论强度**：仅单份 CSV，缺少认证、DB 审计、网络日志。取舍：对 R1/R2 给出"疑似"定性与**中等置信度**，不直接断言"已发生数据泄露"；将"补充日志源后复核"列为首要依赖。
4. **畸形记录的处理**：纳入 vs 排除的冲突。取舍：既不把它当作有明确主体的攻击事件（无 user/IP），也不丢弃，而是单列为 R4 日志完整性问题——避免过度解读，也避免漏掉线索。
5. **admin 失败事件的定级**：仅 2 次失败，可能是误输密码。取舍：从"事件本身"定为中风险，但建议按时间窗聚合统计；若 5–10 分钟内同 IP/同账户超过阈值（如 5 次）再升级。

## 4. 修复建议（按优先级：Quick Wins → Long-term）

> 以下均为**待授权人员在真实环境执行**的建议；本报告未执行其中任何一项。

### 4.1 Quick Wins（立即，0–1 天）

1. **核实 R1 数据导出**：在数据库审计/对象存储访问日志中，按 2026-08-12 09:07:30Z 前后窗口、源 IP 203.0.113.8、用户 `unknown` 检索导出记录，确认导出对象、行数、目标位置；若属实，按数据事件响应流程启动。
2. **冻结/轮换 service-a 令牌**：吊销 203.0.113.8 所使用的 service-a 令牌，重新签发并遵循最小权限；检查该令牌近期所有调用记录。
3. **核查 admin 登录失败**：拉取 198.51.100.23 在更大时间窗（前后 24h）的登录记录；确认是否为管理员本人操作；如非本人，强制 admin 改密并启用 MFA。
4. **保全日志证据**：对 `incident_log.csv` 及相关原始日志做哈希留存（只读副本），避免后续分析污染证据。

### 4.2 中期加固（1–2 周）

5. **令牌生命周期与最小权限**：服务令牌短期化、定期轮换；scope 按业务最小化；建立令牌使用基线（常用 IP、常用 scope、调用频率），偏离即告警。
6. **数据库导出管控**：禁止 `unknown`/匿名主体导出；导出操作需二次审批与留痕；对大批量导出设置速率/行数阈值告警；敏感字段脱敏或加密。
7. **暴力破解防护**：管理后台启用 MFA；按 IP+账户维度设置失败阈值与渐进式延迟/临时锁定；admin 等特权账户加白名单或堡垒机接入。
8. **修复日志管线**：定位 `malformed_record` 根因（采集器/解析器/字段校验），为 severity/user/source_ip 设置非空校验与死信队列；对日志缺失/断流建立监控。

### 4.3 Long-term（1 个月以上）

9. **跨系统关联检测**：接入 web/api/db/网络/认证日志到统一 SIEM，建立规则：`token_scope_mismatch` 后短时间内同主体出现 `unexpected_export` 自动触发高危告警。
10. **威胁狩猎与基线**：建立正常访问基线（地理、时间、数据访问量），定期狩猎异常导出与越权令牌使用。
11. **演练与复盘**：将本模拟场景纳入桌面演练，验证响应流程、角色分工与沟通时效。

### 4.4 工具/方案对比（依 SKILL.md 输出要求）

| 方案 | 适用场景 | 优点 | 局限/成本 |
|---|---|---|---|
| 云厂商原生审计（如 DB 审计日志 + IAM Access Analyzer） | 已在主流云上 | 接入快、与身份体系打通 | 跨云/自建系统关联弱，留存成本随量级上升 |
| 开源 SIEM（如 Wazuh/Elastic Security） | 中小团队、自建 | 成本低、规则可定制 | 需自运维，规则调优成本高 |
| 商业 SIEM/SOC 服务 | 合规要求高、团队充足 | 关联能力强、有托管响应 | 费用高，接入周期长 |
| 应用层加固（MFA、令牌短期化、导出审批） | 所有团队 | 直接降低 R1/R2/R3 风险 | 需研发改造，可能影响服务账号自动化流程 |

> 注：SKILL.md 原推荐方向为 Shopify 性能类应用，与本安全任务不匹配，故此处按安全工具类别给出对比；选型须结合真实技术栈与合规要求验证。

## 7. 结论

- 在 6 条模拟日志中，识别出 **1 项严重（R1 疑似数据外传）、1 项高危（R2 服务令牌越权）、1 项中危（R3 admin 暴力尝试）、1 项低危（R4 日志完整性）**。
- 最优先事项：**核实 203.0.113.8 在 09:04–09:07 的令牌使用与数据库导出行为，并轮换 service-a 令牌**；这两项构成疑似攻击链，置信度中等，须用真实日志复核。
- 本报告严格在授权测试范围内完成，**未执行任何破坏性或线上操作**；所有修复建议均待授权人员在真实环境实施与复测。
- 执行依据方面，`shopify-speed-optimization` 的 SKILL.md 为 Shopify 性能优化技能，不覆盖安全审计；本报告仅借用其输出结构框架，其 Limitations（"仅战略指导、不做 API 集成""须用真实数据验证"）决定了本报告为建议性质、结论需复核。
