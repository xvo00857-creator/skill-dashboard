## 3. 详细发现

### F-01【严重】令牌越权 + 同源 IP 异常数据库导出（疑似数据外泄）

- **位置**：`incident_log.csv`
  - 第 5 行：`2026-08-12T09:04:02Z,api,high,token_scope_mismatch,service-a,203.0.113.8`
  - 第 6 行：`2026-08-12T09:07:30Z,db,critical,unexpected_export,unknown,203.0.113.8`
- **数据流**：
  1. `service-a` 服务账号令牌从 `203.0.113.8` 调用 API，触发 `token_scope_mismatch`（high）——说明令牌实际权限与声明 scope 不符，或 scope 校验被触发但未阻断；
  2. 间隔 **3 分 28 秒**后，**同一源 IP** `203.0.113.8` 对数据库发起 `unexpected_export`（critical），且操作者为 `unknown`——数据库层无法识别主体身份，提示认证上下文丢失或被绕过；
  3. 时间与来源强关联，构成"越权令牌 → 未鉴权数据库导出"的攻击链。
- **人工验证（MUST）**：
  - 可达性：两条记录均真实存在，时间戳、IP 可直接关联；
  - 可利用性：`unexpected_export` 已实际发生（非仅告警），说明数据导出动作已执行；
  - 误报评估：`unknown` 主体也可能是配置错误的服务账号，但"scope 不匹配告警在先 + critical 导出在后 + 同 IP"的组合使误报可能性低；需在真实环境核对 service-a 是否为该导出的合法主体。
- **影响**：可能造成数据库敏感数据批量外泄；`unknown` 身份表明审计追溯链断裂。
- **修复建议**：
  1. 立即吊销/轮换 `service-a` 令牌，审查其 scope 配置，遵循最小权限；
  2. 在 API 网关强制 scope 校验——`token_scope_mismatch` 应**拒绝请求**而非仅告警；
  3. 数据库导出操作必须绑定已认证主体，禁止 `unknown`/匿名导出；对导出行为加二次审批与白名单；
  4. 对 `203.0.113.8` 在该时间窗的所有操作做完整溯源，确认导出数据范围并按事件响应流程处置；
  5. 增加关联检测规则：同一 IP 在 N 分钟内出现 `token_scope_mismatch` 后接 `unexpected_export` 自动升级为严重事件并阻断。
- **CWE/ATT&CK**：CWE-285（不当授权）、CWE-200（敏感信息暴露）；ATT&CK T1078（合法账号滥用）、T1530（数据从云/数据库存储外传）。

### F-02【高】CSV 公式注入

- **位置**：`edge_cases.csv` 第 7 行，record_id=5，`value` 字段原始内容：
  ```
  =HYPERLINK(\"https://example.invalid\",\"do not execute\")
  ```
  （文件中以双引号包裹、内部用 `\"` 转义；`notes` 标注为"公式注入测试文本"）
- **数据流**：外部可控的 `value` 字段未经净化直接写入 CSV → 分析人员用 Excel/LibreOffice/WPS 打开或以公式模式导入 → 以 `=` 开头的单元格被解释为公式 → `HYPERLINK` 生成外链；真实攻击中可替换为 `=WEBSERVICE(...)`、`=IMPORTDATA(...)` 等外传数据，或诱导点击钓鱼链接。
- **人工验证（MUST）**：
  - 首字符为 `=`，满足表格软件公式触发条件（`=`、`+`、`-`、`@` 均为触发字符）；
  - 本 payload 域名 `example.invalid` 为保留无效域名（RFC 2606），不会实际外联，属测试串；但模式成立，风险真实；
  - 非误报：`notes` 自陈"公式注入测试文本"，确认为有意植入的测试样本。
- **修复建议**：
  1. 导出 CSV 时，对以 `=`、`+`、`-`、`@`、Tab、CR 开头的单元格前置单引号 `'` 或空格进行中和；
  2. 写入端对用户可控字段做公式字符过滤/转义；
  3. 告知分析人员以"数据导入"方式打开 CSV（禁用公式自动计算），或使用不执行公式的查看器；
  4. 内容安全策略层面禁止 CSV 导出内容直接被电子表格软件以受信模式打开。
- **CWE**：CWE-1236（CSV 文件中公式元素未正确中和）。

### F-03【中】admin 账号暴力破解迹象

- **位置**：`incident_log.csv` 第 3–4 行：
  - `09:03:45` `login_failed admin` 来自 `198.51.100.23`
  - `09:03:49` `login_failed admin` 来自 `198.51.100.23`
- **数据流**：同一 IP 在 **4 秒**内对 `admin` 连续两次登录失败，呈自动化尝试特征。样本量仅 2 条，无法确认是否成功或持续爆破。
- **人工验证**：时间与 IP 一致；但样本窗口短、次数少，不能单独定性为成功爆破，定为中风险可疑迹象。
- **修复建议**：
  1. 启用登录失败阈值锁定/指数退避与验证码；
  2. 对 `admin` 等特权账号强制 MFA、禁止公网直连或加 IP 白名单；
  3. 拉取该 IP 更长时间窗日志确认尝试总量与是否最终成功；
  4. 部署暴力破解检测规则（同 IP/同账号 N 分钟内失败 ≥M 次告警）。
- **CWE/ATT&CK**：CWE-307（不当限制过度认证尝试）；ATT&CK T1110（暴力破解）。

### F-04【中】日志记录字段缺失（审计盲区）

- **位置**：`incident_log.csv` 第 7 行：
  ```
  2026-08-12T09:09:00Z,web,,malformed_record,,
  ```
  `severity`、`user`、`source_ip` 均为空。
- **数据流**：日志生产端未对必填字段做校验 → 含空字段的记录入库 → 按 user/IP 关联、按 severity 分级的检测规则漏判该记录。
- **人工验证**：hex 确认连续逗号为空字段，非解析错误；事件名自陈 `malformed_record`，但缺失字段使该记录无法被有效审计。需排除日志篡改/注入可能。
- **修复建议**：
  1. 日志采集端对 `severity/user/source_ip` 等必填字段做 schema 校验，拒绝或隔离不合法记录；
  2. 集中收集"畸形日志"指标并告警，突增可能预示日志注入或篡改；
  3. 日志传输启用完整性保护（如签名/追加式存储），防止事后篡改；
  4. 排查 `web` 系统 09:09:00 产生该记录的根因。
- **CWE**：CWE-778（日志记录不充分）。

### F-05【低】重复记录（数据完整性）

- **位置**：`edge_cases.csv` 第 3–4 行，record_id=2 出现两次，内容完全相同（`ok,120,重复记录`）。
- **影响**：重复数据导致统计/计数偏差，可能被用于污染聚合分析或绕过基于次数的阈值。
- **修复建议**：以 record_id 为主键去重；写入端做唯一性约束；排查重复来源（重试/重放/双写）。

### F-06【低】记录字段缺失

- **位置**：`edge_cases.csv` 第 5 行，record_id=3：`status`、`value` 为空，notes 为 `-`。
- **影响**：不完整记录影响数据质量与下游分析。
- **修复建议**：写入端 schema 校验必填字段；缺失值用显式空值标记并记录原因，而非裸空。

### F-07【低】异常负值

- **位置**：`edge_cases.csv` 第 6 行，record_id=4：`status=error, value=-999`。
- **影响**：`-999` 是典型哨兵/错误码，若下游未区分"错误码"与"真实测量值"，会污染统计（均值、阈值告警）。
- **修复建议**：错误状态与数值字段分离；对 error 记录的 value 不参与数值聚合；定义合法取值范围并校验。

### F-08【低】非标准 CSV 转义导致解析差异

- **位置**：`edge_cases.csv` 第 7 行。文件在双引号包裹的字段内使用反斜杠转义（`\"`），而 RFC 4180 标准要求用双写双引号（`""`）。
- **证据**：
  - hex 转储确认字段内为 `5c 22`（`\"`）；
  - 用 Python 标准 `csv` 模块（默认 RFC 4180 方言）解析时，该行被错误切分：`value` 变为 `=HYPERLINK(\https://example.invalid\"`，`notes` 变为 `\"do not execute\")"`，`公式注入测试文本` 溢出为额外列；
  - 而将 `\"` 视为转义的解析器会恢复出完整公式 `=HYPERLINK("https://example.invalid","do not execute")`。
- **影响**：不同解析器看到不同字段内容。若安全过滤/审计用严格解析器、而目标消费方用宽松解析器（或反之），可造成检测与实际不一致，形成过滤绕过；同时列错位本身会破坏下游数据。
- **修复建议**：
  1. 统一使用 RFC 4180 标准转义（字段内双引号写为 `""`），不要使用 `\"`；
  2. 安全检测与下游消费使用**同一个**经过验证的 CSV 解析器配置；
  3. 对列数不一致的行直接隔离告警，不静默吞掉。
- **CWE**：CWE-117 类（输出中和不当/日志注入），本质为解析差异（parser differential）。
