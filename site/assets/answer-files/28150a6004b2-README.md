# Context Package - Usage Guide

> Reusable context system for cross-session development tasks spanning up to two weeks.
> Based on context engineering principles: feed the right information at the right time.

## Files

| File | Level | Purpose | When to Read | When to Update |
|------|-------|---------|--------------|----------------|
| AGENTS.md | 1 (Rules) | Persistent project rules: stack, commands, conventions, boundaries | Every session start | When conventions change (rare) |
| SESSION_CONTEXT.md | 2-5 (State) | Cross-session state: facts, decisions, todos, hypotheses, handoff | Every session start | Throughout session; especially at end |
| PROJECT_MAP.md | 2 (Spec/Arch) | Hierarchical summary of codebase areas | When working in a specific area | When new areas are added |

## Session Workflow

### Starting a New Session

1. Read AGENTS.md (rules, conventions, boundaries)
2. Read SESSION_CONTEXT.md (current state, facts, decisions, todos, hypotheses)
3. Read the relevant section of PROJECT_MAP.md (only the area you will touch)
4. Check the Session Handoff section for immediate next actions
5. Review open Hypotheses - are any blocking your work? Verify or flag them.
6. Review open Confusions - do any need user input before proceeding?

### During a Session

1. Before editing a file, read it. Find an existing pattern to follow.
2. When you learn something verified, add it as [FACT] with source.
3. When a choice is made, record it as [DECISION] with rationale and alternatives.
4. When you discover an assumption, record it as [HYPOTHESIS] with how to verify.
5. When you hit ambiguity, add to Confusion Log and surface to user. Do NOT guess.
6. For multi-step work, emit an Inline Plan before executing.
7. Feed specific errors back (not 500-line dumps) when tests fail.

### Ending a Session

1. Update todo statuses
2. Note which hypotheses were verified or busted
3. Fill in the Session Handoff:
   - What was done
   - Current state (working on, last file, test status)
   - What next session needs to know
   - Immediate next actions
4. Update PROJECT_MAP.md if new areas or patterns were discovered

## The Four Categories Explained

### [FACT] - Confirmed Facts
- Verified ground truth that does not change
- Must have a source (code, test, user confirmation, documentation)
- If you cannot point to the source, it is a [HYPOTHESIS], not a fact
- Examples: API endpoints, schema columns, confirmed requirements, test results

### [DECISION] - Decisions Made
- A choice made from alternatives
- Record what was chosen AND what was rejected AND why
- Prevents future sessions from re-litigating settled choices
- If a decision needs changing, mark old one SUPERSEDED (do not delete)
- Examples: library choices, architecture patterns, naming conventions

### [TODO] - To-Dos
- Actionable work items
- Include owner, status, and dependencies
- Blocked todos should note what blocks them
- Examples: implement feature X, write tests for Y, verify hypothesis H-01

### [HYPOTHESIS] - Assumptions Needing Verification
- Things assumed true but not yet confirmed
- The most dangerous category - building on wrong assumptions causes rework
- Each hypothesis has: risk if wrong, how to verify, and outcome
- Must eventually become [FACT] (confirmed), be killed (wrong), or become [DECISION] (we choose it)
- Examples: library behavior, performance characteristics, compatibility assumptions

## Anti-Patterns to Avoid

| Anti-Pattern | What It Looks Like | Fix |
|---|---|---|
| Context starvation | Agent invents APIs, ignores conventions | Load AGENTS.md + relevant source before each task |
| Context flooding | Loading entire codebase for a one-file change | Use Selective Include; aim for <2000 lines of focused context |
| Stale context | Referencing patterns that changed | Start fresh sessions when switching major features; update SESSION_CONTEXT.md |
| Missing examples | Agent invents new style instead of following yours | Include one pattern example in AGENTS.md; point to example files in SESSION_CONTEXT.md |
| Implicit knowledge | Unwritten project rules cause repeated mistakes | Write it down in AGENTS.md - if it is not written, it does not exist |
| Silent confusion | Agent guesses when it should ask | Use Confusion Log; surface ambiguity explicitly |

## Context Budget Guidance

- AGENTS.md: Keep under 200 lines. It loads every session.
- SESSION_CONTEXT.md: Grows over two weeks but should stay focused. Archive old sessions if it gets long.
- PROJECT_MAP.md: One section per area. Each section 10-20 lines.
- Per-task loaded context: Aim for under 2000 lines of focused code/docs.
- Error output: Include the specific error, not the full 500-line log.

## Two-Week Timeline Suggestion

| Phase | Days | Focus |
|-------|------|-------|
| Setup | Day 1 | Fill in AGENTS.md, PROJECT_MAP.md skeleton, define task goal and DoD |
| Build | Days 2-7 | Implement core features; actively track facts/decisions/hypotheses |
| Integrate | Days 8-9 | Connect pieces; verify remaining hypotheses; resolve confusions |
| Polish | Days 9-10 | Tests, edge cases, documentation; finalize todos |

Throughout: update SESSION_CONTEXT.md every session.
