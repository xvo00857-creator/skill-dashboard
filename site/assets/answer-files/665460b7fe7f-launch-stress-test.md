# 上线计划压力测试报告

> 方法：`/em:stress-test` — Business Assumption Stress Testing
> 对象：一个**依赖单一供应商、无回滚方案、涉及用户敏感数据**的上线计划
> 日期：2026-08-10

---

## 0. 被压测的核心假设

| # | 假设陈述（必须具体、可证伪） | 来源 |
|---|----------------------------|------|
| A1 | **单一供应商可靠性**：该供应商在上线后将持续稳定提供服务，达到约定 SLA，不发生重大故障、安全事件或经营变故。 | 上线方案默认前提 |
| A2 | **无回滚可接受**：即使上线后出现问题，不依赖版本/配置回滚，也能通过热修复、限流、降级或人工干预在可接受时间内控制影响。 | 上线方案明确"无回滚" |
| A3 | **敏感数据安全合规**：供应商对用户敏感数据的采集、传输、存储、访问、删除全链路是安全且合规的，不会发生未授权访问、泄露或越权处理。 | 上线方案默认前提 |

**组合假设（最危险的那条）**：以上三条同时成立——即"供应商不出事 × 出事也能兜住 × 数据不泄露"。这是整个上线计划的隐含前提，也是最需要被压测的对象。

---

## 1. 反证（COUNTER-EVIDENCE）

### 对 A1（单一供应商可靠）的反证
- **单点故障是行业常态而非例外**：主流云厂商、SaaS 服务商均有过公开的大规模中断记录，任何供应商都无法承诺 100% 可用。
- **供应商侧风险不可控**：供应商可能遭遇宕机、API 破坏性变更、安全漏洞、被收购、涨价、终止服务、经营破产——这些事件的发生时间和影响范围完全在我方控制之外。
- **基础概率不利**：任何新接入的第三方依赖，其在生产环境的真实稳定性只有上线后才能验证；上线前的测试无法覆盖供应商侧所有故障模式。
- **锁定效应**：单一供应商意味着切换成本高，一旦出现问题，短期内无法通过"切到备用方案"缓解。

### 对 A2（无回滚可接受）的反证
- **回滚是最快、最确定的止损手段**：在大量线上事故复盘里，回滚（feature flag 关闭、版本回退、配置还原）是 MTTR 最短的止血方式。去掉回滚等于放弃了最可靠的应急工具。
- **热修复本身有风险**：线上紧急修复未经过完整测试，可能引入新问题，形成"事故 → 紧急修复 → 二次事故"的连锁。
- **人工干预不可扩展**：当故障影响面大时，人工处理速度跟不上故障扩散速度。
- **降级/限流不等于回滚**：降级只能减轻部分功能影响，无法撤销已经发生的数据写入、状态变更或对第三方的数据发送。

### 对 A3（敏感数据安全合规）的反证
- **数据泄露是高概率事件**：即使是安全成熟度高的大型组织也反复发生数据泄露；委托第三方处理数据会增加攻击面（我方系统 + 供应商系统 + 双方之间的链路）。
- **合规义务不因委托而转移**：根据《个人信息保护法》（PIPL），个人信息处理者承担合规责任，委托处理不免除我方义务；发生泄露时监管首先追责的是处理者（即我方）。
- **敏感数据一旦泄露不可撤回**：与功能故障不同，数据泄露是不可逆的——数据一旦流出，无法"回滚"到未泄露状态。
- **无回滚 + 敏感数据 = 最坏组合**：如果供应商侧发生数据泄露或错误数据写入，没有回滚意味着无法通过技术手段切断泄露路径或恢复数据状态。

## 2. 下行建模（DOWNSIDE MODEL）

> 三档情景按"对业务/用户/合规的冲击程度"划分。由于本计划涉及敏感数据，冲击维度包含：服务可用性、数据安全、法律合规、用户信任、财务。

### 🟡 Bear case（-30%）：供应商短暂服务中断

| 维度 | 影响 |
|------|------|
| 事件 | 供应商出现数小时级服务中断或显著性能下降，无数据泄露 |
| 服务 | 依赖该供应商的功能不可用或响应缓慢 |
| 数据 | 无泄露 |
| 合规 | 无监管报告义务触发 |
| 用户 | 用户投诉增加，部分用户无法完成核心流程 |
| 财务 | SLA 违约赔偿（如有）、直接收入损失 |
| **业务是否存活** | ✅ 存活，但体验受损 |

### 🟠 Stress case（-50%）：供应商故障导致部分敏感数据暴露 / 错误处理

| 维度 | 影响 |
|------|------|
| 事件 | 供应商配置错误、API 逻辑缺陷或访问控制失效，导致部分用户敏感数据被未授权方访问，或数据被错误写入/处理；因无回滚无法快速切断 |
| 服务 | 核心功能异常，可能需要手动停用相关功能 |
| 数据 | 部分用户敏感数据泄露或损坏，**不可逆** |
| 合规 | 触发数据泄露通知义务（PIPL 要求立即采取补救并通知用户和监管）；可能启动监管调查 |
| 用户 | 受影响用户信任严重受损；可能引发负面舆论 |
| 财务 | 应急响应成本、用户赔偿、潜在罚款、法务费用 |
| **业务是否存活** | ⚠️ 存活但受重创，需投入大量资源善后 |

### 🔴 Catastrophic case（-80%）：大规模数据泄露 / 供应商被攻破

| 维度 | 影响 |
|------|------|
| 事件 | 供应商发生大规模安全 breach，大量用户敏感数据外泄；或供应商遭遇勒索/内部恶意行为导致数据被批量窃取；无回滚方案无法从技术层面切断泄露路径 |
| 服务 | 可能被迫全面停用相关功能甚至下线 |
| 数据 | 大规模敏感数据泄露，**完全不可逆** |
| 合规 | 监管处罚（PIPL 最高可处 5000 万元或上一年度营业额 5% 罚款；可责令暂停相关业务、停业整顿、吊销许可）；直接负责的主管人员可能承担个人法律责任 |
| 用户 | 大规模用户信任崩塌；媒体报道；可能引发集体诉讼 |
| 财务 | 巨额罚款 + 诉讼成本 + 收入断崖 + 用户流失 + 品牌长期损害 |
| **业务是否存活** | ❌ 业务可能无法继续——监管可能要求停止服务，用户流失可能不可逆，品牌损害可能是永久性的 |

## 3. 级联风险（CASCADING RISKS）

> 三条风险因子不是独立的，它们互相放大。以下是关键的因果链条。

```
[供应商故障/被攻破]
        │
        ├─→ 服务不可用 ─→ 用户无法使用核心功能 ─→ 用户投诉/流失 ─→ 收入损失
        │
        ├─→ 敏感数据泄露 ─→ 触发法定通知义务 ─→ 监管介入调查 ─→ 业务整改/暂停 ─→ 收入损失 + 罚款
        │                       │
        │                       └─→ 媒体报道/舆论发酵 ─→ 品牌损害 ─→ 用户流失加速 ─→ 估值/融资受影响
        │
        └─→ [无回滚] ──→ MTTR 被迫拉长 ──→ 以上所有后果的持续时间和影响面被放大
                            │
                            └─→ 紧急热修复 ──→ 引入新缺陷 ──→ 二次事故 ──→ 恶性循环

[合规违规被认定]
        │
        ├─→ 监管要求停止服务 ─→ 被迫下线 ─→ 但无回滚方案 ─→ 下线过程本身可能造成数据不一致/二次损害
        │
        └─→ 责任人个人法律风险 ─→ 管理层决策责任追溯
```

**关键放大点**：
1. **无回滚 × 数据泄露**：数据泄露本身不可逆，无回滚意味着连"切断泄露通道"这个最小止损动作都做不到，泄露持续时间完全取决于供应商修复速度。
2. **单一供应商 × 无回滚**：既不能回退到旧版本，也不能切换到备用供应商，事故期间我方几乎没有主动权。
3. **敏感数据 × 监管时效**：PIPL 要求"立即"补救和通知，而无回滚 + 依赖供应商意味着响应速度受制于供应商，可能无法满足法定时限。

## 4. 敏感度（SENSITIVITY）

| 假设 | 敏感度 | 理由 |
|------|--------|------|
| A1 单一供应商可靠 | **HIGH** | 供应商可用性从 99.9% 降到 99%（看似小变化）意味着月均停机从 ~43 分钟涨到 ~7 小时；一次严重故障即可触发 Stress/Catastrophic 情景 |
| A2 无回滚可接受 | **HIGH** | 回滚的存在与否直接决定 MTTR 是"分钟级"还是"小时/天级"；在数据泄露场景下，回滚/切断能力的缺失使冲击从"可控"变为"不可逆" |
| A3 敏感数据安全 | **HIGH** | 数据泄露规模从 0 到"部分用户"是质变（触发法律义务），从"部分"到"大规模"是生存级威胁；这条假设没有"灰度"——泄露就是泄露 |

**10% 变化的影响**：
- 供应商故障率上升 10% → 年度重大事故概率显著上升，Bear case 几乎必然发生
- 回滚能力缺失（0% → 有回滚是 0→1 的变化，不是渐进的）→ MTTR 可能从分钟级跳到天级
- 敏感数据泄露范围扩大 10% → 受影响用户数、通知成本、罚款基数、舆论压力线性甚至超线性增长

**结论**：三条假设都是 HIGH 敏感度，且它们是**乘性关系**而非加性关系——任何一条失效，整体风险不是增加 30%，而是可能直接跳到 Catastrophic 情景。

## 5. 不可接受条件（UNACCEPTABLE CONDITIONS / KILL CRITERIA）

> 以下任一条件成立时，**不应上线**。这些不是"建议改进"，而是硬性否决条件。

### 🔴 一票否决项

| # | 不可接受条件 | 对应风险 |
|---|-------------|----------|
| K1 | 供应商未通过安全审计/合规评估，或拒绝提供安全认证（SOC 2 / ISO 27001 / 等保 / 本地合规要求的等效证明） | A1 + A3 |
| K2 | 未与供应商签署数据处理协议（DPA），或协议中未明确数据安全责任、违约赔偿、数据删除/返还条款、审计权 | A3 |
| K3 | 用户敏感数据在传输或存储中未加密（传输层 TLS + 存储加密），或加密密钥由供应商单方掌控且我方无独立管控能力 | A3 |
| K4 | 无数据泄露应急响应预案，或预案未覆盖"供应商侧泄露"场景（含通知流程、监管报告模板、24/7 应急联系人） | A2 + A3 |
| K5 | 完全无法在法定时限内完成用户通知和监管报告（PIPL 要求"立即"），且无替代补偿措施 | A3 |
| K6 | 无任何等效止损手段——既无回滚，也无功能开关/灰度/熔断/流量切换/数据隔离中的至少一项 | A2 |
| K7 | 未完成个人信息保护影响评估（PIA / DPIA），或评估中识别的高风险项未闭环 | A3 |
| K8 | 涉及跨境数据传输但未完成跨境合规要求（安全评估/标准合同/认证，视适用情况） | A3 |
| K9 | 敏感数据范围超出实现功能所必需的最小范围（数据最小化原则不满足），或收集了与功能无关的敏感字段 | A3 |
| K10 | 上线方案中无灰度计划，或灰度无明确的暂停/终止阈值（即"出了问题也不知道该在什么条件下停"） | A1 + A2 |

## 6. 上线门禁（LAUNCH GATES）

> 门禁是上线前**必须全部通过**的检查点。每一项都应有明确的"通过/不通过"判定标准和责任人。

### Gate 1：供应商安全与合规门禁
- [ ] 供应商安全审计完成，无未闭环的高风险发现
- [ ] 供应商提供有效的安全合规认证（SOC 2 Type II / ISO 27001 / 等保 / 适用法规要求的等效认证）
- [ ] 数据处理协议（DPA）已签署，条款覆盖：安全责任、违约赔偿、数据返还/删除、审计权、分包商约束、事件通知时限
- [ ] 供应商财务/经营稳定性评估完成（避免供应商倒闭/被收购导致服务终止）
- [ ] 明确供应商侧的事件通知 SLA（如"安全事件 X 小时内通知"）

### Gate 2：数据保护门禁
- [ ] 敏感数据传输全程 TLS 加密
- [ ] 敏感数据存储加密，密钥管理方案明确（我方有独立管控能力或密钥由我方管理）
- [ ] 数据最小化：仅收集实现功能所必需的字段，有明确的数据分类分级清单
- [ ] 访问控制：供应商侧访问我方数据的权限遵循最小权限原则，有访问审计日志
- [ ] 数据保留和删除策略明确，供应商在合同终止时能证明数据已删除
- [ ] 个人信息保护影响评估（PIA/DPIA）完成，所有高风险项已闭环
- [ ] 如涉及跨境传输，跨境合规手续已完成

### Gate 3：止损能力门禁（替代回滚的最低要求）
> 原方案无回滚，以下为**必须具备的等效止损能力**，否则触发 K6 一票否决。
- [ ] 功能开关（feature flag）：可在分钟级关闭依赖供应商的功能路径
- [ ] 灰度/金丝雀发布能力：可按流量比例逐步放量，支持一键暂停/回退到 0%
- [ ] 熔断机制：供应商异常时自动降级或 fail-close，避免故障扩散
- [ ] 数据隔离：新功能涉及的数据写入有隔离标记，必要时可逻辑隔离/清理
- [ ] 明确的"止血优先级"：回滚/功能关闭 > 热修复 > 人工干预

### Gate 4：应急响应门禁
- [ ] 数据泄露/安全事件应急响应预案已制定并覆盖供应商侧场景
- [ ] 预案包含：事件分级、内部通报路径、用户通知模板、监管报告流程和时限、对外沟通口径
- [ ] 与供应商建立 24/7 应急联络渠道，有明确的升级路径
- [ ] 应急演练已完成（至少一次桌面推演或模拟演练），验证预案可执行
- [ ] 明确我方和供应商在应急响应中的职责分工（RACI）

### Gate 5：监控与告警门禁
- [ ] 供应商服务健康度监控（可用性、延迟、错误率），有明确告警阈值
- [ ] 数据访问异常检测（异常批量查询、异常时间访问、越权访问尝试）
- [ ] 敏感数据流转审计日志完整、可检索、保留期满足合规要求
- [ ] 告警有 7×24 响应机制，告警到人的链路已验证
- [ ] 关键业务指标看板就绪，可在上线后实时观测异常

### Gate 6：灰度发布门禁
- [ ] 灰度计划明确：起始流量比例、放量节奏、每阶段观察时长
- [ ] 每阶段有明确的**自动暂停条件**（如错误率 > X%、P99 延迟 > Yms、数据异常告警触发）
- [ ] 每阶段有明确的**人工评审节点**（通过后方可进入下一阶段）
- [ ] 首批灰度用户选择有依据（如内部用户/低风险用户群），不直接全量
- [ ] 灰度期间有专人值守，决策人明确（谁有权暂停/终止）

### Gate 7：用户告知与同意门禁
- [ ] 用户隐私政策/告知已更新，明确说明数据共享给供应商的情况（共享方、目的、数据类型）
- [ ] 如处理敏感个人信息，已取得用户**单独同意**（PIPL 要求）
- [ ] 用户行使权利（查询、删除、撤回同意、导出）的渠道和流程已就绪
- [ ] 如涉及自动化决策，有说明和拒绝渠道（如适用）

## 7. 对冲建议（HEDGE）

| 对冲类型 | 具体措施 |
|----------|----------|
| **验证对冲**（上线前验证假设） | ① 先以非敏感数据或沙箱环境跑供应商全流程，验证稳定性；② 对供应商进行安全评估和渗透测试；③ 小范围灰度用真实流量验证，而非直接全量 |
| **应急对冲**（假设错误时的 Plan B） | ① 至少引入功能开关 + 熔断作为回滚的等效替代；② 评估并预留第二供应商作为冷备（即使不立即接入，也应完成技术评估和商务对接）；③ 数据层做好我方独立备份，减少对供应商的数据锁定 |
| **预警对冲**（提前发现假设破裂的信号） | ① 供应商 SLA 实时监控 + 错误率/延迟异常告警；② 数据访问行为异常检测；③ 定期（季度）复核供应商安全状态和合规认证有效性；④ 设定"供应商连续 X 分钟不可用即自动熔断降级"的硬阈值 |

## 8. 限制与假设说明

1. **本报告未基于具体的供应商名称、产品细节或实际合同条款**——以上分析基于用户描述的三个特征（单一供应商、无回滚、涉及敏感数据）和行业通用风险模式。具体落地时需结合实际供应商评估结果、合同条款、数据类型和适用法规（如 PIPL、GDPR、行业监管要求）进行细化。
2. **法律合规相关内容为一般性原则，不构成法律意见**。具体合规义务（如 PIPL 下的罚款幅度、跨境传输路径、PIA 要求）应咨询法务/合规团队确认。
3. **概率未量化**：由于缺乏供应商历史故障率、实际数据敏感度分级、系统架构细节等信息，本报告未对各情景给出精确概率值，而是按冲击程度分级。建议在门禁评审中结合实际数据补充量化评估。
4. **"无回滚"的理解**：本报告假设"无回滚"指无版本/配置级别的快速回退能力。如果实际存在功能开关、灰度等可部分替代回滚的机制，风险等级可相应调整，但 Gate 3 中的等效止损能力仍需逐项确认。
5. **本报告不编造事实**：所有风险描述基于行业已知的通用故障模式和合规原则，未虚构具体案例或数据。引用的法规要求（PIPL 相关）为公开法律条文的一般性概括。
