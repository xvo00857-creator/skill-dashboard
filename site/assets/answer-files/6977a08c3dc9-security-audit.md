## 二、分析方法与 Skill 规则的应用

本报告严格采用 Skill `competition-cloud-metadata-path` 的工作流：

1. **映射可达性（Map Metadata Reachability）**：记录到达面（来源 IP、系统、事件）与凭证/身份面。
2. **证明凭证或身份签发（Prove Credential Or Identity Issuance）**：区分"原始元数据可达"与"可用凭证材料"，记录角色名、范围等。
3. **收敛到决定性信任路径（Reduce To The Decisive Trust Path）**：将证据压缩为"到达面 → 凭证 → 下游被接受的动作"的最短链。

**影响本报告结果的一条关键 SKILL.md 规则**：SKILL.md "Workflow" 第 3 步及 reference "Common Pitfalls" 要求——**"将元数据可达性、凭证签发、下游权限接受三者分开"，且"只证明令牌签发而不证明哪个下游 API 接受了它"是常见错误**。该规则直接决定了本报告不把 F-2（令牌范围不匹配）单独定为结论，而是必须用同源 IP 将其与 F-1（DB 导出被接受）串联，并明确标注"日志仅证明相关性、不能单独证明该令牌直接被 DB 接受"这一证据边界，避免过度断言。

> 前置条件说明：SKILL.md 声明本 Skill 应在 `$ctf-sandbox-orchestrator` 已建立沙箱假设后作为下游专项使用。本次任务为用户显式指定的**授权防御性离线日志审计**，无活动沙箱、无在线元数据端点可供探测，且任务明确禁止破坏性操作；因此仅采用本 Skill 的**分析框架与证据打包规范**，未执行任何主动探测或利用步骤。

## 四、信任链重建与证据块

### 链条 A（F-1 + F-2，严重）：服务凭证范围异常 → DB 非预期导出

按 Skill "Chain To Reconstruct" 五段式重建：

1. **可达路径建立**：`203.0.113.8` 先到达 API 层，随后到达 DB 层。
2. **获得响应/令牌**：API 层事件为 `token_scope_mismatch`，主体为 `service-a`，说明该服务令牌被出示但所请求范围与其授予范围不匹配。
3. **提取可用身份/凭证材料**：日志未记录令牌原文或声明（claims），仅能确认 `service-a` 这一服务身份及其范围异常；无法从本日志确认该凭证是否源自实例元数据服务（IMDS）、工作负载身份或其他签发源。
4. **下游 API/信任边接受**：3 分 28 秒后，同一 IP 在 DB 层以 `unknown` 身份触发 `unexpected_export`，DB 接受了请求并执行了导出动作。
5. **确认最终权限/产物**：数据导出已发生（critical 级事件），但日志未记录导出的数据范围、目标位置与体量。

**证据块（按 Skill "Evidence To Keep Together" 打包）**：

- 可达性侧（Reachability）：
  - `2026-08-12T09:04:02Z, system=api, source_ip=203.0.113.8`
  - `2026-08-12T09:07:30Z, system=db, source_ip=203.0.113.8`
- 身份/凭证侧（Identity）：
  - 主体：`service-a`（API 层）；DB 层主体为 `unknown`（未认证/身份丢失）
  - 异常：`token_scope_mismatch`（令牌范围与请求不匹配）
  - 缺失：令牌格式、角色名、audience、issuer、过期时间、账户绑定均未在日志中记录
- 接受侧（Acceptance）：
  - 动作：`unexpected_export`（非预期导出）
  - 结果：DB 接受并执行，severity=critical
  - 缺失：导出的数据对象、行数、目标端未记录

**证据边界（依据 Skill "Common Pitfalls" 明确）**：
- 本日志**不能证明** `service-a` 令牌被 DB 直接接受；两事件的关联依据是同一来源 IP 与 3 分 28 秒的时间邻近性，属强相关而非铁证。
- 本日志**不能证明**凭证来自云元数据服务（无 169.254.169.254 等链路本地端点、无 IMDSv2 令牌、无 hop-limit 等记录）。
- 需要补充 API 网关日志、DB 审计日志、服务令牌签发日志与主机/容器网络日志才能闭环。

### 链条 B（F-3，中危）：admin 暴力尝试

## 五、风险分级与影响评估

### F-1 严重（Critical）— 未知身份 DB 非预期导出
- **影响**：数据机密性受损；导出已实际发生，可能构成数据泄露。
- **利用难度**：低（日志显示已成功执行）。
- **根因假设**（待验证）：DB 层未强制认证与授权，接受了来自 `203.0.113.8` 的匿名/身份丢失请求；或服务凭证在 API 层被拒后仍可直达 DB，存在信任边界绕过。

### F-2 高危（High）— service-a 令牌范围不匹配
- **影响**：服务身份 `service-a` 持有超出其应有范围的令牌，或被用于请求未授权范围；是 F-1 的疑似使能因素。
- **根因假设**（待验证）：服务身份过度授权（未遵循最小权限）、令牌 audience/scope 校验仅在 API 层执行而 DB 层缺失、或工作负载身份绑定错误。

### F-3 中危（Medium）— admin 暴力尝试
- **影响**：若成功可导致管理员账户失陷。
- **现状**：日志窗口内未见成功，但缺乏速率限制/锁定机制的证据。

### F-4 低危（Low）— 畸形日志记录
- **影响**：监控盲区，可能掩盖其他攻击痕迹。
- **现状**：关键字段为空，未被丢弃或隔离。

## 六、修复建议

### P0（立即）
1. **轮换并吊销 `service-a` 凭证**：立即轮换该服务身份的所有令牌/密钥；评估其在各系统的访问权限并临时收窄。
2. **DB 层强制认证与授权**：禁止 `unknown`/匿名身份执行导出等高危操作；在 DB 层独立校验令牌 scope/audience，不信任 API 层的单边校验。
3. **阻断与取证**：隔离或阻断 `203.0.113.8`，保全该主机/容器与 API、DB 的完整日志；排查导出的数据范围、体量与去向，评估数据泄露通报义务。
4. **服务身份最小权限**：按 Skill 强调的"区分节点身份与工作负载身份"原则，为 `service-a` 按功能拆分独立身份，仅授予必要 scope，明确 audience 与下游 API 的绑定。

### P1（24 小时内）
5. **暴力破解防护**：对 admin 登录启用速率限制、指数退避与临时锁定；为 admin 启用 MFA；将 `198.51.100.23` 加入观察/黑名单。
6. **告警规则**：对"同一来源短时间内跨系统高危事件""令牌范围不匹配后紧跟数据导出""N 次登录失败"配置实时告警。

### P2（本周内）
7. **修复日志管道**：将 `malformed_record` 类记录隔离到死信队列并触发完整性告警；将 severity、user、source_ip 设为必填字段。
8. **补全审计字段**：在 API/DB 日志中增加令牌 subject、issuer、audience、scope、请求资源、导出目标与数据量，以满足 Skill 证据打包要求。
