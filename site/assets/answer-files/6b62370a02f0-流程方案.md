## 二、流程总览（严格对应 SKILL.md 的 Core Workflow Pattern）

```
[预检] → [人工确认点 1：连接授权] → [Step1 发现工具 RUBE_SEARCH_TOOLS]
      → [Step2 检查连接 RUBE_MANAGE_CONNECTIONS] → [人工确认点 2：执行确认]
      → [Step3 执行解析 RUBE_MULTI_EXECUTE_TOOL] → [分页拉取] → [结果落盘(幂等)]
      → [人工确认点 3：结果复核]
```

## 三、四项约束设计

### 1. 预检（Pre-flight）
- P1：检查 `RUBE_SEARCH_TOOLS` 是否在可用工具集中；缺失即终止，不猜测 schema。
- P2：调用 `RUBE_MANAGE_CONNECTIONS(toolkits=["affinda"])`，仅当状态为 ACTIVE 才继续；非 ACTIVE 时返回授权链接并暂停，等待人工完成。
- P3：检查待解析文件是否存在、大小是否为 0、扩展名是否在 Affinda 支持范围内；不满足则列出清单后终止。
- P4：检查状态目录可写，确保幂等日志可落盘。
- P5：网络可达性诊断（DNS + HTTPS），作为连接失败时的辅助证据。

### 2. 幂等（Idempotency）
- 每次工作流生成/复用一个 `session_id`（SKILL.md："Reuse session IDs within a workflow"），写入 `.affinda_state/session_id`。
- 已处理文件以 `文件路径 + SHA-256` 为键记录到 `.affinda_state/processed_files.tsv`；重复文件自动跳过，不重复提交。
- 结果文件按 `输入文件名.affinda.json` 落盘；若已存在且校验通过则跳过，不覆盖（除非显式 `--force`）。
- 干跑模式（`--dry-run`）只读检查、不写外部状态以外的任何资源。

### 3. 重试（Retry）
- 仅对瞬时错误（网络超时、429、5xx）重试，最多 3 次，指数退避（2s → 4s → 8s）。
- 鉴权失败（401/403）、schema 校验失败（4xx 参数错误）**不重试**，直接进入人工确认点。
- 每次重试记录 attempt 编号、错误摘要、等待时长。
- 分页：按 SKILL.md "Check responses for pagination tokens and continue fetching until complete"，循环拉取直到无分页令牌。

### 4. 人工确认点（Human-in-the-loop）
- H1（连接授权）：Affinda 连接非 ACTIVE 时，展示授权链接，暂停等待人工完成后再继续。
- H2（执行确认）：发现工具 schema 后、正式提交解析前，展示将调用的 tool_slug 与参数摘要，等待人工确认。
- H3（结果复核）：解析完成后展示结果摘要（字段数、置信度等），等待人工确认是否落盘/覆盖。
- 任何破坏性操作（覆盖已有结果、批量提交）均需显式 `--yes` 或交互确认，禁止静默执行。

## 四、SKILL.md 关键规则对本方案的约束

1. **"Always search first"**：禁止硬编码 tool_slug 与参数；预检 P1 不通过即终止。本次演示正因此停在预检阶段。
2. **"Check connection shows ACTIVE"**：连接非 ACTIVE 不得执行工具；对应预检 P2 与 H1。
3. **"Memory parameter"**：`RUBE_MULTI_EXECUTE_TOOL` 必须带 `memory: {}`，脚本已内置。
4. **"Session reuse"**：同一工作流复用 session_id；脚本通过状态文件保证。
5. **"Pagination"**：结果拉取必须循环到无分页令牌；脚本执行阶段内置循环。
