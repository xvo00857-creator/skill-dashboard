## 5. 证据链分析（按 Skill 框架）

### 候选链 A（高置信度关联，中置信度机制）：203.0.113.8 凭据中转 → 数据库导出

| 链环节 | 日志证据 | 状态 |
|---|---|---|
| 来源原语 | 203.0.113.8 对 api 发起请求，触发 `token_scope_mismatch`（09:04:02） | 有证据 |
| 中转/规范化 | 日志未记录 URL 构造、请求头、重定向、host 允许列表等规范化细节 | **缺失** |
| 凭据/敏感响应 | 令牌作用域与 `service-a` 不匹配——提示存在越权令牌，但日志未记录令牌字段、作用域内容、有效期 | 部分证据（仅异常信号） |
| 下游接受访问 | 同一 IP 于 09:07:30 在 db 触发 `unexpected_export`，用户 `unknown`——存在实际的数据导出行为 | 有证据 |

**判定：** 同一外部 IP 在约 3 分半钟内先触发 API 令牌作用域异常、后发生数据库异常导出，时间与来源高度重合，**强烈提示**"越权令牌 → 下游接受 → 数据导出"的凭据中转链。其中"下游接受访问"环节有 `unexpected_export` 事件作为接受性证据，因此并非仅停留在"可达性/异常"层面。

**但依据参考文件 Common Pitfalls，以下仍属待核实，不能据现有日志定论：**

- 无法证明导出数据的内容、量级与去向；

## 6. 修复建议

### 针对 P0（数据库异常导出）
1. 立即在数据库侧核查 09:07:30 前后 `unknown` 身份的会话：导出语句、目标表、数据量、客户端网络信息，确认是否构成实际数据泄露。
2. 封禁或隔离来源 IP `203.0.113.8`，并在主机/网络层排查该 IP 对应的访问凭证与进程。
3. 轮换 `service-a` 及数据库相关账号的密钥/令牌，撤销 09:04 前后签发或使用的异常令牌。
4. 对数据库导出操作启用强制审批与白名单，禁止匿名/未识别身份执行导出。

### 针对 P1（令牌作用域不匹配）
5. 校验 API 网关的令牌作用域强制逻辑：拒绝作用域不匹配的令牌并记录完整声明（issuer、subject、scope、audience、过期时间），不可仅告警后放行。
6. 建立 api→db 的服务间调用鉴权绑定（如 mTLS、服务账号最小权限、audience 校验），防止一个作用域的令牌被带到下游数据库接受。
7. 对 `token_scope_mismatch` 配置实时告警与自动熔断阈值。

### 针对 P2（admin 登录失败）
8. 对管理后台启用登录失败速率限制、账户锁定与 MFA；对 `198.51.100.23` 进行临时封禁或加验证码。

### 针对 P3（畸形日志）
9. 排查日志采集/解析管道，确认 09:09:00 的畸形记录是管道故障还是人为注入；对 web 访问日志做字段完整性校验与异常写入告警。
10. 关键日志启用防篡改（集中存储、只追加、完整性校验），避免在安全事件后出现字段缺失。

### 通用改进
11. 按 Skill"What To Preserve"要求扩充日志字段：记录请求方法、URL 构造、关键请求头、重定向链、响应码/长度差异、令牌声明摘要，使未来的凭据中转链可直接从日志还原。
