# capture 变化场景执行方案

> 场景：可用时间临时减半 · 周三新增不可移动评审会 · 结果需交接给另一位同事
> 核心工作：把零散灵感、待办和资料快速收集并整理到可行动的位置
> 编制时间：2026-08-10（周一）
> 依据：随附 `capture` Skill v1.0.0（SKILL.md + 3 references + 3 scripts，已真实读取并执行）

---

## 1. 目标

在**时间减半 + 周三硬截止 + 需交接**三重约束下，仍然达成 capture 的本职——
**零信息丢失地把散乱内容收进一个可行动、可交接的位置**，并且让接手同事在不依赖口头补充的前提下能继续推进。

不是"做得更全"，而是"在更窄的窗口里，把对评审会和交接最关键的东西先落地，其余不丢但降级"。

---

## 2. 依据（哪些 capture 原则保留，哪些要调整）

| capture 原始原则（SKILL.md §Operating Principles） | 本场景处理 | 原因 |
|---|---|---|
| ① Capture everything（零丢失） | **保留，但分级** | 零丢失是底线；但时间减半不允许"先全收再慢慢 prune"，必须在收集时就打优先级标签，而不是事后 prune。 |
| ② Preserve voice（保留原话） | **保留，用途变了** | 原话保留不再是为了"用户自己认出"，而是为了让接手同事读到原始语气和情绪强度（"这个很重要"vs"随便想想"），避免交接时信息被企业化稀释。 |
| ③ Match output complexity to input | **保留并扩展** | 仍然按 dump 实际体量决定 full 4-section 还是 compressed；但因为要交接，**两种格式都要追加一个"交接块"**（状态/下一步/阻塞/接手人），这是原 skill 没有的。 |
| ④ Be honest about ambiguity | **保留并强化** | 交接场景下歧义代价更高（接手人没法回头问）。原本"最多 1 个澄清问题"的纪律，本场景改为：**收集时不打断（保持 fast-to-action），但所有存疑项统一进"待确认"清单随交接物一起交出去**，而不是猜。 |
| ⑤ No action without approval | **调整** | 原 skill 要求"Section 4 的 offer 等用户挑"。本场景下用户时间减半且要交接，**改为：只做"组织 + 分级 + 交接物生成"这一个动作本身（这是 capture 的本职，不需要审批）；任何超出组织的实质动作（发消息、改文件、建任务）仍然不自动执行，但在交接块里明确写成"建议接手人做的下一步"**。 |

额外依据：
- `references/complexity_matching.md`：≤5 项无聚类用 compressed；8+ 项有聚类用 full。本场景按实际 dump 体量走，不预设。
- `references/workspace_detection.md`：Section 3 连接**只列真实 Glob/Grep/Read 验证过的**，不编造。本场景已对当前工作目录跑过 `workspace_inventory.py`，结果见 §6 自检。
- `references/voice_preservation.md`：项目名用用户原话，不企业化（"ferret app"不改成"Pet Companion Platform"）。交接文档里同样遵守。

## 3. 约束变化如何改变原方案

### 3.1 可用时间减半
- **原方案节奏**：dump → 4 段组织 → 等用户从 Section 4 挑一个 → 再做。这是"多轮、低紧迫"。
- **变化后**：没有多轮空间。组织动作必须**一次到位**，并且当场给出优先级，而不是等用户挑。
- **具体改变**：
  - Section 4 "How I can help" 从"你想我做哪个"变成"按优先级排好的接手人下一步清单"。
  - 不做"事后 prune"，收集时即分级（见 §5 优先级框架）。
  - 压缩格式的触发门槛降低：原本 5 项以下才 compressed，本场景**7 项以下且无强聚类就走 compressed**，省结构开销。

### 3.2 周三不可移动评审会
- **原方案**：没有时间锚，所有项平等进入 Projects/Tasks。
- **变化后**：周三评审会是**唯一硬截止**，所有项必须回答一个问题："**周三评审会前必须 ready 吗？**"
- **具体改变**：
  - 任务清单按"周三前必须 / 周三后可做 / 评审会现场要决定 / 与评审会无关"四桶分类，而不是原 skill 的扁平 Tasks。
  - 评审会本身作为一个项目（Project）入 Section 1，所有为评审会准备的子项挂在它下面。
  - 倒排：今天（周一）→ 周二 → 周三会前，每个时间桶只放能放下的量，因为总时间减半，放不进的直接降级。

### 3.3 结果交接给另一位同事
- **原方案**：输出读者是用户自己，靠"自我识别"工作。
- **变化后**：读者是**接手同事**，他没有上下文、不在用户脑子里、没法即时问。
- **具体改变**：
  - 每个项目/任务追加四个交接字段：**现状（做到哪了）/ 下一步（接手人立刻能做什么）/ 阻塞（卡在哪、找谁）/ 优先级（周三前 or 之后）**。
  - 原 skill 的 Section 3 "Connections" 从"可能相关的文件"变成"**接手人需要知道的文件/链接/联系人位置**"——仍然只列真实验证过的，不编造。
  - 原话保留，但允许在原话后加一行`（交接注：...）`补充接手人需要的客观信息，不替换原话。
  - 结尾不再是"Which of these should I tackle?"，而是"**交接物已就绪，接手人从§下一步开始即可**"。

## 4. 调整后的执行步骤

> 步骤 1–4 是 capture 本职（组织动作本身，按 §2 不需要额外审批）；步骤 5 是交接物生成；步骤 6 起是接手人的动作，本方案只列建议、不自动执行。

### 步骤 1：无前置 intake，直接收（保持 fast-to-action）
- 不先问 3 个澄清问题（SKILL.md 明确反模式）。
- 让对方把脑子里的东西一次倒完：语音、文字、贴文件链接都行。
- 边收边在每条后面**当场打两个标签**：
  - **类型**：task / decision / question / idea / project-component / context（用 `dump_classifier.py` 的分类作种子，人工覆盖）
  - **时间桶**：`周三前` / `周三后` / `评审决定` / `无关`（这是原 skill 没有的、本场景加的）

### 步骤 2：跑工具链（真实执行，不跳过）
- `python complexity_estimator.py <dump文件>` → 决定 full 还是 compressed。
- `python dump_classifier.py <dump文件>` → 拿到每条的标签种子。
- `python workspace_inventory.py --root <工作目录> --keywords "<从dump里抽出的关键词>"` → Section 3 连接，**只采纳真实命中**。
- 三个脚本都是 stdlib-only，已在本环境验证可跑（见 §6 自检）。

### 步骤 3：组织成调整后的结构

**如果是 full 格式（8+ 项且有聚类）**，在原 4 段基础上改造：

```
## Projects & Ideas
### {项目名，用原话}
- 现状：{做到哪了，不知道就写"未开始"}
- 下一步：{接手人立刻能做的一件事}
- 阻塞：{卡在哪/找谁，没有就写"无"}
- 优先级：周三前 / 周三后 / 评审决定
- {子项/原话保留}
- Q: {开放问题，留在项目内，不另起顶层分类}
- Decide: {需要拍板的事}

## Tasks（按时间桶分四组，不再扁平）
### 周三前必须
- {祈使句原话}  [Project: X]  ← 接手人：{具体下一步}
### 评审会上要决定
- Decide: ...
### 周三之后
- ...
### 与评审会无关（不丢，但降级）
- ...

## Connections（接手人需要的真实位置）
- {文件/文件夹/链接}：{为什么相关，证据是 Glob/Grep 命中了什么}
- （若无命中）No connections found — workspace inventory clean.
- （若工作目录不可达）明确说明，不编造。

## Handoff（本场景新增，替代原 Section 4）
- 接手人：{同事名字/待填}
- 从哪开始：{第一步做什么，对应哪个 task ID}
- 评审会时间：周三 {具体时间，待填}
- 评审会要带的东西：{从"周三前必须"桶里汇总}
- 待确认清单（收集时没打断、统一放这）：
  - {存疑项 1}
  - {存疑项 2}
- 我（原负责人）能被打扰的窗口：{时间减半后还剩哪些时段，待填}
```

**如果是 compressed 格式（≤7 项或无聚类）**，在原两段基础上把交接信息 inline：

```
## What I heard
- {原话}（现状：... / 下一步：... / 优先级：...）
- ...

## Handoff
- 接手人从第 1 项开始；周三前完成第 1、3 项；第 2 项带到评审会决定。
- 待确认：...
```

### 步骤 4：保留原话，只加交接注
- 项目名、任务措辞用用户原话（"fix the damn auth bug" 不改成"修复认证模块缺陷"）。
- 客观补充信息（位置、联系人、状态）放在`（交接注：...）`里，不覆盖原话。

### 步骤 5：生成交接物
- 一份 Markdown 文件（即上面结构），放在双方都能拿到的位置（飞书文档/共享盘/git 仓库，具体位置由用户定，本方案不替用户决定发布位置）。
- 文件头写明：原负责人、接手人、生成时间、评审会时间、最后更新时间。
- **不自动发消息、不自动建任务、不自动改文件**——这些是超出"组织"的动作，按 §2 原则 ⑤ 的调整版，只写成"建议下一步"。

### 步骤 6：交给接手人（建议动作，非自动执行）
- 建议原负责人花 5 分钟当面/语音过一遍"周三前必须"桶和"待确认"清单，其余让接手人自己读文档。
- 建议接手人接手后第一件事：把"待确认"清单里能自己决断的决断掉，不能的集中一次问原负责人，不要碎片化打断。

## 5. 优先级框架（周三倒排）

时间减半意味着**不可能全做**。按以下顺序砍：

1. **周三前必须（保）**：评审会要展示/要决定/阻塞别人的。这一桶要严格控制数量——时间减半，这一桶也应近似减半。如果塞不下，说明评审会范围本身要缩，把"想展示的"降级为"能展示的"。
2. **评审会上决定（保）**：需要现场拍板的 Decide 项。这一桶不占执行时间，但必须提前把选项和材料备齐。
3. **周三之后（缓）**：有价值但不卡评审会。原样记录，不做、不展开、不分配，等评审会后由接手人重新评估。
4. **与评审会无关（存但不做）**：零丢失原则要求记录，但本周期不动。放进"冰山区"，接手人日后自行决定。

**取舍红线**：
- 不因为"反正都记下来了"就把第 3、4 桶的项也展开做——时间不允许。
- 不把第 3、4 桶的项偷偷塞进第 1 桶"顺便做一下"——这是时间减半场景下最常见的失控点。
- 原话和原始链接必须保留，哪怕是第 4 桶——这是 capture 对未来接手人的承诺。

## 6. 关键取舍

| 取舍 | 放弃什么 | 保留什么 |
|---|---|---|
| 覆盖范围 vs 深度 | 放弃"本周内推进所有项目"的幻觉 | 保"周三评审会相关项做到可交接" |
| 多轮精修 vs 一次到位 | 放弃"等用户慢慢挑 Section 4 offer"的多轮节奏 | 保一次组织 + 当场分级 + 交接物直接可用 |
| 原话 vs 企业化 | 放弃把零散想法润色成正式项目名 | 保原话和情绪强度，交接注里补客观信息 |
| 零丢失 vs 当场分级 | 放弃"先全收再 prune"的奢侈 | 保零丢失（每条都在），但用时间桶分级替代事后 prune |
| 澄清 vs 不打断 | 放弃"最多 1 个中途澄清问题"的原纪律 | 保 fast-to-action，所有存疑项进"待确认"清单一次性交接 |
| 连接发现 vs 诚实 | 放弃"看起来有道理"的关联 | 保只列 Glob/Grep 真实命中；当前工作目录已验证无周三/评审/handoff 相关文件（见 §7） |

## 7. 风险

| 风险 | 触发条件 | 应对 |
|---|---|---|
| 周三前必须桶仍然超载 | dump 体量本身就超过减半后的容量 | 当场和原负责人确认：评审会范围能不能缩？不能缩就明确告知"做不完"，让原负责人决定砍哪些，而不是默默加班。 |
| 接手人看不懂原话 | 原话里有只有原负责人懂的缩写/代称（"那个东西""Sarah 的事"） | 收集时不打断，但在交接注里标`（待确认：指什么？）`，集中进待确认清单，让原负责人一次性补全。 |
| 编造连接 | Section 3 为了"显得有用"猜了文件/链接 | 严格遵守 `workspace_detection.md`：只列真实命中，没命中就写"No connections found"。已对当前目录跑过 inventory，结果：扫描 7 个文件，`wednesday`/`handoff`/`review` 关键词零文件名命中、零内容命中（review 仅在 dump_classifier.py 的正则里出现，与本场景无关）。 |
| 交接物发出去后原负责人还在被碎片化打断 | 接手人遇到问题就问 | 文档里明确"能决的自己决，不能决的集中在每天 X 点一次问"，并写清原负责人还剩哪些可打扰窗口。 |
| 评审会时间/地点/参会人未知 | 题目只说"周三增加一场不可移动的评审会"，未给具体时间地点 | 交接物里留占位符，由原负责人填；本方案不编造具体时间。 |
| 时间减半的"一半"口径不清 | 是每天时长减半？还是总天数减半？ | 方案按"本周可用于此工作的总容量减半"处理；具体口径由原负责人确认后微调每个时间桶的容量。 |

## 8. 衡量方式（怎么判断这次 capture 做对了）

- **零丢失**：接手人读完文档后，原负责人脑子里没有"啊我还忘了说 X"。检查方式：原负责人花 2 分钟扫一遍，确认没有遗漏项。
- **可交接**：接手人不找原负责人问"这是什么"，就能开始动"周三前必须"桶里的第一项。检查方式：接手人看完后能复述出第一步要做什么。
- **周三就绪**："周三前必须"桶里的每一项在周三会前都有明确的 done 状态（要么做完、要么明确转为"评审会决定"）。检查方式：周二晚上对照桶清单逐项勾。
- **不编造**：Section 3 里每条连接都能指回一个真实文件/链接；没有"你可能有个 X"这种话。检查方式：接手人点每个链接都能打开。
- **不越权**：没有任何超出"组织+生成交接物"的动作被自动执行（没自动发消息、没自动建任务、没自动改文件）。检查方式：原负责人确认所有对外动作都是自己或接手人手动做的。

## 9. 下一步（立即可做）

1. **原负责人**：把脑子里的零散内容一次倒出来（文字/语音/贴链接均可，不预设格式）。
2. **跑工具链**：按 §4 步骤 2 跑 `complexity_estimator.py` + `dump_classifier.py` + `workspace_inventory.py`，决定 full/compressed 并拿到真实连接。
3. **组织成 §4 步骤 3 的结构**，每条打时间桶标签。
4. **填交接块里的占位符**：接手人名字、评审会具体时间地点、原负责人可打扰窗口。
5. **生成 Markdown 交接物**，放到双方都能访问的位置（位置由原负责人定）。
6. **当面/语音 5 分钟过一遍**"周三前必须"桶和"待确认"清单。
7. **接手人**：从"周三前必须"桶第一项开始；"待确认"清单集中一次问完。

> 本方案本身只到步骤 5 生成交接物为止；步骤 6、7 是建议动作，需原负责人/接手人手动执行，本方案不自动触发。
