# add-ollama-tool 受约束流程方案与演示结果

## 一、Skill 能力边界（以 SKILL.md 为准）

`add-ollama-tool` 的真实职责是：**向一个名为 NanoClaw 的特定项目中集成基于 stdio 的 Ollama MCP 服务器**，使容器内 agent 能调用主机 Ollama 守护进程提供的本地模型。具体包括：

- 复制 4 个 TypeScript 文件到 NanoClaw 的两棵代码树（container/Bun 与 host/Node）
- 在 `container/agent-runner/src/index.ts` 的 `mcpServers` 对象中注册 `ollama` 条目
- 在 `src/container-runner.ts` 中转发 `OLLAMA_HOST` / `OLLAMA_ADMIN_TOOLS` 环境变量
- 将 `[OLLAMA]` 日志行提升到 info 级别
- 向 `.env.example` 追加配置桩
- 运行 `pnpm run build`、`tsc --noEmit`、`vitest`、`bun test`、`container/build.sh` 验证
- 可选启用模型管理工具（pull/delete/show/list-running），重启服务，人工验证推理

**该 Skill 不负责**：安装 Ollama、拉取模型、启动/停止 Ollama 守护进程、管理 Docker、创建 NanoClaw 项目本身。这些是前置条件或用户手动操作。

## 三、受约束流程方案

交付脚本：`add-ollama-tool-flow.sh`（约 470 行 bash），严格对应 SKILL.md 四阶段。

### 3.1 安全机制

| 机制 | 实现 |
|---|---|
| **预检（Pre-flight）** | Phase 1 检查项目目录、Skill 源文件、工具链、4 个集成点文件、Ollama 连通性；存在 BLOCKER 时退出码 1，拒绝进入 Phase 2 |
| **幂等（Idempotency）** | 已应用检测（`ollama-mcp-stdio.ts` 存在则跳 Phase 3）；文件复制前 `cmp -s` 比对；代码编辑前 grep 标记；`.env.example` 追加前检查标记字符串；重复运行不产生副作用 |
| **重试（Retry）** | Ollama 连通性检查最多 3 次，间隔 2 秒 |
| **人工确认点** | 每个变更操作（复制文件、编辑 index.ts、编辑 container-runner.ts、追加 .env.example、运行构建命令、写入 .env、重启服务）前均需交互式输入 `y` 确认；`--yes` 可跳过（仅限 CI） |
| **默认 dry-run** | 不加 `--apply` 时只报告"将执行什么"，不写入任何文件 |
| **备份** | `--apply` 模式下修改任何已有文件前自动备份为 `.bak.<时间戳>` |
| **不静默假设** | `--project-dir` 为必需参数，不默认当前目录是 NanoClaw 根目录 |
| **共享块保护** | 日志分支编辑检测已有多分支块（如 `[ATOMIC]`），按 SKILL.md 要求只添加 `[OLLAMA]` 分支，不替换其他工具的分支 |

### 3.2 使用方式

```bash
# 预检（默认 dry-run，不修改任何文件）
./add-ollama-tool-flow.sh --project-dir /path/to/nanoclaw

# 实际应用（仍会逐次请求人工确认）
./add-ollama-tool-flow.sh --project-dir /path/to/nanoclaw --apply

# 仅运行预检阶段
./add-ollama-tool-flow.sh --project-dir /path/to/nanoclaw --phase 1

# 启用管理工具并设置自定义 host
./add-ollama-tool-flow.sh --project-dir /path/to/nanoclaw --apply --admin-tools --ollama-host http://10.0.0.5:11434
```

## 七、影响交付结果的 SKILL.md 规则（至少一条）

**规则：Phase 1 的 "Check if already applied" 与前置条件阻断。**

SKILL.md 第 26 行明确："Check if `container/agent-runner/src/ollama-mcp-stdio.ts` exists. If it does, skip to Phase 3." 第 30-40 行要求验证 Ollama 守护进程可达，不可达时需先安装/启动。

这条规则直接决定了本次交付形态：预检发现目标项目不存在且 Ollama 未运行后，脚本**拒绝进入 Phase 2**，交付物是受约束的自动化流程脚本而非"已应用"的虚假结果。如果忽略这条规则继续执行，所有 `cp` 和编辑命令都会因目标路径不存在而失败，或更糟——在错误位置创建文件。脚本将此规则实现为硬阻断（BLOCKER + exit 1），而非警告后继续。

**另一条关键规则：管理工具 opt-in 门控。** SKILL.md 第 14 行与第 196-211 行规定 `ollama_pull_model`/`delete_model` 等变更类工具仅在 `OLLAMA_ADMIN_TOOLS=true` 时注册，且必须询问用户。脚本将此实现为 Phase 3 的显式 `--admin-tools` 参数与人工确认点，默认不启用——这影响了演示范围（不测试 pull/delete）。
