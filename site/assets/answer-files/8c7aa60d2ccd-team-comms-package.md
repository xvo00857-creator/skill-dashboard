## 0. 边界声明（先读）

本次任务执行前，起草方实际掌握的输入只有 team-communications Skill 本身（`SKILL.md` + 4 份 reference 模板）。**任务描述中提到的"会议记录""范围冲突""缺失的负责人/截止日期""含手机号的资料"等原始材料并未作为附件提供**，也没有连接 Slack / 邮件 / 日历 / 云盘等可拉取真实数据的工具。

按 `SKILL.md` Anti-Patterns 与各 reference 的硬性要求：

- 不得编造指标、成果、负责人、截止日期或已完成动作；
- 3P 与 general-comms 均要求在写之前确认团队名、受众、时间范围、目的与语气；
- general-comms 明确要求先问"目标受众 / 目的 / 语气 / 格式"再动笔。

因此，本交付物是**可直接评审的文案包骨架**：所有事实位以 `【待确认：…】` 标注，未填处一律留空，不做任何推断性补全。文案在负责人/截止日期/范围冲突解决前**不得发送**。

## 2. 冲突、缺失信息、风险登记

### 2.1 范围冲突
- 冲突点：【待确认：范围具体在争什么——功能集 / 上线时间 / 资源投入 / 责任边界】
- 冲突方：【待确认：哪几方，谁有裁决权】
- 当前状态：【待确认：是否已有结论 / 是否仍在升级】
- 处理原则：在冲突未裁决前，对外文案**只陈述已达成一致的部分**；争议部分用"正在评估，将于【日期】前同步"措辞，不替任何一方背书。

### 2.2 缺失信息
- 负责人缺失：会议记录中【待确认：哪些 action item 无 owner】→ 文案中不写"由 X 负责"，改写为"负责人待确认，将在【日期】前补齐"。
- 截止日期缺失：【待确认：哪些里程碑无日期】→ 文案中不写具体日期，改写为"时间线待确认"。
- 团队名 / 项目名 / 时间周期：全部待确认。

### 2.3 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 在范围冲突未解决前对外发声 | 被解读为站队或既定结论 | 只写已共识部分；争议部分标注"评估中" |
| 补全缺失 owner / deadline 时编造 | 信任崩塌（Skill 反模式） | 一律 `【待确认】`，由有权限的人补 |
| 敏感信息（手机号等）外泄 | 隐私 / 合规风险 | 文案不出现个人手机号；用群组邮箱 / 工单 / 内部 IM 频道代替 |
| 未经授权发送 | 越权 | 本稿仅为评审稿；发送前需【待确认：授权人】书面确认 |
| 受众错配（团队稿发给管理层，或反之） | 粒度过粗 / 过细 | 分版本，见 §5；发送前按受众清单核对 |

## 3. 最小可安全执行方案（在现有信息下）

**能做的：**
1. 以本骨架为基础，等待用户 / 团队补齐 §1 中所有"待确认"项。
2. 补齐后，按 §5 的受众版本分别填充，每版控制在 Skill 要求长度内（3P 每段 1–3 句；newsletter 每条 1–2 句；FAQ 每答 1–2 句）。
3. 对所有事实位做"事实—来源"回链：每条事实必须能指回会议记录 / 文档 / 邮件 / 负责人确认中的一处。
4. 对含个人信息的字段做脱敏扫描（手机号、私人邮箱、身份证号等）。
5. 由【待确认：授权人】评审并书面批准后，通过【待确认：渠道】发送。

**不能做的（停止线）：**
- 不替范围冲突下结论；
- 不编造负责人、日期、指标、链接、已完成动作；
- 不在文案中保留任何个人手机号；
- 不在未授权情况下发送或转发给任何受众。

---

## 4. 停止条件（命中任一即停，回到用户 / 团队确认）

1. 任一"待确认"项无法在 24 小时内由有权限的人补齐 → 暂停该版本，不发"半成品"。
2. 范围冲突在发送前仍无裁决人或结论 → 暂停对外版本，仅保留"冲突已识别、正在升级"的内部告知。
3. 发现源材料含未脱敏的手机号 / 私人邮箱 / 身份证号 → 暂停发送，先脱敏并经合规 / 当事人确认。
4. 授权人未明确批准 → 不发送。
5. 事实回链检查中任一条事实找不到来源 → 从文案中删除该条，不保留。

## 5. 沟通文案草稿（分受众，事实位留空）

> 说明：以下为骨架。emoji 与版式参照 `references/3p-updates.md` 的严格格式（团队版）；管理层与协作方版按 general-comms 原则裁剪；全员版按 newsletter 分区。**所有 `【待确认：…】` 必须在发送前替换为可回链事实或删除。**

### 5.1 受众 A：团队内部（执行者）— 3P 格式

```
🚀 【待确认：团队名】（【待确认：起止日期，通常一周】）
Progress: 我们在【待确认：项目/变化主题】上【已达成一致的 1–3 句进展，含可回链事实/指标】。范围中【已共识部分】已确认；【仍有争议部分】正在评估。
Plans: 下周我们将【1–3 句：已分配 owner 且有日期的事项】。负责人或日期尚未确认的事项见下方"待补齐"，不写入本版 Plans。
Problems: 【1–3 句：真实阻塞，例如"X 模块负责人待确认""Y 截止日期缺失，影响下游排期"】。敏感沟通请走【内部 IM 频道 / 工单 / 群组邮箱】，勿在公开渠道贴个人手机号。
```

待补齐清单（不随 3P 正文发送，仅团队内跟进）
- [ ] 【待确认：事项】— 负责人：【待确认】— 截止：【待确认】
- [ ] …

### 5.2 受众 B：协作方 / 下游团队 — 简式公告

```
主题：【项目名】变化同步（【日期】）

Hi all，
同步一项与你方相关的变化：【1–2 句客观描述，只含已共识事实】。

对你们的影响：【待确认：接口/排期/交付物变化，无则写"当前评估无直接影响，如有更新再同步"】。
需要你们配合：【待确认：具体 ask，无 ask 则写"暂无需配合"】。
联系人：【团队/角色邮箱或 IM 频道，不写个人手机号】。

范围中【争议点】仍在内部评估，确定后将于【日期前】另行同步。
```

### 5.3 受众 C：管理层 / 领导层 — 决策视角一页纸

```
【项目名】变化同步 · 【日期】 · 汇报人：【待确认】

一句话：【1 句：变化是什么 + 对 OKR/里程碑的净影响】。

已确认：
- 【事实 1，含指标/链接】
- 【事实 2】

待决策 / 风险：
- 范围冲突：【双方主张 + 建议裁决路径，不替领导拍板】
- 缺失 owner / deadline：【清单 + 补齐计划】
- 敏感信息处理：【已脱敏 / 待合规确认】

建议下一步：【1–3 条可选项 + 各自代价，由领导选择】
衡量方式：见 §6。
```

### 5.4 受众 D：全员（仅在变化影响全员时启用，否则跳过）— newsletter 分区

> 按 `references/company-newsletter.md`：📣 公司公告 / 🎯 重点进展 / 🧭 领导动态 / 🧵 社交动态。本变化只在确属公司级时进入"📣 公司公告"，每条 1–2 句并链接权威文档；否则不发全员版，避免"Information only relevant to small groups"。

```
📣 公司公告
- 我们在【项目名】上【1 句已共识变化】，详情见【权威文档链接】。范围细节仍在评估，确定后再同步。
```

### 5.5 可选：FAQ 配套（如已收到重复提问）

按 `references/faq-answers.md` 格式：

```
- *Question*: 【待确认：员工真实在问的问题，需来自 Slack/邮件/文档，不编造】
- *Answer*: 【1–2 句，基于官方沟通；不确定时写"待定，将于【日期】前更新"；需高管口径的标注"需官方回应"】
```

## 6. 衡量方式（如何判断这次沟通"有效"）

> 指标必须在发送前与授权人确认基线，否则不写具体数字。

- 到达率：目标受众在【渠道】的已读 / 已送达比例 ≥ 【待确认：基线】。
- 理解度：发出后 48 小时内，重复提问数较变化前【下降/持平/上升，待基线】；在 FAQ 中跟踪。
- 执行对齐：所有 action item 在截止日期前有 owner 且状态更新率 ≥ 【待确认】。
- 风险事件：因本沟通导致的误读、越权转发、敏感信息外泄 = 0。
- 升级率：因范围冲突未解决而升级到管理层的次数（用于判断是否需要更早裁决）。
