## 5. 关键事件分析

### 5.1 R1/R2/R3：疑似越权 → 数据外泄链（09:04:02 ～ 09:07:30）

**事实链**
1. 09:04:02，API 层记录 `service-a` 令牌发生 `token_scope_mismatch`（high），来源 `203.0.113.8`。这表示该服务账号持有的令牌尝试访问其被授权范围之外的资源——可能是令牌配置错误，也可能是令牌被盗用后尝试越权。
2. 09:07:30，DB 层记录 `unexpected_export`（critical），用户字段为 `unknown`，来源同为 `203.0.113.8`。"unexpected_export" 表示发生了不符合基线的数据库导出行为；"unknown" 表示未能映射到已知身份。

**关联判断**
- 两事件共享同一来源 IP，时间相隔约 3 分 28 秒，且 severity 从 high 升级到 critical，符合"先试探越权、后实施导出"的攻击链假设。
- ⚠️ **但证据是环境性的，非确证**：两条记录的 user 不同（`service-a` vs `unknown`），且日志中没有会话 ID、请求 ID、导出任务 ID 或令牌序列号能把二者直接绑定。存在"同一 NAT 出口下的不同主体""配置错误引发的偶发告警"等替代解释。因此 R1 置信度评为"中"，R2（单事件本身）置信度为"高"。

**潜在影响**
- 若导出属实，可能涉及用户隐私、订单、支付等敏感数据外泄，触发合规通报义务（具体取决于真实数据类型与适用司法辖区，本报告不臆测数据内容）。

### 5.2 R4：管理员账号连续登录失败（09:03:45 ～ 09:03:49）

- 同一 IP `198.51.100.23` 在 4 秒内对 `admin` 发起两次失败登录。
- 两次失败尚不足以构成典型暴力破解（通常阈值更高），但针对 `admin` 这一高权限账号名的定向尝试本身即为可疑信号，可能是撞库/喷洒的早期阶段。
- ⚠️ 该 IP 与 R1 的 `203.0.113.8` 不同，目前无证据将其与外泄链关联；不排除为相互独立事件。

### 5.3 R5：畸形日志记录（09:09:00）

- 记录 `web,,malformed_record,,` 缺失 severity、user、source_ip。
- 两种可能：(a) 日志采集/解析管道缺陷（字段映射或转义问题）；(b) 异常请求导致日志组件写入失败，或更少见的日志干扰/篡改。
- ⚠️ 仅凭一条记录无法区分原因。无论哪种，都降低了审计可追溯性，需作为数据质量问题跟进。

### 5.4 R6：正常基线

- `alice` 于 09:00:12 从 `192.0.2.10` 成功登录，无异常，作为本次窗口的正常行为参考。

## 6. 修复建议（按优先级）

### P0 — 立即处置（针对 R1/R2/R3）

1. **冻结与轮换**：立即轮换 `service-a` 的所有令牌/密钥；临时撤销该账号的 DB 导出权限直至调查完成；对 `unknown` 身份对应的数据库会话/导出任务进行定位与终止（如仍在运行）。
2. **保全证据**：在只读副本上调取 09:00–09:10 UTC 期间 API 网关、DB 审计日志、IAM/STS 日志、导出对象存储访问日志，按会话 ID/请求 ID/令牌序列号/源 IP 做关联检索；导出镜像与日志做哈希留存，避免污染原始证据。
3. **影响面评估**：确认 `unexpected_export` 导出了哪些库/表/行数、是否含个人信息或支付数据；据此判断是否需要启动数据泄露响应与合规通报流程（由真实数据管控团队按适用法规判定）。
4. **临时管控**：在 DB 层导出通道增加强制审批/白名单；对来自 `203.0.113.8` 的访问临时阻断或置于监控模式（在授权范围内由运维执行，本报告不代为操作）。

### P1 — 短期加固（针对 R3/R4）

5. **令牌最小权限**：审计 `service-a` 的令牌 scope 配置，落实最小权限；为服务账号令牌设置短有效期、自动轮换与受众（audience）绑定；对 `token_scope_mismatch` 建立实时告警与自动降级（如连续 N 次即吊销令牌）。
6. **管理员登录防护**：对 `admin` 等特权账号启用 MFA；登录失败增加速率限制与指数退避/临时锁定；将特权登录纳入高优先级告警（含成功+失败）。
7. **身份可追溯性**：消除 DB 层 `unknown` 用户——所有导出必须携带可解析的调用方身份（服务账号或真人），拒绝匿名导出。

### P2 — 中期改进（针对 R5 与整体）

8. **日志管道修复**：排查 `malformed_record` 成因，修复字段缺失；为日志增加 schema 校验与死信队列，畸形记录不应静默丢失。
9. **统一关联 ID**：在 web/api/db 全链路注入一致的请求/会话 ID，使跨层关联不再依赖源 IP 这类弱证据。
10. **基线与检测规则**：为 DB 导出建立行为基线（谁、何时、导什么、多大），偏离即告警；将"令牌越权后短时间内 DB 导出"沉淀为关联检测规则。
11. **留存与监控**：按合规要求设定日志留存周期；对安全事件日志做访问控制与防篡改（WORM/只追加存储）。
