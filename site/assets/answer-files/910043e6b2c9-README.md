# KubeSphere 持续交付配置 — 示例服务 demo-go-http

基于 `kubesphere-devops-pipeline` Skill 的实际能力，为示例 Go HTTP 服务设计的 KubeSphere 持续交付配置。

## 一、方案概述

| 项目 | 说明 |
|------|------|
| 示例服务 | demo-go-http（Go HTTP 服务，公开仓库 `github.com/kubesphere-sigs/demo-go-http`） |
| 流水线类型 | 普通流水线（`type: pipeline`），Jenkinsfile 内联在 Pipeline CRD 中 |
| 触发方式 | PipelineRun CRD（Skill 推荐的对象协调方式） |
| 构建方式 | Kubernetes Pod agent，内含 golang / kaniko / kubectl 三个容器 |
| 部署方式 | `kubectl apply` 滚动更新 |
| 验证方式 | `kubectl rollout status` + readinessProbe |
| 回滚方式 | `kubectl rollout undo`（失败自动回滚 + 参数手动回滚） |

### 流水线阶段

```
Checkout and Test → Build and Push Image → Deploy → Verify Deployment
                                                          ↓ 失败
                                                   post.failure 自动回滚
Manual Rollback（参数 MANUAL_ROLLBACK=true 时单独执行）
```

## 二、文件清单

| 文件 | 用途 |
|------|------|
| `pipeline.yaml` | Pipeline CRD，包含完整 Jenkinsfile |
| `pipelinerun.yaml` | 两个 PipelineRun：正常构建 + 手动回滚 |
| `credentials.yaml` | DevOps 凭证模板（registry-credential、git-credential），仅占位符 |
| `rbac.yaml` | ServiceAccount + Role + RoleBinding，最小权限部署凭证 |
| `deployment.yaml` | 应用 Deployment（含探针）+ Service |
| `validate.py` | 本地验证脚本（仅依赖 Python3 + PyYAML） |

## 三、约束导致的方案变化

本次任务附加约束：**不新增非必要依赖、不改变无关文件、本地可重复验证、外部账号只到确认前步骤**。这些约束对方案的影响如下：

| 约束 | 方案变化 |
|------|----------|
| 不新增非必要依赖 | 1. 不引入 ArgoCD/Flux 等 GitOps 工具（Skill 本身也未覆盖），采用 Skill 原生支持的 Pipeline CRD + kubectl apply；2. 镜像构建使用 Kaniko（无需 Docker daemon，以容器镜像方式运行）；3. 部署/验证/回滚全部使用 kubectl，不引入 helm/kustomize 等额外工具；4. 验证脚本仅用 Python3 + PyYAML（本地已有），不要求安装 kubectl |
| 不改变无关文件 | 所有交付物集中在 `kubesphere-cd-demo/` 目录，未修改 Skill 压缩包、解压目录或系统中任何其他文件 |

## 四、凭证边界

### 4.1 凭证清单

| 凭证 ID | 类型 | 用途 | 边界 |
|---------|------|------|------|
| `registry-credential` | basic-auth | Kaniko 推送镜像到镜像仓库 | 仅在 Build and Push Image 阶段通过 `withCredentials` 注入，作用域限于该 stage |
| `git-credential` | basic-auth | 私有 Git 仓库克隆 | 本示例使用公开仓库，**未引用**此凭证；仅提供模板供私有仓库场景使用 |
| `demo-deployer` (ServiceAccount) | K8s SA | kubectl 部署/验证/回滚 | 通过 RoleBinding 绑定到 `demo` 命名空间的 Role，仅能操作 deployments/services/pods，无集群级权限 |

### 4.2 凭证安全原则

1. **不硬编码**：Jenkinsfile 中通过 `withCredentials` 引用凭证 ID，不出现明文密码。
2. **不使用环境变量直传**：遵循 Skill 要求，不在流水线 spec 中使用 `GITHUB_` 等环境变量。
3. **最小权限**：`demo-deployer` Role 不使用通配符动词，仅授予 `get/list/watch/update/patch`（deployments）和 `get/list/watch`（services/pods）以及 `deployments/rollback` 的 `create` 权限。
4. **凭证文件不含真实密钥**：所有敏感值为 `PLACEHOLDER`，真实密钥应通过 KubeSphere UI 或 API 在运行时注入。

### 4.3 私有仓库确认前步骤

Skill 明确要求：创建多分支流水线前**必须询问用户仓库是否私有**。本示例使用公开仓库（`credential_id` 为空），若切换为私有仓库，需按以下顺序操作：

1. 确认仓库为私有
2. 创建 `git-credential`（basic-auth，username=git，password=GitHub PAT）
3. 在流水线 SCM 配置中引用 `credential_id: "git-credential"`

本次未执行上述步骤（无真实仓库和账号），仅提供凭证模板。

## 五、部署验证

### 5.1 流水线内自动验证

流水线 `Verify Deployment` 阶段执行：

```bash
kubectl rollout status deployment/demo-go-http -n demo --timeout=300s
kubectl wait --for=condition=ready pod -l app=demo-go-http -n demo --timeout=120s
```

- `rollout status` 等待滚动更新完成
- `kubectl wait` 确认 Pod Ready（readinessProbe 通过）
- Deployment 配置了 readinessProbe（HTTP `/`，端口 8080）和 livenessProbe，确保只有健康副本接收流量

### 5.2 本地验证（无需集群）

```bash
cd kubesphere-cd-demo
python3 validate.py
```

验证 9 大类 62 项检查，退出码 0 表示全部通过。

### 5.3 真实环境验证命令（需 KubeSphere 集群，本次未执行）

```bash
# 1. 应用 RBAC
kubectl apply -f rbac.yaml

# 2. 创建凭证（替换占位符后）
kubectl apply -f credentials.yaml

# 3. 创建流水线
kubectl apply -f pipeline.yaml

# 4. 检查流水线同步状态（Skill 要求：运行前确认同步到 Jenkins）
kubectl get pipeline demo-go-http-cd -n demo-project -o jsonpath='{.metadata.annotations.pipeline\.devops\.kubesphere\.io/syncstatus}'

# 5. 触发构建
kubectl apply -f pipelinerun.yaml

# 6. 观察运行状态
kubectl get pipelineruns -n demo-project -w

# 7. 查看运行详情
kubectl get pipelinerun demo-go-http-cd-run-001 -n demo-project -o yaml
```

## 六、回滚步骤

### 6.1 自动回滚

流水线 `post.failure` 块在部署或验证失败时自动执行：

```bash
kubectl rollout undo deployment/demo-go-http -n demo
```

回滚到上一个 ReplicaSet，无需人工干预。

### 6.2 手动回滚

通过参数化触发回滚专用 PipelineRun：

```bash
# pipelinerun.yaml 中已定义 demo-go-http-cd-rollback-001
# MANUAL_ROLLBACK=true 时跳过构建和部署，仅执行 rollback 阶段
kubectl apply -f pipelinerun.yaml
```

或直接使用 kubectl：

```bash
kubectl rollout undo deployment/demo-go-http -n demo
kubectl rollout status deployment/demo-go-http -n demo --timeout=300s
```

### 6.3 回滚到指定版本

```bash
# 查看历史版本
kubectl rollout history deployment/demo-go-http -n demo
# 回滚到指定 revision
kubectl rollout undo deployment/demo-go-http -n demo --to-revision=<N>
```

## 九、实际影响执行的 SKILL.md 规则

以下规则直接影响了本次配置设计：

| SKILL.md 规则 | 对本次交付的影响 |
|---------------|-----------------|
| Pipeline 是 K8s 自定义资源，推荐用 PipelineRun CRD 触发（对象协调方式） | 采用 `kubectl apply -f pipelinerun.yaml` 触发，而非直接调 Jenkins API |
| **触发前必须检查参数**（CRITICAL） | PipelineRun 中显式传递 `IMAGE_TAG` 和 `MANUAL_ROLLBACK` 两个参数，布尔值用字符串 |
| 租户创建资源**必须**设置 `kubesphere.io/creator` 注解（CRITICAL） | Pipeline 和所有凭证 Secret 均设置了该注解 |
| 多分支流水线创建前**必须询问仓库是否私有**（CRITICAL） | 本方案选用公开仓库，在文档中说明私有仓库的确认前步骤，未擅自假设 |
| 凭证必须通过 DevOps 凭证管理，**禁止**在 spec 中使用 `GITHUB_` 环境变量 | 使用 `withCredentials` + basic-auth 凭证，验证脚本专门检查此项 |
| `archiveArtifacts` 必须与构建在同一 stage（同一工作空间） | 归档步骤放在 Checkout and Test 阶段内 |
| `container('xxx')` 名称必须与 Pod YAML 中的容器名匹配 | 三个容器名 golang/kaniko/kubectl 均一致，验证脚本自动检查 |
| 不要在 inline Jenkinsfile 中使用 `\$class` 转义（Common Mistakes） | Jenkinsfile 中未使用，验证脚本自动检查 |
| 优先使用 v1alpha3 API，v1alpha2 已废弃 | 所有 CRD 使用 v1alpha3，验证脚本自动检查 |
| 流水线运行前需确认同步状态 `pipeline.devops.kubesphere.io/syncstatus` | 真实环境验证命令中包含同步状态检查 |
| 使用 `kubernetes { yaml ... }` agent 定义自定义 Pod | Jenkinsfile 使用单 Pod 三容器设计，共享工作空间 |
| 布尔参数值必须为字符串 `"true"`/`"false"` | PipelineRun 中 `MANUAL_ROLLBACK` 值为字符串，验证脚本检查类型 |
