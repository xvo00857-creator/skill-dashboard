## 3. 风险分级与证据

### 风险 1（Critical）：疑似令牌滥用导致的未授权数据库导出

- **涉及记录**：第 4、5 条
- **证据**：
  - 09:04:02，IP `203.0.113.8` 以 `service-a` 身份调用 API，触发 `high` 级 `token_scope_mismatch`（令牌权限范围不匹配）。
  - 仅 3 分 28 秒后（09:07:30），**同一 IP** `203.0.113.8` 对 `db` 系统触发 `critical` 级 `unexpected_export`（非预期导出），且 `user` 字段为 `unknown`（无法归属到已知身份）。
- **分级理由**：同一来源 IP 先出现令牌权限异常，短时间内即发生数据库层的非预期批量导出，且操作者身份不明，构成"权限异常 → 数据外传"的可疑攻击链；数据导出直接影响数据保密性，原始日志已标记为 critical。
- **影响面（基于日志可推断）**：数据库内容可能被未授权读取/导出；因日志未含导出数据量、目标表、导出目的地等字段，无法评估泄露范围。

### 风险 2（High）：admin 账户短时间暴力破解/撞库尝试

- **涉及记录**：第 2、3 条
- **证据**：
  - 09:03:45 与 09:03:49，IP `198.51.100.23` 在 **4 秒内**连续两次对 `admin` 账户 `login_failed`。
  - 两次尝试的用户名、IP、系统（web）完全一致，时间间隔极短，符合自动化撞库/暴力破解特征。
- **分级理由**：针对高权限默认账户名 `admin` 的集中失败登录，虽未成功，但属明确的攻击前兆；原始日志标记为 warning，考虑到目标账户敏感性与尝试频率，上调为 High。
- **影响面（基于日志可推断）**：若继续尝试或口令较弱，admin 账户存在被攻陷风险；当前日志中未见该 IP 登录成功记录。

### 风险 3（Medium）：畸形日志记录，疑似日志管道异常或痕迹掩盖

- **涉及记录**：第 6 条
- **证据**：
  - 09:09:00，web 系统出现 `malformed_record` 事件，`severity`、`user`、`source_ip` 三个关键字段**均为空**。
- **分级理由**：该记录发生在风险 1 的数据库导出之后约 1 分 30 秒。字段缺失可能源于：(a) 日志采集/格式化管道故障；(b) 攻击者注入畸形记录干扰审计；(c) 某服务未按规范输出。仅凭本条日志无法定性，但它削弱了日志完整性与可追溯性，需排查。
- **影响面（基于日志可推断）**：若为管道故障，可能存在其他未被正确记录的安全事件；若为人为注入，则存在反取证行为。

## 4. 攻击链关联分析

```
09:03:45  198.51.100.23  web  login_failed(admin)   ─┐ 4 秒内两次，暴力破解前兆
09:03:49  198.51.100.23  web  login_failed(admin)   ─┘
          │
09:04:02  203.0.113.8    api  token_scope_mismatch(service-a) ─┐ 同一 IP
09:07:30  203.0.113.8    db   unexpected_export(unknown)       ─┘ 3分28秒后
          │
09:09:00  (空)           web  malformed_record ── 导出后 1分30秒，字段全空
```

- **链路 A（数据外传嫌疑）**：`203.0.113.8` 的 API 令牌权限异常 → 数据库非预期导出（unknown 身份）。这是本批次中最需要优先处置的链路。
- **链路 B（账户攻击）**：`198.51.100.23` 对 admin 的快速失败登录，与链路 A 来源 IP 不同，暂未发现直接关联，但时间窗口重叠（均在 09:03–09:09），需在真实环境中排查是否为协同攻击。
- **链路 C（审计完整性）**：畸形记录紧随数据导出之后，时间关联性值得注意，但因果性无法仅凭本日志确认。

## 5. 修复建议

> 以下建议均针对日志中实际可见的问题提出，遵循 SKILL.md "always validate with your specific store/data" 的要求，需在真实环境中验证后再落地。

### 5.1 针对风险 1（Critical）

1. **立即吊销并轮换** `service-a` 的 API 令牌/密钥，排查该令牌的权限范围配置（scope），遵循最小权限原则重新下发。
2. **冻结并核查** 09:07:30 前后的数据库导出任务：确认导出执行者身份、导出内容（表/字段/行数）、导出目的地与审批记录。
3. **数据库访问控制**：禁止 API 服务账户直接拥有导出/批量读取权限；导出操作需走审批与堡垒机，且绑定真实用户身份（消除 `unknown`）。
4. **网络侧**：对 `203.0.113.8` 在边界/WAF 进行临时封禁与流量回溯（在授权范围内）。
5. **告警规则**：将"同一 IP 内 token_scope_mismatch 后短时间内出现 db unexpected_export"配置为高危关联告警。

### 5.2 针对风险 2（High）

1. 对 `admin` 账户启用**强口令策略 + MFA**；避免使用 `admin` 等默认账户名，考虑更名或禁用直接登录。
2. 部署登录限速与账户锁定：同一 IP 对同一账户 N 次失败后临时锁定并告警。
3. 在 WAF/认证网关对 `198.51.100.23` 进行限速或封禁，并回溯该 IP 历史登录尝试。
4. 核查 `admin` 账户在该时间点前后是否有成功登录或密码重置记录。

### 5.3 针对风险 3（Medium）

1. 排查日志采集管道（agent/解析器/传输）在 09:09:00 前后是否有故障或重启记录。
2. 在日志入库前增加 schema 校验：`severity/user/source_ip` 等关键字段缺失时拒绝入库并产生告警，而非写入空值。
3. 检查 web 服务是否存在可被注入畸形日志的入口（如用户可控字段未转义写入日志）。
4. 启用日志完整性保护（如集中式日志服务、写入后不可篡改存储），降低反取证风险。
