## 二、Skill 的真实能力边界（以文件为准，不扩张）

该 Skill 只负责一件事：**让生产行为可见、可诊断**，即随功能同步编写埋点。具体覆盖：

1. 先定义 on-call 会问的问题，再决定埋什么；
2. 为每个问题选择正确信号（结构化日志 / 指标 / 追踪）；
3. 结构化日志（稳定事件名、机器可读字段、统一级别、强制关联 ID、禁记密钥与完整 PII）；
4. 指标（请求型服务用 RED：Rate/Errors/Duration 直方图；资源型用 USE；严控标签基数；看分位数不看平均）；
5. 分布式追踪（OpenTelemetry 厂商中立、自动埋点为主、手动 span 只包有意义的内部工作单元、跨异步边界传播 context）；
6. 基于“用户可感知症状”的告警（可操作、带 runbook、阈值有依据、仅 page/ticket 两级）；
7. 验证遥测本身是否正确输出。

SKILL.md 明确声明**不做**（“NOT for”）：

- 正在发生的故障实时诊断 → 属于 `debugging-and-error-recovery`；
- 已测量到的慢的性能剖析与优化 → 属于 `performance-optimization`；
- 上线日监控清单与回滚触发器 → 属于 `shipping-and-launch`；本 Skill 只提供喂给它们的埋点数据。

因此题目中“回滚办法”一项，**运行时/上线回滚触发器不在本 Skill 职责内**；本报告只给代码层回滚手段（见第六节），并标注边界，不越界代写上线门禁。

## 五、按 Skill 七步流程的最小改动方案

### 步骤 1：先写下 on-call 问题（埋点之前必须完成）

> 以下为模板，需替换为目标功能的真实问题；SKILL.md 要求 2–4 个，且每个信号都必须服务于其中一个问题。

```
FEATURE: <待填：功能名，如 checkout payment retry>
QUESTIONS ON-CALL WILL ASK:
1. <该功能首次成功率 vs 重试后成功率？>
2. <永久失败时为什么失败？（下游错误/超时/参数校验）>
3. <下游依赖是否比平时慢？>
→ 每条日志/指标/追踪都必须能回答以上之一，否则不加。
```

### 步骤 2：信号选择

| on-call 问题 | 信号 | 理由（SKILL.md 成本模型） |
|---|---|---|
| 这个具体 case 发生了什么？ | 结构化日志 | 按事件计费，随流量增长，适合单例排查 |
| 整体多快/多频繁？ | 指标（RED 直方图） | 每个序列固定成本，聚合查询便宜 |
| 时间花在跨服务的哪一跳？ | Trace | 按请求计费，通常采样，定位慢在哪 |

口诀：指标告诉你**出事了**，追踪告诉你**在哪**，日志告诉你**为什么**。

### 步骤 3：结构化日志 + 强制关联 ID

要点（与 SKILL.md 一致）：

- 事件而非散文：稳定 `event` 名 + 机器可读字段，禁止字符串拼接；
- 级别统一：`error`（需人介入）/`warn`（已降级但处理了）/`info`（重要业务事件）/`debug`（生产默认关）；
- **requestId 强制**：在系统边界生成或接纳 `x-request-id`，挂到每条日志、span 和出站调用上；
- **硬规则**：禁止记录密钥、令牌、密码、完整 PII；字段走白名单，不打印整个请求体（源自 `security-and-hardening`）。

待适配骨架（TypeScript，风格对齐 SKILL.md 示例；具体 logger 以项目现有为准）：

```typescript
// 1) 请求边界中间件：生成/接纳 requestId，派生 child logger，回写响应头
app.use((req, res, next) => {
  req.id = req.headers['x-request-id'] ?? crypto.randomUUID();
  req.log = logger.child({ requestId: req.id });
  res.setHeader('x-request-id', req.id);
  next();
});

// 2) 业务处：稳定事件名 + 结构化字段，不做字符串拼接
req.log.warn({
  event: 'payment_failed',
  paymentId: id,
  provider: 'stripe',
  errorCode: err.code,   // 错误码可以，错误堆栈/完整错误文本按白名单处理
  attempt: n,
}, 'payment failed');
```

### 步骤 4：RED 指标（每个端点 + 每个外部依赖）

- Rate、Errors、Duration 三件套；Duration 用**直方图**，buckets 覆盖 50ms–5s 量级；
- 标签只允许来自小而固定的集合：`method`、`route`（路由模板，如 `/api/tasks/:id`）、`status_class`（`2xx` 而非 `200`）、`provider`；
- **严禁** `user_id`、`email`、`request_id`、原始 URL、错误消息文本作为标签（基数爆炸，基数查询应进日志/追踪）；
- 看 p50/p95/p99，**永远不看平均**。

```typescript
import { Histogram } from 'prom-client'; // 需依赖审批；未批前用 perf_hooks 先记日志

const httpDuration = new Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP request duration',
  labelNames: ['method', 'route', 'status_class'], // 小而固定的集合
  buckets: [0.05, 0.1, 0.25, 0.5, 1, 2.5, 5],
});
```

外部依赖（如支付网关、数据库）同样埋 Rate/Errors/Duration，加 `provider` 标签；队列/连接池等资源改用 USE（利用率/饱和度/错误）。

### 步骤 5：分布式追踪（OpenTelemetry）

- 厂商中立，自动埋点覆盖 HTTP/gRPC/常见 DB 客户端，代码量趋近于零；
- `tracing.ts` 必须在所有其他模块之前 import；
- 手动 span 只包 `applyDiscounts`、`chargeProvider` 这类有意义的内部工作单元，并附上 on-call 会用来过滤的属性；
- **跨每个异步边界传播 context**（HTTP header、队列消息元数据），否则 trace 在断点处中断；
- 默认头采样低比率；若后端支持尾采样，错误保留 100%。

```typescript
// tracing.ts —— 必须最先 import
import { NodeSDK } from '@opentelemetry/sdk-node';
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node';

const sdk = new NodeSDK({
  serviceName: '<待填：服务名>',
  instrumentations: [getNodeAutoInstrumentations()],
});
sdk.start();
```

### 步骤 6：基于症状的告警

只对“用户可感知的症状”告警，不对 CPU/内存等原因告警：

| 症状（可 page） | 原因（只上 dashboard，不 page） |
|---|---|
| 错误率 > 1% 持续 5min | CPU 85% |
| p99 延迟 > 2s | 某个 pod 重启 |
| 队列年龄 > 10min | 磁盘 70% |

每条新告警必须满足：① 可操作（若“会自愈、忽略即可”就删除）；② 链接 runbook（含义/第一条查询/升级路径，三行也行）；③ 阈值与时长有 SLO 或历史数据依据，不拍脑袋；④ 只用 **page** 与 **ticket** 两级。

### 步骤 7：验证遥测本身（埋点也是代码，会出错）

- 在 staging 造一个错误 → 用 `requestId` 在日志里定位，确认字段是结构化对象而非 `[object Object]`；
- 打测试流量 → 确认指标序列以预期标签出现且数值合理；
- 在追踪 UI 里跟一条请求跨服务 → 无断 span；
- 每条新告警试触发一次（临时调低阈值）→ 确认送达正确渠道且 runbook 链接有效。

## 六、回滚办法（代码层；运行时回滚触发属 shipping-and-launch）

1. **PR 级回滚**：所有埋点放在独立 commit/PR，回滚即 `git revert` 该 PR，不触碰业务代码。
2. **开关级回滚（不发版）**：用环境变量控制——`LOG_LEVEL`（生产可提到 `error` 降噪）、`METRICS_ENABLED=false`、`TRACING_ENABLED=false`；OTel SDK 启动前读取开关，关闭时不初始化、不产生开销。
3. **告警灰度回滚**：新告警先以 `ticket` 级上线、阈值临时调高，确认无噪音后再升 `page`；异常时直接在告警平台禁用该规则，无需回滚代码。
4. 依赖未审批的部分（`prom-client`/OTel 包）不落地，因此不存在“引入后又要卸载”的回滚负担。
