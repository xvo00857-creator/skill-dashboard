## 2. 数据质量与不安全输入发现（edge cases）

### E-1【中危】CSV 公式注入（Formula Injection）
- 位置：`edge_cases.csv` record_id=5，`value` 字段以 `=` 开头，内容为 `=HYPERLINK("https://example.invalid","do not execute")`。
- 风险：若该文件被 Excel/LibreOffice/WPS 等电子表格软件直接打开，以 `=`/`+`/`-`/`@` 开头的单元格可能被当作公式求值，`=HYPERLINK(...)` 可诱导点击外联，变种可触发数据外带（如 `=WEBSERVICE(...)`）或命令执行类 DDE。这是典型的不安全输入。
- 处置（已采取/未采取）：
  - 已使用 Python `csv` 模块以纯文本方式解析，**未在任何电子表格软件中打开**，**未执行该公式**，**未访问** `example.invalid`（该域名为 RFC 2606 保留域名，本身也不会解析）。
  - 该载荷按 notes 自述为"公式注入测试文本"，按测试样本处理。
- 修复建议：
  - 导出/生成 CSV 时，对以 `=`、`+`、`-`、`@`、Tab、回车开头的单元格做无害化处理（前置单引号 `'` 或删除控制字符）。
  - 接收侧对外部来源 CSV 进行公式字符校验；电子表格打开时禁用自动公式/DDE。
  - 内容安全策略中将此类字段视为不可信文本，不得直接渲染为可执行公式。

### E-2【低危】非标准 CSV 转义导致字段错位
- 位置：`edge_cases.csv` record_id=5 原始字节为：
  `5,ok,"=HYPERLINK(\"https://example.invalid\",\"do not execute\")",公式注入测试文本`
- 问题：文件使用反斜杠 `\"` 转义内嵌引号，而非 RFC 4180 规定的双写双引号 `""`。标准 CSV 解析器会在第一个 `\"` 处提前闭合引号字段，导致 `value` 被截断、`notes` 错位、`公式注入测试文本` 落入额外的无名列（Python `csv` 解析结果中出现 `None: ['公式注入测试文本']`）。
- 影响：自动化解析会产生字段错位与数据丢失；若下游依赖列位置，可能误判或漏判注入载荷。
- 修复建议：统一采用 RFC 4180 双写双引号转义；在解析管线中增加"列数与表头不一致"告警；对该条记录以原始字节复核，确认真实 payload 为完整的 `=HYPERLINK(...)` 公式。

### E-3【低危】重复记录
- 位置：`edge_cases.csv` record_id=2 出现两次，两行内容完全相同（status=ok, value=120, notes=重复记录）。
- 影响：统计/聚合时会重复计数，可能扭曲指标（如总量、成功率）。
- 修复建议：以 `record_id` 为主键去重；写入侧增加唯一性约束；去重前保留原始行号以便追溯。

### E-4【低危】必填字段缺失
- 位置：`edge_cases.csv` record_id=3，`status` 与 `value` 均为空，`notes` 为 `-`。
- 影响：记录不完整，无法参与状态/数值统计；可能表示上游采集失败或传输截断。
- 修复建议：定义必填字段校验，空值记录进入隔离区而非直接入库；补充上游采集日志以定位丢失环节。

### E-5【低危】异常负值
- 位置：`edge_cases.csv` record_id=4，`status=error`，`value=-999`。
- 分析：`-999` 常作为错误/缺失哨兵值；若 `value` 语义为计数、金额、时延等非负度量，则该值非法。注意：以 `-` 开头在电子表格中也可能被解释为公式，但此处 `-999` 为纯数字，主要风险是数据语义异常而非公式注入。
- 修复建议：明确 `-999` 是哨兵值还是真实异常；若是哨兵，应转为 `NULL` 并以 `status=error` 表示；若业务上不允许负值，应在写入侧拒绝并告警。

### 3.2 发现项

#### I-1【严重】疑似入侵链：令牌权限越界 → 数据库异常导出
- 证据：
  - 09:04:02 `api` 系统记录 `token_scope_mismatch`（high），主体 `service-a`，源 IP `203.0.113.8`——服务账号所持令牌的权限范围与请求不匹配，可能是越权尝试或令牌被滥用。
  - 09:07:30 `db` 系统记录 `unexpected_export`（critical），用户为 `unknown`，源 IP **同为** `203.0.113.8`——同一外部 IP 在 3 分 28 秒后触发了数据库异常导出。
- 推断：同一源 IP 先出现 API 令牌范围异常，随后发生未识别用户的 DB 导出，构成"令牌滥用/越权 → 数据外泄"的可疑攻击链。`unknown` 用户表明导出操作未关联到有效身份，可能是凭据失效后冒用或绕过认证。
- 影响：若属实，可能导致数据库内容未授权导出（数据泄露）。
- 修复建议：
  1. 立即吊销/轮换 `service-a` 的令牌及相关密钥，核查令牌签发记录与实际权限范围。
  2. 核查 09:04–09:08 期间 `203.0.113.8` 对 api 与 db 的全部访问日志，确认导出的表、行数、目标位置。
  3. 对 db 导出操作强制身份认证与二次授权，禁止 `unknown`/匿名导出；导出行为纳入实时告警与审批。
  4. 按最小权限原则收敛 service-a 的 token scope；启用 scope 变更与异常使用的关联告警。
  5. 评估数据泄露影响，按内部应急响应流程上报。

#### I-2【中危】admin 账户短时间连续登录失败（疑似暴力破解）
- 证据：09:03:45 与 09:03:49（间隔 4 秒）同一 IP `198.51.100.23` 对 `admin` 账户连续两次 `login_failed`。
- 分析：样本仅 2 次，未达典型暴力破解量级，但目标为高权限 `admin` 账户且来源单一，属于可疑的口令猜测前兆。该 IP 与 I-1 的 `203.0.113.8` 不同，暂不并案。
- 修复建议：
  - 对 admin 登录启用速率限制、账户锁定/退避与多因素认证。
  - 核查该 IP 前后更长时间窗口的登录记录，确认是否存在更多失败尝试或成功登录。
  - admin 账户禁止来自公网直接登录，改为堡垒机/零信任接入。

#### I-3【中危】日志记录畸形 / 日志完整性缺陷
- 证据：第 6 行 `2026-08-12T09:09:00Z,web,,malformed_record,,`——`severity`、`user`、`source_ip` 三个关键字段为空。
- 分析：畸形记录本身可能是：(a) 日志采集/序列化管线故障；(b) 攻击者尝试污染或绕过日志；(c) 某事件未正确填充字段。无论哪种，都会削弱审计可追溯性，且在 I-1 可疑外泄链之后 1.5 分钟出现，时序上值得警惕。
- 修复建议：
  - 日志 schema 强制必填字段校验，缺字段的记录进入隔离并告警，而非静默落盘。
  - 核查 09:09 前后 web 系统与日志采集组件状态，排除管线故障。
  - 关键日志启用防篡改（追加写入、集中存储、完整性校验）。

#### I-4【信息】正常登录基线
- 证据：09:00:12 `alice` 从 `192.0.2.10` 成功登录 web。
- 说明：单条成功登录无异常，作为正常基线记录；若需进一步判断，应结合 alice 的历史登录地/时段基线。
