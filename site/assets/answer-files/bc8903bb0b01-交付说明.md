## 二、架构选型（依据 SKILL.md 决策矩阵）

脚本支持两种架构，按 SKILL.md 第 89–107 行的决策矩阵选择：

- **集中式存储（Centralized Storage）**：日志路由到中心项目的一个区域桶，适合项目数多（可扩展到数千）、需要统一 SQL 分析、按视图做访问控制的场景；需注意排除审计日志以避免重复存储费用。
- **读时聚合（Read-Time Aggregation）**：日志留在源项目，通过 Log Scope 跨项目查询，适合项目数 < 375、不希望数据复制、不想干扰基于桶的日志指标的场景；代价是查询者需对每个源项目有 IAM 权限。

## 三、受约束流程设计要点

脚本 `cross-project-logging-setup.sh` 实现了以下保护机制：

### 1. 预检（Preflight，全部 Tier R 只读）
- 检查 gcloud 是否安装、是否已认证、必填参数是否齐全、区域是否合理；
- 非 dry-run 时做一次轻量 API 连通性探测；
- **不运行** `projects list` / `organizations list` 等网络发现命令（SKILL.md 第 24–28 行明确禁止，否则会挂起超时）；
- dry-run 模式下 gcloud/认证缺失降级为警告，仍可输出完整命令清单供审阅。

### 2. 幂等（Idempotency）
- 创建桶 / sink / view / scope 前，先用 `describe`（Tier R）检查是否已存在；
- 已存在则跳过并记录日志，可安全重复执行。

### 3. 重试（Retry）
- 对 `writerIdentity` 查询等幂等只读操作使用指数退避重试（默认 3 次，间隔 2s→4s→8s）；
- 变更操作不自动重试，避免重复创建。

### 4. 人工确认点（严格对应 SKILL.md 安全分级）

| 层级 | 操作类型 | 脚本行为 |
| :--- | :--- | :--- |
| **Tier R** 只读 | `logging read`、`buckets list`、`sinks describe` | 直接执行 |
| **Tier M** 非计费变更 | `buckets create`、`sinks create`、`views create`、`scopes create` | 幂等执行，无需确认 |
| **Tier B** 计费/安全敏感 | `add-iam-policy-binding`、`metrics create`、`links create` | **逐字打印命令并等待输入 `yes`**，不在同一轮执行 |
| **Tier D** 不可逆数据丢失 | `buckets delete`、`sinks update --add-exclusion` | **必须逐字输入 `Yes, discard logs`**，否则中止 |

### 5. 审计日志排除（SKILL.md 第 192–197 行）
源项目 sink 默认排除 6 类审计日志（activity / system_event / access_transparency 的 cloud/external audit），避免重复存储产生费用，这是 SKILL.md 推荐做法。

## 四、可核验演示结果（真实输出，未触碰外部资源）

### 演示 1：集中式存储 dry-run
命令：
```bash
bash cross-project-logging-setup.sh --mode central \
  --central-project my-central-proj \
  --source-projects src-proj-a,src-proj-b \
  --bucket-id central-logs-bucket --region us-central1 \
  --retention-days 30 --dry-run
```
关键输出（节选）：
```
[WARN]  DRY-RUN 模式：仅打印命令，不执行任何变更
[WARN]  未找到 gcloud CLI；dry-run 模式下继续，仅输出命令清单。
[INFO]  预检通过
[DRY-RUN] gcloud logging buckets create central-logs-bucket --project=my-central-proj \
          --location=us-central1 --retention-days=30 --enable-analytics
[DRY-RUN] gcloud logging sinks create route-to-central \
          logging.googleapis.com/projects/my-central-proj/locations/us-central1/buckets/central-logs-bucket \
          --project=my-central-proj
[DRY-RUN] gcloud logging sinks create route-to-central \
          logging.googleapis.com/projects/my-central-proj --project=src-proj-a \
          --exclusion=filter=LOG_ID("cloudaudit.googleapis.com/activity") ...（共 6 条排除）
[INFO]  [步骤 4/5] IAM 授权（Tier B，安全敏感）
[INFO]    （dry-run）待执行命令：
[INFO]      gcloud logging sinks describe route-to-central --project=<source> --format=value(writerIdentity)
[INFO]      gcloud projects add-iam-policy-binding my-central-proj --member=<writerIdentity> \
                  --role=roles/logging.logWriter
[DRY-RUN] gcloud logging views create view-src-proj-a ... --log-filter=project_id="src-proj-a"
```
可核验点：Tier B 的 IAM 授权命令**未被执行**，仅打印待办；所有 sink 都带 6 条审计日志排除；桶使用区域 `us-central1` 而非 `global`。

### 演示 2：读时聚合 dry-run
命令：
```bash
bash cross-project-logging-setup.sh --mode scope \
  --scoping-project my-scope-proj \
  --source-projects src-proj-a,src-proj-b --dry-run
```
关键输出：
```
[DRY-RUN] gcloud logging views create app-logs-view --bucket=_Default --location=global --project=src-proj-a
[DRY-RUN] gcloud logging views create app-logs-view --bucket=_Default --location=global --project=src-proj-b
[DRY-RUN] gcloud logging scopes create central-query-scope --project=my-scope-proj \
          --resource-names=projects/src-proj-a/.../app-logs-view,projects/src-proj-b/.../app-logs-view
[INFO]  [步骤 3/3] IAM 授权（Tier B，安全敏感）
[INFO]    读时聚合要求查询者在每个源项目具备 roles/logging.viewAccessor 或 roles/logging.viewer
```

### 演示 3：安全门单元验证
- **Tier B 拒绝**：输入 `no` → 脚本输出"用户未确认 Tier B 操作，已中止"并以退出码 1 终止；
- **Tier B 通过**：输入 `yes` → 继续执行；
- **Tier D 拒绝**：输入 `yes`（非逐字口令）→ 中止；输入 `Yes, discard logs` → 通过；
- **重试**：模拟前两次失败第三次成功 → 指数退避后成功；全部失败 → 重试耗尽返回非零；
- **参数校验**：缺少 `--central-project` → 预检失败退出；非法 `--mode` → 预检失败退出；
- **语法检查**：`bash -n` 通过。

## 五、在真实环境执行的前置条件（需人工提供）

1. 安装 Google Cloud SDK 并完成 `gcloud auth login` / `gcloud auth application-default login`；
2. 提供真实的 `--central-project`、`--source-projects`（或 `--source-organization`）ID；
3. 确认执行账号在中心项目具备 `roles/logging.admin`（创建桶/sink/view）和 `resourcemanager.projects.setIamPolicy`（授予 sink writerIdentity）；
4. 先跑一次 `--dry-run` 审阅命令，再去掉该标志正式执行；Tier B 步骤会逐字打印命令并等待输入 `yes`。

## 六、故障排查指引（依据 SKILL.md 第 384–435 行）

若日志未出现在中心桶，按顺序排查：
1. **Sink 过滤器**：确认过滤器匹配预期日志；**sink 过滤器中必须用 `LOG_ID("abc")` 而非 `logName:abc`**（SKILL.md 第 393–395 行明确指出后者可能匹配失败）；
2. **排除过滤器**：确认没有误排目标日志；
3. **Writer Identity 权限（最常见原因）**：`gcloud logging sinks describe <sink> --project=<source> --format="value(writerIdentity)"` 取出服务账号，在中心项目授予对应角色：
   - Cloud Logging 桶 → `roles/logging.bucketWriter`（或中心项目级 `roles/logging.logWriter`）
   - GCS 桶 → `roles/storage.objectCreator`
   - Pub/Sub → `roles/pubsub.publisher`
   - BigQuery → `roles/bigquery.dataEditor`
4. **验证查询**：区域桶查询时**必须带 `--view=_AllLogs`**（SKILL.md 第 305–314 行），默认 `_Default` 视图只含匹配默认过滤器的日志。

4. **第 305–314 行区域桶查询必须带 `--view=_AllLogs`**：验证命令中已体现。
5. **第 393–395 行 sink 过滤器必须用 `LOG_ID()`**：故障排查章节已纳入。
