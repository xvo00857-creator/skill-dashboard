## 2. 风险分级

### 2.1 严重（Critical）：疑似服务令牌失陷导致数据库异常导出

- 关联事件：第 4 条（api / high / token_scope_mismatch / service-a / 203.0.113.8）→ 第 5 条（db / critical / unexpected_export / unknown / 203.0.113.8）
- 定级依据：
  - 同一源 IP `203.0.113.8` 在 208 秒（约 3 分 28 秒）内先后触发 API 令牌作用域不匹配与数据库异常导出；
  - 数据库事件的用户字段为 `unknown`，说明认证主体缺失或被刻意隐匿，与"使用越权/被盗令牌直接访问数据层"的模式吻合；
  - `unexpected_export` 意味着数据可能已被批量读出，具备数据泄露影响面。
- 证据链：
  1. 09:04:02 service-a 令牌被用于请求其授权范围之外的 API 资源 → 令牌与实际调用方/用途不一致；
  2. 09:07:30 同一 IP 对 db 发起未预期导出，执行主体无法识别 → 数据层访问控制或审计归因失效；
  3. 两条事件时间紧邻、来源一致，构成"令牌异常 → 数据外传"的可疑时序链。
- 置信度：中高。IP 与时序强相关，但仅凭日志无法排除 NAT/代理复用、定时任务误配等良性解释；未取得数据库审计明细、导出内容与目标地址前，不判定为"已确认的数据泄露"。

### 2.2 高危（High）：admin 账户短间隔暴力破解尝试

## 4. 修复建议

### 4.1 针对 2.1 令牌失陷 / 异常导出（立即处置）
1. 立即吊销并轮换 `service-a` 的所有有效令牌/密钥，审查其签发来源与授权范围。
2. 在 API 网关强制校验令牌受众（aud）与作用域（scope），拒绝 scope 不匹配请求并告警；对服务间调用启用 mTLS 或短期工作负载身份（如 SPIFFE/SPIRE 类机制）。
3. 数据库侧收紧导出权限：导出操作需二次授权与审批，限制可导出表与行数，记录导出目标、数据量与执行人真实身份，禁止匿名/`unknown` 主体执行导出。
4. 对 09:04–09:08 期间 service-a 与 db 的访问做回溯：确认导出是否成功、涉及哪些表、数据流向何处，必要时启动数据泄露响应流程。
5. 网络层对 203.0.113.8（在真实环境中替换为实际对端地址）实施临时阻断与会话终止。

### 4.2 针对 2.2 admin 暴力破解
1. 对管理后台启用登录失败锁定/退避与多因素认证（MFA），`admin` 等特权账户必须 MFA。
2. 增加基于 IP 与账户的速率限制与验证码；对 4 秒内两次失败这类自动化模式直接临时封禁。
3. 核查 `admin` 账户是否必要、是否应改名或禁用口令登录、是否遵循最小权限。

### 4.3 针对 2.3 畸形日志
1. 在日志采集端增加字段校验：`severity`、`user`、`source_ip` 缺失时拒绝写入或标记为 `schema_violation` 并独立告警。
2. 对日志写入链路做完整性保护（如追加写入、签名/哈希链、集中式转发），防止注入与篡改。
3. 排查 09:09:00 前后采集器/解析器是否有异常，确认是攻击还是故障。

### 4.4 通用改进
- 统一日志字段规范，补充 `request_id`、`session_id`、`user_agent`、`result_code`、`target_resource` 等字段，提升跨系统关联能力。
- 建立跨 web/api/db 的关联检测规则：同一源 IP 在 N 分钟内跨系统触发高危事件即生成聚合告警。

## 6. 约束、冲突与取舍

### 冲突一：Skill 适用边界与任务类型不匹配（门控规则）

- **事实**：所读 `SKILL.md` 第 8 行明确规定："Use this skill only as a downstream specialization after `$ctf-sandbox-orchestrator` is already active... If that has not happened yet, return to `$ctf-sandbox-orchestrator` first."；`agents/openai.yaml` 亦设置 `allow_implicit_invocation: false`。
- **冲突**：当前环境中 `$ctf-sandbox-orchestrator` 并未激活，且该 Skill 的领域是 CTF 沙箱中的浏览器持久化状态（cookies、localStorage、service worker 等），而本任务是 CSV 服务端安全日志的风险审计，二者领域不重叠。
- **取舍**：严格遵循 SKILL.md 的门控规则，不将该 Skill 作为本任务的执行依据直接套用；仅迁移其可复用的证据方法论（见下），并在本报告中显式声明边界。未伪造任何浏览器状态、沙箱节点或 CTF 执行结果。
- **影响结果的具体规则**：SKILL.md 第 8 行的门控规则直接决定了本报告不把该 Skill 当作日志审计规程使用，而是如实标注其不可直接适用，避免了"用错工具还假装合规"的风险。

### 冲突二：证据相关性 vs. 归因严谨性（不得过度断言）

- **事实**：203.0.113.8 同时出现在 `token_scope_mismatch` 与 `unexpected_export`，时序紧邻，高度可疑；但日志中缺少会话 ID、请求结果码、导出目标与数据量，且该 IP 属文档保留段（模拟数据）。
- **冲突**：若直接判定为"令牌失陷导致数据泄露"，可能高估；若仅按单条事件分别定级，则会低估链式攻击风险。
- **取舍**：参照 `references/browser-persistence.md` "Common Pitfalls" 中"Treating cached UI data as backend authorization without proving a server-side effect"的精神（不得把未经证实的关联当作已证实的后端效果），将 2.1 定为"疑似/中高置信度"而非"已确认泄露"，并在证据块 A 中列出待补证据。同时按链式风险给出 P0 级处置与复测项，兼顾响应时效与归因严谨。
- **依赖**：最终确认需 API 网关鉴权日志、数据库审计明细、网络流量记录，这些不在本次输入范围内。

### 约束三：授权范围与数据完整性限制

- 本次仅授权只读分析 `incident_log.csv`，未对任何主机、账号或令牌执行探测、登录、吊销或阻断；第 4 节中的处置建议需由有权人员在真实环境执行。
- 日志仅 6 条且字段有限（无 request_id、session_id、result_code、user_agent、目标资源），跨系统关联能力受限；第 6 条畸形记录无法定性，结论以"待排查"呈现，不臆造原因。

### 风险提示

- 本报告基于模拟日志，IP 均为 RFC 5737 保留地址；若迁移到真实环境，需以真实情报与资产信息重新校准。
