# github-triage 可执行交付

把团队里重复的 **GitHub issue/PR 分诊**工作自动化：抓取全部 open 条目 → 按规则分类 → 逐条分析并产出带证据链接的报告 → 汇总。

本交付是对随附 Skill `github-triage/SKILL.md` 的可执行落地，**严格只读**，不评论、不合并不关闭、不打标签。

## 约束导致的方案变化

| 新约束 | 影响 | 本交付的处理 |
|--------|------|--------------|
| 不新增非必要依赖 | Skill 自带的 `scripts/gh_fetch.py` 依赖 Python ≥3.11 + typer + rich（经 `uv run`），本机是 Python 3.9 且未装这些包 | 新写 `triage.py`，**仅用 Python 标准库**；分页逻辑复刻 `gh_fetch.py`，不引入 typer/rich，也不修改原 `gh_fetch.py` |
| 不修改无关文件 | 不能改 Skill 原文件，也不能动用户仓库 | 只在本交付目录内新增文件；报告写到 `/tmp/<时间戳>/`；Skill 原文件 `SKILL.md`、`scripts/gh_fetch.py` 保持只读不动 |
| 本地/沙盒可重复验证 | 真实分诊需要 `gh` 登录态与网络 | 提供 `--mock` 模式（用 `fixtures/` 数据，零账号零网络）和 `--check` 确认前预检；`verify.sh` 一键复现 |
| 外部账号只做到模拟或确认前步骤 | 本机未安装/未登录 `gh` | 不尝试任何真实写操作；`--check` 只跑 `gh auth status`/`gh repo view` 等只读探测，缺 gh 时明确报缺失项 |
| Skill 依赖 `task_create`/`task` 子任务工具 | 当前执行环境没有这两个工具 | 把“1 条目 = 1 后台子任务”实现为“1 条目 = 1 次独立函数调用 + 1 个独立报告文件”，保留逐条隔离与报告格式；`analyze_one_item` 可直接作为子任务入口迁移 |

## 用法

### 1. 无需账号的完整演练（mock）

```bash
python3 triage.py --mock
# 指定输出目录以便核对：
python3 triage.py --mock --report-dir /tmp/triage-demo
```

输出：在报告目录生成 `issue-<n>.md`、`pr-<n>.md` 与 `SUMMARY.md`。

### 2. 确认真实环境是否就绪（只读预检，不执行分诊）

```bash
python3 triage.py --check                 # 检查当前目录
python3 triage.py --check --repo owner/repo --repo-dir /path/to/checkout
```

预检只运行 `gh auth status`、`gh repo view`、`git rev-parse HEAD` 等只读命令；缺 gh、未登录、不是 git 仓库都会逐项列出，退出码 `2` 表示未就绪。

### 3. 真实分诊（需 gh 已登录 + 本地检出）

```bash
python3 triage.py --repo owner/repo --repo-dir /path/to/checkout
# 或在仓库目录内直接：
cd /path/to/checkout && python3 /path/to/triage.py
```

- 自动分页抓取全部 open issue/PR（每页 500，用 `created:<` 游标翻页，按 number 去重）。
- 每条目单独抓取详情、单独分析、单独写报告；单条失败只写 `*.error.txt`，不中断整体。
- 证据来自本地检出的 `git grep`/`git log`，permalink 使用 `git rev-parse HEAD` 的完整 SHA。

## 输入输出示例

输入（`fixtures/issues.json` 片段）：

```json
{
  "number": 102,
  "title": "Bug: panic on startup when config file is missing",
  "labels": [{"name": "bug"}],
  "body": "...panic: runtime error... goroutine 1 [running]: ... src/config/loader.go:27"
}
```

输出（`/tmp/.../issue-102.md` 片段）：

```markdown
# Issue #102: Bug: panic on startup when config file is missing
**Type:** Bug Report | **Author:** carol | **Created:** 2026-08-03T09:12:00Z
## Verdict: CONFIRMED_BUG
### Evidence
- `src/config/loader.go:27` 命中关键词 `config`：[src/config/loader.go#L27](https://github.com/octocat/Hello-World/blob/7fd1a60.../src/config/loader.go#L27)
## Severity: HIGH
```

`SUMMARY.md` 汇总各类计数与需关注条目。

## 异常处理

- **gh 未安装/未登录**：真实模式直接报错退出；`--check` 列出具体缺失项。
- **网络/API 失败**：`gh` 非零退出时抛 `TriageError`，带 stderr 摘要。
- **JSON 解析失败**：gh 返回非 JSON 或固件损坏时明确报错。
- **单条分析失败**：写 `<kind>-<n>.error.txt`，其余条目继续。
- **非 git 仓库**：代码搜索与 SHA 获取失败时，相关结论标 `[UNVERIFIED]`，不伪造证据。
- **命令超时**：外部命令 60s 超时，报错退出。
- **零写守卫**：任何 `gh issue comment/close/edit`、`gh pr merge/review/edit`、`gh api -X POST/PUT/PATCH/DELETE`、`git checkout/fetch/pull/switch/push/...` 在执行前被 `ForbiddenCommandError` 拦截。

## 可重复验证

```bash
bash verify.sh
```

内容包括：单元测试、mock 全流程产物与关键断言、`--check` 预检、零写守卫正反例、缺 gh 时真实模式的错误处理。不需要 GitHub 账号，不安装任何依赖。

## 与 Skill 的对应关系

| SKILL.md 规则 | 落地位置 |
|---------------|----------|
| 零写策略（Zero-Action Policy） | `_guard_gh` / `_guard_git` 白名单；`test_triage.py::TestZeroActionGuard` |
| 每条事实需 commit-SHA permalink | `build_blob_link` / `build_commit_link`；无证据时输出 `[UNVERIFIED]` |
| Phase 0 准备（REPO/REPORT_DIR/COMMIT_SHA） | `run_real` / `make_report_dir` / `get_current_sha` |
| Phase 1 全量分页抓取 | `fetch_all_open`（复刻 `gh_fetch.py` 分页） |
| Phase 2 分类表 | `classify_issue` / `classify_pr` |
| Phase 3 一条目一报告 | `analyze_issue` / `analyze_pr`，每条目写独立文件 |
| 各类型报告模板 | `analyze_issue`/`analyze_pr` 内的 Markdown 结构 |
| Phase 5 汇总 | `write_summary` → `SUMMARY.md` |
| 报告目录 `/tmp/{YYYYMMDD-HHmmss}/` | `make_report_dir` 默认值 |
| 不采样、处理全部 backlog | `fetch_all_open` 翻页至取完；`--max-items` 仅测试用 |

## 未完成范围（诚实说明）

- 本环境无 `gh`、无 GitHub 登录态，**未对真实仓库执行分诊**；真实模式仅通过代码审查与 mock/单元测试验证逻辑。
- 逐条深度语义分析（Skill 中由 LLM 子任务完成）在脚本中以确定性关键词搜索 + 规则启发式替代，不等同于 LLM 判断；`Confidence`/`Severity`/`Risk` 为启发式结果，需人工复核。
- Skill 自带 `gh_fetch.py` 因 Python 版本与依赖原因未在本机运行，但其分页逻辑已被 `triage.py` 用标准库重新实现。
