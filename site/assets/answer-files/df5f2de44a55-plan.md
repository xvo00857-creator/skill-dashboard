# 受约束的并行特性开发流程方案

> 依据 Skill：`parallel-feature-development` v1.0.2
> 适用场景：将一个较大特性拆分为多个并行工作流，由多个实现者（或多个 agent）同时开发。
> 本方案严格在该 Skill 的能力边界内：它是**协调方法论**，不自动建分支、不自动改代码、不自动合并。

---

## 一、用户旅程

以"用户认证模块"为例，端到端旅程如下：

| 阶段 | 角色 | 动作 | 产出 |
|------|------|------|------|
| 1. 需求提出 | 产品/用户 | 提出"需要登录+注册+鉴权"特性 | 特性需求单 |
| 2. 需求澄清 | lead | 澄清范围、技术栈、并行人数、集成方式 | 澄清记录（见第二节） |
| 3. 预检 | lead | 检查仓库状态、运行环境、是否已有同名分支/文件 | 预检报告（见第四节） |
| 4. 功能拆解 | lead | 按 Hybrid 模式拆为 3 个工作流 + 1 个契约层 | 归属矩阵 `ownership-matrix.json` |
| 5. 契约先行 | lead | 定义接口契约，实现者只导入不修改 | `contracts/auth-contract.ts` |
| 6. 人工确认 CP-1 | lead + 实现者 | 确认归属与契约，无人异议后才开工 | 确认记录 |
| 7. 并行开发 | 实现者 | 各自在子分支开发，跨工作流只用契约/stub | 各子分支提交 |
| 8. 集成 | lead | 按依赖图顺序合并，执行集成验证清单 | 合并后的 `feature/auth` |
| 9. 人工确认 CP-2 | lead | 验证清单全部通过后才允许交付/上线 | 验证记录 |
| 10. 交付 | lead | 交付特性，归档归属矩阵与契约 | 可交付特性 |

## 三、功能拆解与文件归属（Hybrid 模式）

依据 SKILL.md「Integration Patterns → Hybrid」与 file-ownership.md「Ownership Decision Process」：

- **implementer-1**：登录垂直切片（UI + hook + API + 测试）
- **implementer-2**：注册垂直切片（UI + hook + API + 测试）
- **implementer-3**：共享鉴权基础设施（中间件、JWT 工具，水平层）
- **lead**：接口契约文件 + barrel/index 文件（唯一所有者）

详细归属见 `ownership-matrix.json`，契约见 `contracts/auth-contract.ts`，分支计划见 `branch-plan.md`。

### Cardinal Rule（核心铁律）

**一个文件只能有一个 owner。** 本规则由 `validate-ownership.js` 的 R1 检查项自动校验。

## 四、预检（Pre-flight Checks）

在任何写操作之前，lead 必须完成以下预检；任一项失败则停止，不进入开发：

| 编号 | 预检项 | 方法 | 失败处理 |
|------|--------|------|----------|
| P1 | 仓库存在且干净 | `git status` 确认工作区无未提交改动 | 先提交/stash，否则不开始 |
| P2 | 目标分支不存在 | `git branch -a` 检查 `feature/auth*` 是否已存在 | 已存在则走幂等复用（见第五节），不重复创建 |
| P3 | 归属文件无冲突 | 运行 `node validate-ownership.js` | 修复矩阵后重跑，直到通过 |
| P4 | 契约文件路径无主冲突 | 同上 R2 检查 | 契约必须归 lead |
| P5 | 运行时/工具链可用 | `node --version`、`tsc --noEmit` 等 | 缺失则先安装，不进入开发 |
| P6 | 实现者已确认归属 | CP-1 人工确认 | 有异议则重新拆解（Skill：拆分错误时停止新工作、重新分配） |

> 本次演示实际可执行的预检：P3、P4、P5（见第六节运行结果）。P1、P2、P6 需要真实仓库与人工，标注为未执行。

## 五、幂等、重试与人工确认点

### 5.1 幂等设计

- **归属矩阵校验**：`validate-ownership.js` 只读不写，重复运行结果一致，可安全重跑。
- **分支创建**：预检 P2 先检查分支是否存在；存在则复用，不重复创建（不 `git branch -D` 后重建）。
- **契约文件**：契约先行合并后，后续实现者只导入；重复执行"定义契约"步骤不会覆盖已有契约（需 lead 确认后才能改）。
- **本演示所有产物**：均写入本地 `pfd-demo/` 目录，重复生成会覆盖同名文件——这是本地可逆操作，已在交付时明示；不涉及任何外部资源。

### 5.2 重试策略

| 场景 | 重试策略 | 上限 |
|------|----------|------|
| 校验脚本失败（R1–R5 违规） | 修正矩阵后重跑 | 不限，直到通过；连续 3 次未通过则升级到 lead 重新拆解 |
| 合并冲突 | 按 merge-strategies.md：契约优先 → lead 裁决 → 测试决定 → lead 手动合并 | 手动合并 1 次，仍失败则暂停并广播 |
| 契约漂移导致测试失败 | lead 广播契约变更 → 实现者 rebase → 重跑测试 | 2 轮，仍失败则停止新工作重新对齐 |
| 网络/权限类外部错误 | 不静默重试，直接报错并等待人工指示 | 0（避免在无权限时反复撞墙） |

### 5.3 人工确认点（Checkpoints）

- **CP-1（开发前）**：lead 向所有实现者广播归属矩阵与契约，全员确认无异议后才创建子分支开工。依据：Skill 要求"契约修改前广播"，开工前确认同理。
- **CP-2（集成后交付前）**：lead 跑完集成验证清单全部 6 项，确认通过后才允许合并到主干/上线。依据：merge-strategies.md Integration Verification Checklist。
- **CP-3（拆分错误时）**：若中途发现拆解不合理，停止新工作，lead 重新分配并广播；已写的部分代码允许沉没成本，不硬凑。依据：SKILL.md Troubleshooting 最后一条。

## 七、与题目假设的冲突说明

题目将本 Skill 归入"自动化与工具"，暗示其可能自动执行并行开发流程。但 SKILL.md 实际内容是**协调模式与规则文档**（功能拆解策略、文件归属、接口契约、集成模式、分支管理、故障排查），不含任何可执行脚本或外部系统操作。因此：

- 本方案不把 Skill 的职责扩张为"自动建分支/自动合并/自动改代码"；
- 所有外部写操作都放在人工确认点之后，由人或有权限的工具执行；
- 自动化部分仅为本地只读校验脚本，用于在开工前静态验证 Skill 的规则是否被遵守。
