## 术语统一说明

> [!NOTE]
> 本章节用于统一项目中出现的关键术语，避免因理解不一致导致的沟通偏差。术语表应在项目启动时建立，复盘时补充项目过程中新增或产生歧义的术语。

| 术语 | 英文/缩写 | 定义 | 备注 |
|------|----------|------|------|
| 复盘 | Retrospective / Post-mortem | 项目结束后对过程和结果进行系统性回顾，总结经验教训以指导未来实践 | 区别于"总结"：复盘强调事实还原和根因分析，而非成绩罗列 |
| 行动项 | Action Item | 复盘产出的具体待办任务，需满足 SMART 原则 | 无负责人和截止日期的行动项不具备执行效力 |
| 里程碑 | Milestone | 项目中的关键时间节点，标志某一阶段的完成 | 应具备明确的完成标志（Definition of Done） |
| 根因分析 | Root Cause Analysis (RCA) | 透过表面现象识别问题根本原因的方法 | 常用方法：5-Why、鱼骨图、故障树分析 |
| SMART 原则 | SMART Criteria | 目标设定的五个标准：具体、可衡量、可分配、相关、有时限 | 用于检验行动项的可执行性 |
| 技术债 | Technical Debt | 为短期交付速度而采取的非最优技术方案所隐含的未来返工成本 | 需记录并规划偿还，不可无限累积 |
| 偏差 | Variance | 实际结果与计划目标之间的差距 | 正偏差（超前）和负偏差（滞后）均需分析 |
| SOP | Standard Operating Procedure | 标准作业程序，团队约定的常规操作流程 | 复盘结论应转化为 SOP 更新以实现知识固化 |
| Definition of Done | DoD | 完成的定义，团队对"任务完成"的统一判定标准 | 应在项目启动时明确，避免验收争议 |
| 度量指标 | Metric | 用于量化衡量目标达成情况的数据指标 | 好的指标应可获取、可对比、可行动 |

## 假设与限制

### 本文档的假设

1. 复盘参与者对项目过程有充分了解，能够提供事实性输入
2. 项目数据（指标、日志、文档）可获取且可信
3. 复盘过程遵循对事不对人的原则，参与者可畅所欲言
4. 行动项的负责人有能力和资源推动执行

### 本文档的限制

1. 本文档为通用复盘框架模板，具体项目需根据实际情况裁剪章节和字段
2. 复盘结论受限于参与者的认知范围和信息完备性，可能存在盲区
3. 行动项的执行效果需在后续迭代中跟踪验证，本文档不保证行动项必然落地
4. 文中所有「占位符」内容需替换为实际信息后方可作为正式文档使用

> [!WARNING]
> 禁止在未填入实际项目数据的情况下将本文档直接作为复盘结论提交。模板提供结构，不提供内容；所有判断必须基于项目事实。
