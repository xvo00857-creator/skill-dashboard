# 跨团队协作与责任对齐 - 异步协作计划（草稿）

> 状态：**草稿，待各负责人确认后生效**
> 生成日期：2026-08-12（周三）
> 依据 Skill：ai-team-orchestration（Producer / Dev / QA 三角色模型）
> 重要：本计划不替任何成员承诺其未同意的截止时间；所有日期均为建议检查点。

---

## 0. Skill 能力边界说明（必读）

`ai-team-orchestration` 的真实职责是：**在代码仓库中启动并运行一个轻量级多智能体开发团队**，固定三个角色——

- `@ai-team-producer`：澄清范围、按比例规划、协调、合并
- `@ai-team-dev`：实现、自测、准备 PR
- `@ai-team-qa`：仅在需要时做独立行为测试

它**不是**通用的人类跨组织/跨时区协作框架，不定义：组织架构、时区轮班、人事升级链、外部依赖谈判流程。

因此本题中"三个团队"与 Skill 的"三个角色"并不直接等同。以下方案**只沿用 Skill 中确实适用的机制**（角色分离、持久上下文、异步交接、按风险伸缩流程、未知工作先询问），不把 Skill 扩张为通用项目管理框架。超出 Skill 边界的部分（组织升级路径、跨时区排班）已明确标注为"Skill 未定义，按通用协作原则补充，需确认"。

---

## 1. 目标

在不替成员承诺未同意截止时间的前提下，于 2026-08-12 至 2026-08-19 一周内，建立可异步运转的协作机制，使三方在时区不同、两项依赖未确认的情况下仍能持续推进，并在周末有可验证的进展记录。

## 2. 范围

**范围内**
- 建立单一事实源（持久化上下文，而非聊天记录）
- 明确 Producer / Dev / QA 三角色责任边界与排除项
- 两项未确认依赖的登记、跟进与升级触发条件
- 一周内可验证的检查点（非强制截止时间）

**范围外（明确排除）**
- 不替任何成员设定或承诺其未书面确认的交付日期
- 不在依赖未确认前假设依赖成立并据此排期
- 不规定具体 Git 命令或分支策略（遵循仓库自身策略，见 SKILL.md "Follow repository policy"）
- 不强制对每项变更走正式流程（按风险伸缩，小改动可直接进行）

## 3. 异步协作方案

依据 SKILL.md 的"Context Recovery"与"clear handoffs"原则：

1. **单一事实源入库**：在实际项目仓库中维护 `PROJECT_BRIEF.md`（跨会话持久上下文）与本计划/进度记录。决策、阻断、下一步只认仓库记录，不认聊天。
   - *当前状态：尚未确认实际项目仓库位置，无法创建——标记为待确认项 A。*
2. **交接协议**：每个工作窗口结束前，负责人更新进度记录（Completed / In progress / Blocked / Decisions / Next action），使下一时区的接手人可自助继续。
3. **冷启动提示**：接手人按固定句式恢复上下文（来自 SKILL.md）：
   > "Read the repository instructions, then read whichever sources exist for this work: the active issue or request, PROJECT_BRIEF.md, and the active plan or progress note. Continue from the recorded next action."
4. **Dev 交接语**（交给实现方时使用，来自 sprint-plan-template）：
   > "Read the repository instructions, PROJECT_BRIEF.md when present, and this plan. Implement the in-scope work, run the listed verification, update durable context when needed, and prepare a pull request. Do not merge."
5. **响应预期**：异步而非即时。跨时区问题写入持久记录并 @ 对应角色负责人；不要求对方在线即时回复。
6. **QA 按需介入**：仅当风险/不确定性/仓库策略需要时才加入独立 QA；小改动不强制（SKILL.md："Use only when dedicated behavioral verification adds value"）。

## 4. 责任边界

依据 SKILL.md 三角色分离原则（反模式："One agent owns planning, implementation, testing, and approval"）：

| 角色 | 负责 | 不负责 / 排除 |
|---|---|---|
| Producer（协调方） | 定义成果、约束、验收标准、明确排除项；按风险选择评审/QA 级别；保持持久上下文简洁最新；协调依赖跟进与升级 | 不亲自实现；不替 Dev/QA 承诺日期；不绕过仓库合并策略 |
| Dev（实现方） | 按仓库约定做最小完整实现；运行相关检查；检查最终 diff；提交/更新 PR（含摘要、验证情况、限制说明） | 不自我批准合并；不修改与本次范围无关的代码 |
| QA（独立验证，按需） | 测试所请求变更与重要回归；报告可复现的发现；验证修复 | **不修改应用源码**（反模式："QA fixes application source"）；无价值时不介入 |

**待确认项 B**：上述三个角色由哪三个实际团队/人员承担、各自时区与工作时间窗口——题目仅说明"三个团队时区不同"，未给出具体团队名与时区，**需各负责人书面确认**后此表才生效。

## 5. 未确认依赖与假设

以下为题目给定的"两项依赖尚未确认"。具体内容题目未提供，**不得编造**：

- **依赖 1**：[待填写：依赖描述、提供方、对接人] — 状态：**未确认**
- **依赖 2**：[待填写：依赖描述、提供方、对接人] — 状态：**未确认**

处理规则（依据 SKILL.md "Preserve unknown work and ask before destructive or privileged actions"）：
- 依赖未确认前，**不假设其成立**，不据此排后续节点；
- 涉及依赖的工作项在进度记录中标记为 Blocked，并写明阻塞原因与等待对象；
- 任何绕过依赖、破坏他人未确认工作的操作须先询问，不得擅自执行。

其他待确认假设：
- 待确认项 A：实际项目仓库/任务追踪系统位置
- 待确认项 B：三角色对应的实际团队、人员、时区窗口
- 待确认项 C：仓库自身的分支保护、必需检查、合并策略

## 6. 升级路径

> 说明：SKILL.md **未定义**组织级升级链，以下为依据其"先询问、保未知工作、持久记录"原则补充的最小升级机制，**需团队确认后采用**。

| 触发条件 | 升级动作 | 升级到 |
|---|---|---|
| 依赖在约定响应窗口内无回应（窗口时长待确认） | 在持久记录中登记阻断，@ 依赖对接人并抄送 Producer | 依赖提供方对接人 |
| 依赖二次催办后仍无回应或被拒绝 | Producer 评估范围裁剪或替代方案，必要时上升 | 各方负责人 |
| 成员被要求承诺其未同意的截止时间 | 暂停承诺，回到 Producer 重新协商范围/时间 | Producer |
| 出现破坏性/高风险操作（改写共享历史、丢弃未知工作等） | 立即停止，先询问并协调（SKILL.md 原则） | 相关方 + Producer |
| QA 与 Dev 对是否为缺陷有分歧 | 以可复现步骤记录，Producer 依据验收标准裁决 | Producer |

升级全过程在持久记录中留痕，不仅在聊天中讨论（反模式："Bugs and decisions kept only in chat"）。

## 9. 风险与决策

- **风险**：仓库位置/团队人员未确认 → M0 可能无法落地。决策：先以本草稿为协调基础，确认后立即入库。
- **风险**：两项依赖迟迟不确认 → 一周内可能无实现产出。决策：M2 前无进展即升级，并准备范围裁剪方案，而非假设依赖成立。
- **决策**：采用 Skill 的三角色模型而非新建流程；QA 按需而非强制。
