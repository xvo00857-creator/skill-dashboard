# EAS Workflows 受约束批量校验流程方案

## 1. Skill 能力边界

本方案严格基于 `expo-cicd-workflows` Skill 的真实能力：

- **能做**：获取 EAS 官方 JSON Schema / 语法文档 / 预打包作业文档；编写和校验 `.eas/workflows/*.yml`；用 AJV 按官方 schema 校验 YAML 结构。
- **不做**：不触发 EAS 构建、不提交应用商店、不部署、不管理外部云资源、不修改 Expo 账户配置。
- **数据来源**：仅使用 Skill 脚本（fetch.js / validate.js）、其声明的 npm 依赖，以及官方 schema 端点 `https://api.expo.dev/v2/workflows/schema`。未编造任何 job 类型、参数或枚举值。

## 2. 环境兼容性说明（实际影响交付的规则）

SKILL.md 指定通过 `node <skill-dir>/scripts/validate.js` 运行校验，但该脚本与 fetch.js 的 CLI 入口均依赖 `import.meta.main`。该特性在 Node.js v22.10+ 才默认可用，当前环境为 Node v20.19.2，直接运行无输出。

**处理方式**：未修改 Skill 原始文件。runner 通过 ES 模块 `import` 直接复用 fetch.js **导出的** `fetchCached` 函数（该函数在 v20 下正常工作），并使用 Skill `package.json` 声明的 ajv / ajv-formats / js-yaml 依赖，按 validate.js 同等逻辑（AJV 2020 + allErrors + js-yaml）执行校验。

## 3. 受约束的流程设计

### 3.1 预检（preflight）
runner 启动时逐项检查，任一失败即终止：
- Node.js 主版本 >= 18（需要内置 fetch 和 ESM）
- Skill fetch.js 存在
- 校验依赖已安装（ajv/dist/2020.js、js-yaml/index.js）
- 每个待校验文件存在

### 3.2 幂等
- **Schema 获取**：复用 fetch.js 的 ETag + Cache-Control/Expires 缓存（15 分钟 TTL），重复获取命中本地缓存（实测 2~3ms）。
- **文件校验**：状态文件 `.batch-validate-state.json` 记录每个文件的校验结果；`--skip-valid` / `--resume` 模式下已通过的文件直接跳过，不重复校验。
- **依赖安装**：按 SKILL.md 的 `[ -d node_modules ] || npm install` 模式，已安装则跳过。
- **报告文件**：带时间戳命名，不覆盖已有报告。

### 3.3 重试
- 获取 schema 时网络失败按指数退避重试（1s → 2s → 4s，上限 8s），默认 3 次，可通过 `--max-retries` 调整。
- fetch.js 自身的 ETag 机制在服务端返回 304 时复用缓存，减少网络依赖。

### 3.4 人工确认点
- **确认点 1**：校验开始前展示待校验文件清单，交互模式下需输入 `y` 确认；`--yes` / `-y` 可跳过（用于 CI 或本次演示）。
- **Workflow 内确认**：示例 workflow 中使用了 schema 原生的 `require-approval` job 类型，在 build 与 submit 之间设置人工审批关卡。
- 未设计任何自动触发真实构建/提交的步骤，所有"有副作用"的操作仅限本地文件写入。

### 3.5 可恢复
- 每校验完一个文件立即写入状态文件（非全部完成后才写），中断后重跑可从断点继续。
- `--resume` 模式：跳过所有已通过文件，只重校失败/未处理的文件。
- 修复文件后重跑，状态自动更新。

### 3.6 语义检查（SKILL.md 第 3、4 条）
在 schema 校验之外补充：
- `needs` / `after` 引用的 job 名必须存在于同一 workflow 中。
- 违规以警告形式记录到报告（不阻断，但可见）。

## 4. 文件清单

## 5. 可核验的演示结果

### 演示 1：合法 + 故意错误文件批量校验
- `ci-demo.yml`：**通过**（含 custom/build/require-approval/submit 四类 job，表达式引用 build 输出）
- `broken-demo.yml`（原始错误版）：**失败**，104 条 schema 错误 + 1 条语义警告（`needs` 引用不存在的 `nonexistent-job`）
- 退出码 1

### 演示 2：幂等重跑（`--skip-valid`）
- `ci-demo.yml`：跳过（状态文件已记录通过）
- `broken-demo.yml`：仍失败
- ETag 缓存命中：二次获取 schema 仅 3ms

### 演示 3：可恢复（修复后 `--resume` 重跑）
- 修复 broken-demo.yml 为合法 fingerprint job
- `ci-demo.yml`：跳过
- `broken-demo.yml`：**通过**
- 退出码 0

## 6. 使用方法

```bash
# 安装依赖（幂等，按 SKILL.md）
[ -d expo-cicd-workflows/expo-cicd-workflows/scripts/node_modules ] || \
  npm install --prefix expo-cicd-workflows/expo-cicd-workflows/scripts

# 批量校验（交互确认）
node batch-validate.mjs .eas/workflows/*.yml

# 非交互模式 + 可恢复
node batch-validate.mjs --yes --resume .eas/workflows/*.yml

# 跳过已通过文件
node batch-validate.mjs --yes --skip-valid .eas/workflows/*.yml
```

## 7. 限制与待确认假设

- **未实际触发 EAS 构建**：本流程仅做 YAML 静态校验，不验证 Expo 账户权限、EAS 配额、构建凭据或 profile 配置是否在真实项目中可用。按 SKILL.md Limitations，生成示例不能替代环境特定测试和安全审查。
- **schema 时效性**：schema 通过 ETag 缓存，最长 15 分钟；如需最新可删除 `scripts/.cache/` 后重跑。
- **Node 版本**：当前 v20.19.2 下 Skill 自带 validate.js CLI 不可直接运行（import.meta.main 问题），runner 已绕过；若升级到 Node v22.10+，可直接使用 `node scripts/validate.js`。
- **示例 workflow 中的 steps 内容**（如 `uses: expo/expo-github-action`、`npm ci`）来自官方语法文档示例，schema 对 custom job 的 steps 不做结构约束（items 为 `{}`），其在真实 EAS 环境中的可用性未验证。
- **submit job 的 build_id** 使用表达式 `${{ needs.build.outputs.build_id }}` 引用，schema 仅校验其为字符串，输出字段名是否与 build job 实际输出一致需对照官方文档确认。
