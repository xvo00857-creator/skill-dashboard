### 1.3 为何不能直接产出测试文件

SKILL.md「Generating Tests from Route Scan」规定的流程为：

1. 扫描路由 → 2. 读取每个路由处理器（请求体结构、鉴权要求、返回类型、业务规则）→ 3. 按路由组生成测试文件 → 4. 描述性命名 → 5. 使用工厂/夹具 → 6. 断言响应结构

第 1、2 步是第 3 步的必要输入。在没有任何路由处理器的情况下：

- 无法获知端点路径、HTTP 方法、请求体 schema、鉴权中间件、返回状态码与业务规则；
- Skill 输出的是"ready-to-run test files"（可直接运行的测试文件），需要导入项目真实的 app/server、使用项目真实的测试辅助函数；
- 若凭空编造路由和测试内容，将违反"不得编造文件内容"的要求，且产出物无法运行、无验收价值。

因此本次交付为：**测试设计框架 + 最小改动方案 + 回滚办法 + 测试清单 + 待确认项**，待目标代码库就位后可立即按此执行。

## 三、测试设计框架（代码库就位后按此执行）

### 3.1 鉴权测试矩阵（每个需鉴权端点）

| 测试用例 | 预期状态码 |
|---|---|
| 无 Authorization 头 | 401 |
| Token 格式非法 | 401 |
| 过期 JWT | 401（且错误信息匹配 /expired/i） |
| 合法 Token 但角色错误 | 403 |
| 已删除用户的 Token | 401 |
| 合法 Token + 正确角色 | 2xx |

### 3.2 输入校验矩阵（每个带请求体的 POST/PUT/PATCH）

| 测试用例 | 预期状态码 |
|---|---|
| 空体 `{}` | 400 或 422 |
| 逐个缺失必填字段 | 400 或 422 |
| 类型错误（int 位传 string） | 400 或 422 |
| 边界值 min-1 | 400 或 422 |
| 边界值 min | 2xx |
| 边界值 max | 2xx |
| 边界值 max+1 | 400 或 422 |
| SQL 注入字符串 | 400 或 200（已净化） |
| XSS payload | 400 或 200（已净化） |
| 必填字段传 null | 400 或 422 |
| 错误 Content-Type（xml 代替 json） | 按 SKILL.md 陷阱章节补充 |

### 3.3 分页测试矩阵（每个列表端点）

| 测试用例 | 预期 |
|---|---|
| 默认分页参数首页 | 200，返回结构含 data/items、total、page、pageSize/size |
| 超出总页数的页 | 200，空数组 |
| page ≤ 0 | 400 或 422 |
| pageSize 超过上限 | 200，服务端截断至上限（≤100） |

### 3.4 文件上传测试矩阵（每个上传端点）

| 测试用例 | 预期状态码 |
|---|---|
| 未认证 | 401 |
| 未附加文件 | 400 |
| 不支持的文件类型（exe） | 400 |
| 超大文件（>10MB） | 413 |
| 空文件（0 字节） | 400 |
| MIME 伪装（pdf 扩展名 + exe 魔数） | 400 或 415 |
| 合法文件 | 200，返回 url 和 id |

### 3.5 限流测试（最后添加，避免干扰并行测试）

| 测试用例 | 预期 |
|---|---|
| 突发超过阈值（如 60 次/分钟） | 出现 429 |
| 429 响应含 Retry-After 头或 retry_after 字段 | 存在 |

### 3.6 通用断言要求

- 每个端点一个 `describe` 块，隔离失败；
- 断言响应结构，不仅是状态码；
- 断言敏感字段（password、secret、hashedPassword）不出现在响应中；
- 断言具体错误信息/字段，不仅是 `errors` 存在；
- 测试命名描述行为，如 `"returns 401 when token is expired"`，不用 `"auth test 3"`。

## 四、最小改动方案

### 4.1 原则

遵循题目约束与 SKILL.md 最佳实践：

1. **兼容既有目录结构**：测试文件放入项目既有测试目录（如 `tests/api/`、`__tests__/`、`tests/`），不新建平行目录；
2. **兼容既有测试框架**：Skill 原生输出 Vitest+Supertest 或 Pytest+httpx。若项目已使用其他框架（Jest/Mocha/unittest），**不擅自引入新依赖**，而是将 Skill 的测试模式适配到既有框架，或标记为待确认项（见第六节）；
3. **不升级主版本**：不修改 `package.json` / `requirements.txt` 中已有依赖的主版本号；
4. **不引入未经批准的新依赖**：若项目缺少 supertest/httpx 等测试 HTTP 客户端，先标记待确认，不自行 `npm install` / `pip install`；
5. **仅新增测试文件与测试辅助函数**：不修改任何业务路由代码；
6. **使用工厂/夹具**：测试数据通过项目既有的 factory/fixture 机制创建，不硬编码 ID。

### 4.2 预期新增文件清单（模式，具体路径待代码库确认）

```
<既有测试目录>/
├── api/
│   ├── <路由组1>.test.ts        # 或 .test.py / _test.py
│   ├── <路由组2>.test.ts
│   └── ...
└── helpers/                      # 仅当项目缺少时才新增，否则复用既有
    ├── server.ts                 # 或 conftest.py
    ├── auth.ts                   # JWT 生成/过期 token 工具
    └── db.ts                     # 测试数据工厂与清理
```

### 4.3 执行步骤（代码库就位后）

1. 在项目根目录执行 SKILL.md 的路由检测命令，生成完整路由表；
2. 逐个读取路由处理器，记录：路径、方法、鉴权要求、请求体 schema、返回状态码、业务规则（所有权、角色）；
3. 确认项目测试框架与测试目录结构；
4. 按路由组生成测试文件，套用第三节矩阵；
5. 运行测试，记录通过/失败；
6. 对失败用例区分：测试本身问题 vs 业务代码缺陷，后者输出缺陷报告而非修改业务代码；
7. 覆盖率检查：确认每个路由至少有冒烟测试，鉴权/校验/分页/上传/限流维度按适用性覆盖。

## 五、回滚办法

由于本方案**仅新增测试文件、不修改业务代码、不修改依赖清单**，回滚非常简单：

1. **删除新增的测试文件**：删除 `<既有测试目录>/api/` 下本次新增的 `<路由组>.test.ts` / `_test.py` 文件；
2. **若新增了 helpers**：删除 `helpers/` 下本次新增的 `server`、`auth`、`db` 辅助文件（若这些文件是项目已有的则未改动，无需回滚）；
3. **依赖回滚**：本方案默认不新增依赖。若经批准后新增了 supertest/httpx 等开发依赖，回滚时从 `package.json` 的 `devDependencies` 或 `requirements-dev.txt` 中移除对应行，并重新安装；
4. **Git 回滚**：若在独立分支上提交，可直接 `git revert <commit>` 或 `git branch -D <branch>`；
5. **验证回滚**：回滚后运行既有测试套件，确认全部通过、无残留引用。

**建议**：在独立 git 分支上执行测试生成，合并前经人工 review，进一步降低风险。
