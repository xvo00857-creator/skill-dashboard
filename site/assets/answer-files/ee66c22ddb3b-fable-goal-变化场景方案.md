# fable-goal 变化场景方案：故事化目标落地

> 场景：可用时间临时减半 · 周三（8/12）增加不可移动评审会 · 结果需交接给另一位同事
> 核心工作：用故事化方法把抽象目标变得具体、有画面、更容易坚持
> 日期基准：2026-08-10（周一）

---

## 一、约束变化如何改变原方案

按 fable-goal 七部分框架逐项分析三条新约束的影响：

| 约束 | 冲击的部分 | 原方案会怎么变 |
|------|-----------|--------------|
| **可用时间减半** | Desire + stakes、Quality bar、Verification loop | 必须砍 scope。原方案可能铺多个故事角度或多轮打磨，现在只能保留一个最生动的目标叙述 + 一轮验证。stakes 从"做到最好"收缩为"可交接、接手人能继续"。 |
| **周三不可移动评审会** | Verification loop、Delivery | 评审会成为天然的检查点（checkpoint），但它是**验证场合**而非**交付里程碑**——不围绕它赶工造一个"完整版"，而是把当前进度拿去受检，收集反馈后交给接手人。 |
| **交接给同事** | Delivery、Creative freedom + decision authority | 交付物从"完成的作品"变为"接手人冷启动就能继续的包"。必须明确 what 和 done condition，把 how 的决定权交给接手人——这正是 fable-goal "get out of the model's way" 原则在人际协作上的直接应用。 |

**核心判断**：三条约束叠加后，方案的第一优先级从"把故事写得多好"变成"让接手人读完就能自主推进"。故事化目标陈述本身是最小不可砍单元——没有它，接手人不知道在坚持什么；其余一切都可以缩减或延后。

## 二、调整后的方案

### 目标

产出一份**可交接的故事化目标方案**：用第一人称、有画面感的叙述把抽象目标说清楚，让接手同事读完后能在不找原负责人确认的情况下独立继续推进，并知道"做到什么算完"。

### 依据

- **fable-goal 核心原则**（来自 SKILL.md）：
  - *Done must be observable*——完成状态必须是可检查的，"做得好"是愿望，"接手人能复述目标和 done condition"才是可验证的完成条件。
  - *Get out of the way*——不 micromanage 执行步骤；写清 what，给接手人 how 的 creative freedom。
  - *Three iteration passes*——至少三轮自查，且每轮要用该媒介自己的语言定义（对文档来说：通读检查流畅性、逐条核对事实、模拟接手人冷启动阅读）。
  - *Stakes must be true*——不编造紧迫感或受众数字；本场景真实 stakes 是"时间减半 + 必须交接"。
- **事实约束**（题目给定，未添加任何外部数据）：时间减半、周三评审会不可移动、交接给同事。

### 步骤

> 假设原计划每天投入约 2 小时，现收缩为每天约 1 小时；周三评审会本身占用人时间，不安排额外产出。

| 日期 | 投入 | 做什么 | 产出 |
|------|------|--------|------|
| **周一 8/10（今天）** | ~1h | 写出故事化目标陈述第一版：desire + stakes、quality bar、observable done condition。这是接手人最需要的东西，其他一切围绕它。 | 目标陈述 v1（七部分中的前 1、2、6 部分） |
| **周二 8/11** | ~1h | 补充执行步骤、优先级、关键取舍；完成交接文档草稿（当前状态、决策边界、验证方式、下一步）。 | 交接文档草稿（含步骤 3、4、5、7 部分） |
| **周三 8/12** | 评审会 | **验证 checkpoint**：把当前版本带去评审会过一遍，收集反馈。现场标记：①必须改的 ②可留给接手人判断的。 | 反馈标注清单 |
| **周四 8/13** | ~1h | 根据"必须改"清单做最小修订；整理正式交接包（目标陈述 + 当前进度 + 决策边界 + 验证清单 + 下一步）。 | 交接包 v1 |
| **周五 8/14** | ~1h | 与接手同事做 15 分钟 walkthrough：请 ta 用自己的话复述目标和 done condition，确认无歧义后正式移交。 | 交接完成确认 |

### 关键取舍

1. **砍 scope，不降 quality bar 的下限。** 时间减半后，选择只做一个角度的故事化叙述并把它写透，而不是铺多个方向每个都半成品。Quality bar 从"多方向探索"变为"一个方向做到接手人能直接用"。
2. **评审会是验证点，不是里程碑。** 不为周三"赶一个完整版"。周三的版本就是周二的草稿——它的作用是受检，不是交付。这避免了为会议制造临时版本、会后又返工的浪费。
3. **给接手人 creative freedom，不写 step-by-step。** 交接包里写清 what（目标是什么、done condition 是什么、哪些边界不能动），但不规定 how（具体怎么推进、先做哪个、用什么工具）。接手人有权在边界内做判断，不需要事事请示。
4. **故事化叙述是最小不可砍单元。** 如果时间进一步压缩到只能保一样东西，保"desire + stakes 的生动叙述"——这是"用故事化方法让抽象目标变具体"的核心，也是接手人理解"为什么坚持"的唯一来源。步骤清单、风险分析都可以口头补充，但没有画面感的目标陈述，接手人拿到的只是一个任务列表，不是一个能坚持的目标。

### 风险

| 风险 | 触发条件 | 应对 |
|------|---------|------|
| 接手人不熟悉"故事化方法"/fable-goal 七部分结构 | 接手人读完目标陈述后不知道怎么继续 | 交接包附七部分结构简述；周五 walkthrough 时花 5 分钟解释"为什么用故事化叙述而非任务列表" |
| 周三评审反馈要求大改，超出周四 1 小时预算 | 评审意见指向目标陈述本身需要重写 | 周四只改"事实错误"和"方向偏差"；"可以更好"的反馈全部标记为"接手人决定"，不替接手人做审美判断 |
| 砍 scope 后目标失去画面感，退化为抽象任务列表 | 为压缩篇幅删掉了具体场景和 stakes 描述 | 自检时专门检查：目标陈述是否包含一个读者能"在脑子里看到"的具体场景？如果不能，补回画面感再交 |
| 交接后接手人遇到边界模糊的情况 | 决策边界写得不够清楚 | 交接包中明确列出"以下决定你可以直接做"和"以下情况请找我确认"两类，减少灰色地带 |

### 衡量方式（observable done）

方案完成的可观察标准：

1. **接手人复述测试**：接手同事读完交接包后，能用自己的话说出——目标是什么、做到什么算完、哪些决定 ta 可以自己做。三条都说对，交接才算完成。
2. **七部分覆盖检查**：故事化目标陈述覆盖 fable-goal 七部分中的前六部分（desire + stakes、quality bar、tools/discovery mandate、creative freedom、verification loop、delivery）；第七部分（goal line + autonomy directive）在人际交接场景中转化为"交接确认语"——接手人确认"我知道目标是什么，我可以自主推进到 done condition"。
3. **事实一致性**：方案中所有约束描述（时间减半、周三评审、交接）与题目给定事实一致；无编造的数据、来源、能力声明或已完成动作。
4. **自检通过**：按 SKILL.md 六点自检逐项确认；机械检查（self_check.py）6/6 通过。

## 三、故事化目标陈述（按 fable-goal 七部分结构）

> 以下是交接包的核心文件——给接手同事读的目标叙述。用第一人称、有画面感的方式写，让接手人"看到"目标完成时的样子，而不是只拿到一个任务列表。

**1. Desire + stakes**
我想把一个目前还很模糊的目标，变成一个我（和接手的同事）能在脑子里清晰看到的东西——不是"用故事化方法"这个抽象动作，而是一个具体的场景：某个人读到这个目标叙述时，能立刻想象出完成那天的画面，知道为什么值得坚持。这件事这周必须交出去，因为我的可用时间被砍了一半，周三还有一场挪不动的评审会，之后由另一位同事接着推进。stakes 很真实：如果交接时目标还是模糊的，接手人拿到的不是一个能坚持的目标，而是一堆不知道往哪走的待办。

**2. Quality bar**
好的故事化目标叙述读起来像一个朋友在跟你说 ta 真正想要什么——具体、有画面、不绕弯。读完后你知道"做完长什么样"，而不是只知道"要做什么"。对功能性内容（步骤、取舍、风险），标准反过来：写清行为和边界，不用形容词凑数。

**3. Tools + discovery mandate**
接手人可以用任何顺手的方式推进——文档工具、笔记软件、甚至纸笔都可以。开始之前，先花 10 分钟看看手头有什么资源、缺什么信息，需要的话自己去查、去问、去找参考。方法不设限。

**4. Creative freedom + decision authority**
怎么组织叙述、先推进哪部分、用什么格式，这些由接手人判断。唯一不能动的是：目标必须保持具体和可观察，不能退回抽象空话；事实约束（时间减半、周三评审已过、已交接）不能改。其余决定接手人有权直接做，不需要回来请示。

**5. Verification loop**
在宣布"目标已经足够具体"之前，至少过三轮：第一轮，通读整个叙述，检查有没有哪里读着空洞、像口号；第二轮，逐条核对事实——有没有编造约束、数据或已经做了但其实没做的事；第三轮，把自己当成接手人，冷读一遍，看能不能仅凭这份文档就知道下一步做什么。三轮都过了才算数。

**6. Delivery**
成果是一份中文 Markdown 方案（就是本文件），包含目标陈述、步骤、取舍、风险、衡量方式和下一步。交接时通过 walkthrough 确认接手人理解无误。

**7. Goal line + autonomy directive（交接场景转化版）**
"一个具体、有画面、可观察、可交接的故事化目标方案，接手人能自主推进到完成"——这就是目标。接手人在边界内完全自主推进，不需要为每个决定回来确认。
