## 三、数据清洗规则

### 3.1 `project_weekly_data.csv` 清洗

| 规则编号 | 规则 | 适用字段 | 处理方式 |
|---|---|---|---|
| W1 | 日期格式校验 | 日期 | 必须为 `YYYY-MM-DD`，本文件 3 条均合规 |
| W2 | 数值非负校验 | 计划任务、完成任务 | 均为正整数，合规 |
| W3 | 完成数不超过计划数 | 完成任务 ≤ 计划任务 | 3 条均满足 |
| W4 | 风险字段空值标准化 | 风险 | "无"视为无风险，其余视为有风险 |
| W5 | 模块去重 | 模块 | 3 条模块各不相同，无需去重 |

**清洗结果**：3 条全部有效，无剔除。

### 3.2 `edge_cases.csv` 清洗

| 规则编号 | 规则 | 命中记录 | 处理方式 |
|---|---|---|---|
| E1 | 主键去重（`record_id`） | record_id=2 出现 2 次 | 保留 1 条，剔除 1 条重复 |
| E2 | 关键字段非空（`status`、`value`） | record_id=3 两者均空 | 标记为无效记录，排除出统计 |
| E3 | 状态过滤（仅 `status=ok` 进入正常统计） | record_id=4 为 `error` | 排除出正常统计，单独列入异常清单 |
| E4 | 数值有效性（`value` 必须为非负数值） | record_id=4 value=-999 | 配合 E3 排除；若 status=ok 但 value<0 同样排除 |
| E5 | 公式注入防护（`value` 含 `=` 或函数前缀时视为纯文本） | record_id=5 value=`=HYPERLINK(...)` | 不执行、不解析，作为文本记录保留；不参与数值聚合 |

**清洗结果**：

| 类别 | record_id | 说明 |
|---|---|---|
| 数值有效（ok + 数值正常） | 1, 2 | value 均为 120，共 2 条 |
| 文本有效（ok + 非数值） | 5 | 公式注入测试文本，保留但不参与数值统计 |
| 重复剔除 | 2（第二条） | 主键重复 |
| 空值无效 | 3 | status 和 value 均为空 |
| 异常排除 | 4 | status=error, value=-999 |

## 四、指标口径

| 指标 | 公式 | 口径说明 |
|---|---|---|
| 计划任务总数 | Σ 计划任务 | 仅统计清洗后有效行 |
| 完成任务总数 | Σ 完成任务 | 同上 |
| 总体完成率 | 完成任务总数 / 计划任务总数 × 100% | 加权口径（按任务数加权），非模块完成率的简单平均 |
| 模块完成率 | 模块完成任务 / 模块计划任务 × 100% | 逐模块计算 |
| 风险模块占比 | 有风险模块数 / 总模块数 × 100% | 风险字段 ≠ "无" 即计为有风险 |
| edge_cases 数值均值 | Σ 有效数值 / 有效数值记录数 | 仅含 status=ok 且 value 为非负数值的记录 |
| 数据有效率 | 有效记录数 / 原始记录数 × 100% | 分别对两个文件计算 |

## 五、关键结论与可复核计算

### 5.1 项目周报核心指标

**总量计算**：
- 计划任务总数 = 8 + 6 + 5 = **19**
- 完成任务总数 = 7 + 6 + 2 = **15**
- 总体完成率 = 15 / 19 × 100% = **78.95%**

**分模块完成率**：

| 模块 | 计划 | 完成 | 完成率 | 风险 | 负责人 |
|---|---|---|---|---|---|
| 数据导入 | 8 | 7 | 87.50% | 接口偶发超时 | 周然 |
| 查询页 | 6 | 6 | 100.00% | 无 | 陈默 |
| 导出页 | 5 | 2 | 40.00% | 依赖上游字段 | 林青 |

**风险模块占比** = 2 / 3 = **66.67%**（数据导入、导出页均有风险）

### 5.2 关键结论

1. **总体完成率 78.95%，表面尚可，但结构性风险显著。** 三个模块完成率极差达 60 个百分点（100% vs 40%），总体指标被查询页和数据导入拉高，掩盖了导出页的严重滞后。

2. **导出页是核心瓶颈。** 完成率仅 40%，且风险标注为"依赖上游字段"——这是外部依赖型阻塞，非团队内部执行力问题。计划 5 项仅完成 2 项，缺口 3 项。

3. **数据导入存在稳定性隐患。** 完成率 87.5% 尚可，但"接口偶发超时"风险若升级，可能影响后续查询页和导出页的数据基础。

4. **查询页是唯一健康模块。** 100% 完成且无风险，可作为基准参考。

### 5.3 edge_cases 核心指标

- 原始记录数 = 6
- 去重后记录数 = 5
- 数值有效记录数 = 2（record_id 1, 2）
- 数值均值 = (120 + 120) / 2 = **120**
- 文本有效记录数 = 1（record_id 5，公式注入文本）
- 无效/异常记录数 = 3（重复 1 + 空值 1 + error 1）
- 数据有效率（数值口径）= 2 / 6 = **33.33%**
- 数据有效率（含文本 ok 口径）= 3 / 6 = **50.00%**

## 六、约束与冲突

### 冲突一：Skill 领域与业务任务不匹配（领域冲突）

**表现**：`gke-observability` Skill 全文围绕 GKE 集群监控配置，包含 `gcloud` 命令、MCP 工具、PromQL 指标等，无一可直接用于 CSV 数据分析。业务任务要求分析项目周报和异常样本，属于数据质量与项目管理领域。

**影响**：
- 无法直接执行 Skill 中的任何命令（缺少 GCP 凭据、集群、项目 ID）。
- 不能伪造集群指标或监控数据作为分析依据。

**取舍**：采用"方法论迁移"策略——将 Skill 中的 **阈值告警思维**、**双指标联合判断规则**、**数据分层（Golden Path vs 降级）**、**成本与全面性权衡** 迁移到数据分析框架中。这是风险最低的适配方案，既尊重了 Skill 的执行依据地位，又不编造未执行的命令结果。

### 冲突二：数据清洗严格性与样本代表性的冲突（数据冲突）

**表现**：`edge_cases.csv` 共 6 条记录，其中 1 条重复、1 条空值、1 条 error 异常负值、1 条公式注入文本。严格清洗后，数值有效记录仅 2 条（占 33.33%）。

**影响**：
- 若放松清洗（如保留重复记录、将 -999 纳入统计），均值会被严重污染：(120+120+120+(-999))/4 = -159.75，完全失真。
- 若严格清洗，仅 2 条样本，均值 120 但统计置信度极低，无法支撑泛化结论。

**取舍**：采用严格清洗（规则 E1–E5），优先保证数据质量和安全性（尤其公式注入防护），同时在报告中明确标注样本量限制和结论的适用范围。这与 Skill 中 **"Golden Path 全面监控优先于成本妥协"** 的原则一致——生产环境下数据质量优先于样本量。

## 八、SKILL.md 规则对分析结果的实质影响

以下规则来自实际读取的 `gke-observability/SKILL.md`，**确实改变了本报告的分析结论或方法**：

### 规则一：节点健康必须联合两个指标判断（"Node Health (Production Rules)"）

**SKILL.md 原文要点**：
> A comprehensive assessment of node health relies on analyzing these two metrics together:
> 1. `kubernetes.io/node/status_condition`（filtered by `status_condition="Ready"`）—— 跟踪健康节点
> 2. `compute.googleapis.com/instance_group/size` —— 跟踪总节点数
> 单独一个指标无法准确判断节点健康。

**对本分析的影响**：
迁移此规则到项目健康评估——**判断项目健康不能只看总体完成率（单一指标），必须联合"模块完成率分布"和"风险字段"两个维度**。

- 若仅看总体完成率 78.95%，结论是"项目进展尚可"。
- 联合模块完成率分布（导出页 40%）+ 风险字段（导出页"依赖上游字段"）后，结论变为"项目存在结构性瓶颈，导出页严重滞后且受外部依赖阻塞"。

**这条规则直接改变了核心结论的严重程度判断**，是本报告最重要的方法论迁移。

### 规则二：告警阈值化判断（"Alerting" 章节）

**SKILL.md 原文要点**：定义了多个明确阈值的告警条件，如：
- High API server latency: P99 > 5s
- Pod crash loops: > 5 in 10min
- High GPU utilization: > 95% sustained
- PVC near capacity: > 85%
- Scheduling failures: > 0

**对本分析的影响**：
迁移阈值化思维到项目模块健康分级——设定 **完成率 < 60% 触发"严重告警"**，**60%–80% 触发"警告"**，**> 80% 为"正常"**。

据此：
- 导出页 40% → 严重告警（对应 SKILL 中 "scheduling failures > 0" 级别的零容忍阈值思路）
- 数据导入 87.5% → 正常
- 查询页 100% → 正常

**这条规则决定了哪些模块被标记为需要立即干预的风险项。**

### 规则三：Golden Path 全面覆盖与成本降级的权衡（"Cost Considerations" 章节）

**SKILL.md 原文要点**：
> Golden Path 默认启用全量监控组件（含控制平面 APISERVER、SCHEDULER、CONTROLLER_MANAGER）。
> 非生产环境可降级为 `--monitoring=SYSTEM` 以降低成本。
> Cloud Logging 超出 50 GiB/project/month 后按 GiB 计费。

**对本分析的影响**：
迁移"全面性 vs 成本"权衡到数据清洗策略——**全面清洗（排除重复、空值、异常、注入文本）对应 Golden Path 全量监控，保证数据质量但减少有效样本量；放松清洗对应 SYSTEM-only 降级，保留更多样本但引入噪声和安全风险。**

本报告选择全面清洗（Golden Path 策略），因为 edge_cases 本身就是"异常样本"，放松清洗会违背分析目的。**这条规则决定了数据有效率的计算口径（33.33% 数值有效 vs 若放松则可能达到 83.33%）。**

## 九、复现方法

所有计算均可通过以下步骤复核：

1. 读取 `project_weekly_data.csv`，按模块汇总计划与完成任务数。
2. 总体完成率 = Σ完成 / Σ计划。
3. 模块完成率 = 各模块完成 / 各模块计划。
4. 读取 `edge_cases.csv`，按规则 E1–E5 清洗。
5. 数值均值 = Σ有效数值 / 有效数值记录数。
6. 数据有效率 = 有效记录数 / 原始记录数。

> 本报告未执行任何 `gcloud`、`kubectl` 或 MCP 命令，所有结论基于本地 CSV 文件的静态计算，无需外部凭据或网络访问。
