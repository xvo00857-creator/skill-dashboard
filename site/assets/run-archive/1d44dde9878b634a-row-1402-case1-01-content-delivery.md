## 三、AI 推测层（基于事实的推断）

> ⚠️ 以下均为 AI 基于事实层数据做出的推断，**不等同于事实**。每条标注推理依据，供使用者自行判断。

### 推断 1：导入可靠性可能是最优先的产品差异化切入点

【推断】在三项核心发现中，「最关心导入可靠性」以 46% 居首，高于「愿意为自动摘要付费」（31%）。这提示在当前样本中，用户对数据导入的可靠性关注度高于对自动摘要功能的付费意愿，导入可靠性可能是更优先的产品差异化方向。

- **推理依据**：事实层 2.2 表格中 46% > 31% 的数值对比。
- **边界**：此推断仅反映"关注度排序"，不直接等同于"付费意愿排序"或"市场机会排序"。

### 推断 2：自动摘要功能的付费意愿有限，可能不适合作为核心付费点

【推断】仅 31% 的受访者表示愿意为自动摘要付费，不足三分之一。这表明在当前样本中，自动摘要作为独立付费功能的吸引力有限，若将其作为核心变现点可能面临转化压力。

- **推理依据**：事实层 2.2 表格中 31% 的数值。
- **边界**："愿意付费"不等于"实际付费"；且未提供付费价格区间，无法判断价格弹性。

### 推断 3：10-50 人中小团队可能是核心用户群

【推断】10-50 人团队占样本的 43.3%（52/120），是占比最高的分组。若样本具有代表性，中小团队可能是轻量协作软件的核心用户群。

- **推理依据**：事实层 2.3 分组数据。
- **边界**：源文件明确声明"不代表真实市场规模"，且未说明抽样方法，此推断的外部效度存疑（见待核实层）。

### 推断 4：协作工具在样本中已有较高使用渗透率

【推断】78% 的受访者每周使用协作工具，说明在当前样本中协作工具并非低频或新兴品类，而是已有较高渗透率的日常工具。

- **推理依据**：事实层 2.2 表格中 78% 的数值。
- **边界**："每周使用"的频率定义不明确（是每周至少一次还是每天？），且未区分使用深度。

## 四、待核实层（源文件缺失的关键信息）

> 以下信息在 `market_research.md` 中**未提供**，但对解读数据和形成可靠结论有实质影响。在补充这些信息之前，推断层的结论应视为暂定。

| 编号 | 缺失信息 | 为什么需要 |
|---|---|---|
| V1 | **抽样方法**：120 名受访者如何选取？随机抽样 / 便利抽样 / 定向邀请？ | 决定样本是否具有代表性，直接影响所有推断的外部效度 |
| V2 | **受访者画像**：行业分布、角色（管理者/员工/IT）、地域、公司类型 | 不同画像的用户对协作工具的需求和付费意愿差异显著 |
| V3 | **"演示数据"的定义**：是模拟生成的数据、内部试点数据，还是其他含义？ | 源文件自称"演示数据"，若为模拟数据则所有数值均无实证意义 |
| V4 | **问卷题型**：核心发现的三个数值是单选、多选还是评分题的汇总？ | 多选时百分比之和可能超过 100%，单选时则互斥；题型不同解读方式不同 |
| V5 | **"导入可靠性"的操作定义**：指什么场景的导入？（文件导入 / 数据迁移 / 第三方集成？） | 概念定义不明确会导致不同受访者理解不一致，数据可比性存疑 |
| V6 | **统计显著性与置信区间**：样本量 120 的调查，各项百分比的误差范围是多少？ | 小样本下百分比波动可能较大，31% 与 46% 的差异是否显著需统计检验 |
| V7 | **分组 × 核心发现的交叉分析**：不同团队规模的分组在三项发现上是否有差异？ | 目前仅有边际分布，无法判断中小团队与大团队的需求差异 |
| V8 | **数据收集的具体方式**：在线问卷 / 面对面访谈 / 电话调查？ | 不同调查方式的回答偏差模式不同 |

## 六、执行阻断说明（按 SKILL.md 规则记录）

### 阻断 1：阶段 0.2 — gh CLI 未登录

- **SKILL.md 原文规则**：阶段 0.2 检查 `gh auth status`，"❌ 未登录 → 提示 `gh auth login`，终止"。
- **实际状态**：`gh` 已安装（v2.4.0），但执行 `gh auth status` 返回 "You are not logged into any GitHub hosts"。
- **影响**：recon 阶段需要 `gh api` 拉取源码片段，capture 阶段需要 `gh API` 拉取文件内容。这两个阶段无法执行。
- **处理**：按规则终止全流程，不假装执行了 scan / recon / capture。

### 阻断 2：任务类型不匹配 — Skill 自身的"不适合"判定

- **SKILL.md 原文规则**：description 字段明确标注"不适合：② 写文章/出 PRD（用 writing-assistant / prd-doc-writer）"。
- **实际任务**：基于 `market_research.md` 完成结构化成稿，本质为写作任务，非生态扫描任务。
- **影响**：Skill 的核心流程（scan 多渠道扫信源 → recon 真物侦察 → capture 抓截图/源码 → embed 输出 HTML）与本任务无对应操作对象。
- **处理**：不强行套用全流程，仅迁移 Skill 的可复用原则（层级标签、信源分级、反编造、反过度工程化）。

### 阻断 3：反向信号 4 — "真物"难以界定

- **workflow-anti-patterns.md 原文规则**：反向信号 4 — "新东西的'真物'难以界定（如抽象概念/非工具类）→ recon 阶段会失锚，应该用 long-research 而非这个"。
- **实际对象**：输入为"轻量协作软件市场小样本研究"，属于市场调研数据，非具体工具/产品/生态。没有 GitHub repo、没有产品落地页、没有截图目录、没有商店页——recon-heuristics.md 定义的 7 种"真物栖息地"均无对应对象。
- **影响**：recon 阶段完全失锚，capture 阶段无物可抓。
- **处理**：将源文件本身（`market_research.md` 的原文数据）视为唯一"真物"，以"真物优先"原则指导事实层的逐字引用。

## 七、迁移自 Skill 的核心原则（实际影响成稿的规则）

以下原则来自 `case-radar` Skill 的文件，虽未执行全流程，但直接影响了本文档的结构与内容：

1. **层级标签系统**（来源：`reference/html-template-spec.md` 第 3 节）—— Skill 默认 3 层标签（事实层 / AI 推测层 / 你的判断区），本文档将其映射为【事实】/【推断】/【待核实】三层，是成稿的核心结构。
2. **信源分级 + 反编造**（来源：`SKILL.md` 核心原则第 2 条）—— Skill 要求"一手源 / 二手优质 / 三手中文"分级并砍掉 SEO 垃圾。本文档将 `market_research.md` 原文视为唯一一手源，事实层逐条标注出处，不引入任何外部数据。
3. **真物优先**（来源：`SKILL.md` 核心原则第 1 条 + `reference/recon-heuristics.md` 元规则）—— Skill 强调"菜单一文不值，菜才是真东西"，"能不能让人 3 秒内 grok"。本文档将源文件的原始数据表视为"真物"，直接呈现而非用文字描述替代。
4. **反过度工程化**（来源：`reference/workflow-anti-patterns.md` + `SKILL.md` 核心原则第 6 条）—— Skill 警告"建工具不做事"陷阱和"AI 让自己显得完成度高的装饰层"。本文档砍掉了与核心信息无关的结构层（如生态全景、分组 grid），只保留事实/推断/待核实三层。
5. **装饰图比无图更糟**（来源：`SKILL.md` 阶段 3.4）—— Skill 明确"截不到真物的案例不进精读单，不要硬塞装饰图"。本文档对应原则：没有的数据不编造，缺失的信息放入待核实层而非用推测填充。
