## 3. 约束与冲突

本次审计至少覆盖以下三种约束/冲突，并说明关键取舍：

### 冲突一：Skill 能力域与任务类型错配

- **事实**：`protocol-reverse` Skill 适用于自定义二进制协议、Protobuf/gRPC、WebSocket 帧、PCAP 流量还原（见 SKILL.md "适用场景"）。其工作流 Phase 1–4 假设输入为 PCAP/二进制样本，产出为帧布局、消息字典、解码脚本。
- **实际输入**：`incident_log.csv` 是文本型结构化安全日志（字段：timestamp / system / severity / event / user / source_ip），不含任何二进制协议帧、PCAP 或序列化载荷。
- **SKILL.md 路由规则**："确认任务是否为协议/流量/序列化格式逆向（非纯 Web 参数签名 → 转 `js-reverse/`）"。按此规则，本任务不属于协议逆向，应路由至安全日志分析/事件响应方向。
- **取舍**：用户明确指定使用 `protocol-reverse` Skill，故不切换 Skill，但**不编造不存在的协议帧、hex 摘录或解码脚本**。将 SKILL.md 中可迁移的规则（授权边界、禁止 ACT、证据脱敏、自检清单）应用于日志分析，Phase 1–4 的协议特定产物标记为"不适用"。

### 冲突二：授权文件缺失 vs. 禁止 ACT 规则

- **事实**：SKILL.md 要求读取 `precedent-reverse.md` 确认授权，且"auth 未 granted 禁止对目标 ACT"。该文件缺失，无法取得授权确认。
- **取舍**：采取**最保守解释**——视为未授权，全程不执行任何主动操作（不连接 IP、不重放令牌、不探测端口）。这恰好满足业务任务"禁止实施破坏性操作"的硬约束。复测清单中所有需要主动验证的项均标注"需另行授权后方可执行"。

### 冲突三：日志数据质量缺陷 vs. 分析完整性

- **事实**：第 6 条记录 `malformed_record` 的 severity、user、source_ip 字段均为空；文件扩展名为 `.csv` 但实际使用 Markdown 表格（`|` 分隔）格式，首行还有一个独立的 `csv` 标记行。
- **取舍**：不丢弃异常记录，而是将其作为**日志完整性事件**单独分析（可能是日志管道故障，也可能是攻击者篡改日志以掩盖痕迹）。在风险分级中给予"待确认"等级，并在复测清单中加入日志管道校验项。

## 5. 事件关联分析

### 5.1 攻击链 A：令牌滥用 → 数据外泄（IP 203.0.113.8）

**关联证据**：
- 记录 #4（09:04:02）与 #5（09:07:30）源 IP 均为 `203.0.113.8`。
- #4 中 `service-a` 的令牌出现 `token_scope_mismatch`——服务令牌被用于超出其授权范围的操作。
- 仅 3 分 28 秒后，同一 IP 触发 `db` 系统的 `unexpected_export`，用户字段为 `unknown`（未关联到合法身份）。
- **合理推断**：攻击者利用 scope 配置缺陷或令牌窃取，使 `service-a` 令牌获得了超出预期的数据库访问权限，进而执行未授权数据导出。`unknown` 用户表明操作未经过正常身份认证流程，或使用了匿名/伪造身份。

**置信度**：中高（IP 关联 + 时间邻近 + 权限升级逻辑链完整，但缺少 API 网关与数据库审计的详细载荷以确认因果）。

### 5.2 攻击链 B：管理员暴力破解（IP 198.51.100.23）

**关联证据**：
- 记录 #2、#3 均为 `admin` 账号登录失败，源 IP 相同，间隔仅 4 秒。
- 目标为高权限 `admin` 账号，属于精准攻击而非随机扫描。
- 仅 2 次尝试即停止，可能是：(a) 攻击者切换到其他手段（如令牌滥用，见攻击链 A）；(b) 被 WAF/限流拦截；(c) 侦察性试探。

**置信度**：中（样本量小，无法判断是否为更大规模爆破的一部分；需结合更长时间窗口的日志）。

### 5.3 事件 C：日志完整性异常

**关联证据**：
- 记录 #6 `malformed_record` 出现在攻击链 A 之后 1 分 30 秒，severity/user/source_ip 全部为空。
- 可能原因：(a) 攻击者尝试注入/篡改日志以掩盖操作痕迹；(b) 日志采集管道在高负载下丢字段；(c) 上游系统格式变更未同步。
- 由于出现在攻击窗口内，**不能排除人为因素**，需优先排查。

### 5.4 基线事件：alice 登录

- 记录 #1 `alice` 从 `192.0.2.10` 登录成功，时间早于所有异常事件。
- 当前无证据表明 alice 账号被入侵，但应核查：alice 是否拥有 `service-a` 相关权限？`192.0.2.10` 是否为可信内网段？作为潜在跳板排查。

## 8. 修复建议

### 8.1 紧急处置（针对 R1/R2，24 小时内）

1. **立即吊销 `service-a` 当前令牌**，重新签发并严格限定 scope（最小权限原则）。
2. **冻结 `203.0.113.8` 的访问权限**（在 WAF/安全组/API 网关层封禁），直至完成调查。
3. **核查数据库导出记录**：确认 `unexpected_export` 导出了哪些表/数据量/目标存储位置，评估数据泄露范围。
4. **检查 `service-a` 的令牌 scope 配置**：确认是否存在过度授权（如服务令牌意外拥有 db 读写权限），修复权限矩阵。

### 8.2 短期加固（针对 R3/R4，1 周内）

5. **启用管理员账号登录限流与告警**：同一 IP 连续失败 ≥3 次自动锁定并触发告警；对 `admin` 等特权账号强制 MFA。
6. **封禁 `198.51.100.23`** 并纳入威胁情报黑名单；排查该 IP 是否有其他历史活动。
7. **修复日志采集管道**：排查 `malformed_record` 根因（是管道 bug 还是人为注入）；对日志写入增加完整性校验（如哈希链、仅追加存储）。
8. **扩展日志保留窗口**：当前样本仅 9 分钟，无法判断攻击是否有前期侦察或后续横向移动，建议拉取前后 24 小时日志复查。

### 8.3 长期改进（1 个月内）

9. **建立服务间零信任访问控制**：服务令牌默认无跨系统权限，需显式申请并审批。
10. **部署数据库活动监控（DAM）**：对 `unexpected_export` 类操作实现实时拦截（而非仅事后告警）。
11. **完善日志规范**：统一 `.csv` 实际格式（当前为 Markdown 表格），强制非空字段校验，避免畸形记录进入分析管道。
12. **制定事件响应 Runbook**：针对"令牌越权 + 数据外泄"组合场景，明确冻结、取证、通知、合规上报的流程与责任人。

### 10.3 风险

- **误报风险**：`token_scope_mismatch` 可能是合法的 scope 配置变更过渡期现象，`unexpected_export` 可能是运维人员的临时操作（但 `unknown` 用户不支持此解释）。建议在处置前先与 `service-a` 负责人确认。

- **合规风险**：若 `unexpected_export` 确认为数据外泄，可能触发数据安全法/个人信息保护法下的通知义务，需法务与合规团队介入。
