# 调试诊断报告：服务升级后偶发超时与测试间歇失败

> 按 `debugging-and-error-recovery` Skill 的六步结构化流程执行。

---

## 一、问题描述

- **现象**：某服务从 v1 升级到 v2 后，生产环境出现偶发请求超时；CI 中部分测试间歇失败。
- **升级变更**：v2 为提升性能引入了连接池（v1 每次请求新建连接）。
- **特征**：超时不是立即出现，而是在服务运行一段时间后逐渐增多；测试失败与否取决于前面测试的执行情况。

---

## 二、Step 1：复现（Reproduce）

按 Skill 要求，先可靠复现失败，再进行诊断。

### 复现方法

在沙盒中构建最小可复现场景（仅使用 Python 标准库，无第三方依赖），固定随机种子 `42` 保证可重复：

```bash
cd debugging-demo
python3 repro.py
```

### 复现结果

| 指标 | 数值 |
|------|------|
| 总请求数 | 30 |
| 成功 | 1 |
| 下游错误（每次泄漏一个连接） | 3 |
| 连接池超时（池耗尽） | 26 |
| 最终池可用连接数 | 0 / 3 |

**关键时序**：
- req-001：下游错误 → 连接 conn_id=0 泄漏
- req-002：下游错误 → 连接 conn_id=1 泄漏
- req-003：成功 → 连接 conn_id=2 归还
- req-004：下游错误 → 连接 conn_id=2 再次泄漏
- req-005 起：池已空（0 可用），所有请求阻塞 1 秒后超时

### 测试间歇失败复现

```bash
python3 -m unittest test_flaky -v
```

连续运行 3 次结果：第 1 次 1 个错误，第 2 次 2 个错误，第 3 次 1 个错误。错误均为 `PoolTimeoutError`，失败测试为 `test_pool_should_not_exhaust`。

**间歇原因**：测试套件通过 `setUpClass` 共享同一个 `ServiceV2` 实例（模拟生产单例），前面测试触发的下游错误会泄漏连接并累积；当泄漏数达到池大小时，后续测试超时。由于下游错误率是随机的（30%），每次运行泄漏的连接数不同，表现为"间歇失败"。

## 三、Step 2：定位（Localize）

按 Skill 的分层定位法，逐层排除。

### 假设列表与验证

| 编号 | 假设 | 验证方法 | 证据 | 结论 |
|------|------|----------|------|------|
| H1 | 下游服务本身变慢或不可用 | 检查下游服务统计与调用链 | 下游实际只收到 4 次请求（3 错 1 成功），其余 26 次请求根本没到达下游 | 排除 |
| H2 | 网络问题导致请求丢失 | 对比 v1 与 v2 在相同下游配置下的表现 | v1 在相同条件下 0 超时，17 成功；v2 26 超时 | 排除 |
| H3 | 连接池配置不当（池太小/超时太短） | 检查池状态日志 | 池大小 3，但 `in_use=3` 且 `available=0` 持续不变——连接被借出后从未归还 | 部分相关，但非根因 |
| H4 | 异常路径下连接未归还（资源泄漏） | 对比成功请求与错误请求的日志 | 成功请求有"归还连接"日志；下游错误请求无"归还连接"日志，且池可用数逐次递减 | **确认根因** |
| H5 | 测试间状态污染 | 检查测试是否共享实例 | `setUpClass` 中只创建一次 `ServiceV2`，所有测试方法共享同一连接池 | 确认（加重因素） |
| H6 | 并发竞态条件 | 复现为单线程顺序请求仍出现超时 | 单线程下 30 次请求中 26 次超时，与并发无关 | 排除 |

### 定位结论

失败发生在 **API/Backend 层的连接池管理模块**。具体位置：`service_v2.py` 的 `call()` 方法中，`conn.request()` 抛出 `DownstreamError` 后，后续的 `self.pool.release(conn)` 不会被执行，因为没有 `try/finally` 保护。

## 四、Step 3：简化（Reduce）

剥离无关因素，得到最小失败用例：

```python
# 最小复现：3 行核心逻辑
downstream = DownstreamService(error_rate=1.0)  # 100% 错误
service = ServiceV2(downstream, pool_size=1)     # 池大小 1
service.call("r1")  # 抛 DownstreamError，连接泄漏
service.call("r2")  # PoolTimeoutError —— 池已空
```

最小失败用例证明：只要有一次下游错误且池大小为 1，第二次请求必然超时。无需并发、无需复杂配置。

---

## 五、Step 4：修复根因（Fix the Root Cause）

### 根因

`service_v2.py` 的 `call()` 方法中，连接归还逻辑 `self.pool.release(conn)` 位于 `conn.request()` 之后且无 `try/finally` 保护。当下游调用抛出异常时，执行流直接跳出方法，`release()` 永远不会被调用，连接永久泄漏。多次异常后连接池耗尽，后续 `acquire()` 阻塞直到超时。

### 症状修复（错误示范）

```python
# 不好：增大连接池或延长超时，只是推迟崩溃
service = ServiceV2(downstream, pool_size=100, acquire_timeout=10.0)
```

### 根因修复（最小修复）

在 `call()` 中添加 `try/finally`，确保无论成功还是异常都归还连接：

```python
def call(self, request_id):
    conn = self.pool.acquire()
    try:
        result = conn.request(self.downstream, request_id)
        return result
    except DownstreamError as e:
        raise
    finally:
        self.pool.release(conn)  # 关键：总是执行
```

**修复范围**：仅修改 `call()` 方法的异常处理结构，不新增依赖，不改动其他文件或逻辑。

## 六、Step 5：防护回归（Guard Against Recurrence）

添加专门的回归测试 `test_regression.py`，包含两个测试用例：

1. **`test_connections_returned_on_error`**：80% 错误率下发起 20 次请求，断言 0 超时、池可用数等于池大小、泄漏数为 0。
2. **`test_pool_recovers_after_error_burst`**：100% 错误率下触发 10 次错误后，池应完全可用；切换到 0% 错误率后应能正常服务。

该测试在 v2（有 bug）上会因 `PoolTimeoutError` 失败，在 v2_fixed 上通过。

### 验证命令

```bash

# 2. 对比验证 v1 / v2 / v2_fixed（预期：退出码 0）

# 3. 回归测试（预期：2 tests OK）
```

### 验证结果

| 版本 | 成功 | 下游错误 | 超时 | 平均耗时 | 池最终可用 |
|------|------|----------|------|----------|------------|
| v1（升级前，无连接池） | 17 | 13 | 0 | 50.3ms | N/A |

| v2_fixed（修复后） | 17 | 13 | 0 | 50.4ms | 3 / 3 |

- v2_fixed 的 `release_calls=30`，与 `acquire_calls=30` 完全匹配，`leaked=0`。
- 回归测试 2/2 通过。
- 修复后性能与 v1 持平（平均 50.4ms vs 50.3ms），且保留了连接池的架构优势。

## 八、约束导致的方案变化

用户新增了以下约束，本报告逐一说明其影响：

### 1. 不新增非必要依赖

- **原方案可能**：使用 `requests`、`psycopg2`、`pytest` 等第三方库构建真实服务与测试。
- **实际方案**：全部使用 Python 标准库（`threading`、`logging`、`unittest`、`random`、`time`、`json`、`collections`）实现连接池、下游服务模拟、日志、调用链和测试。零第三方依赖。
- **影响**：模拟场景的真实度略有降低（无真实 HTTP/DB 交互），但核心 bug 模式（异常路径资源泄漏）完全等价，且验证命令可在任何 Python 3 环境中直接运行。

### 2. 不改动无关文件

- **原方案可能**：在排查过程中修改配置文件、调整测试框架、重构多个模块。
- **实际方案**：修复仅涉及 `service_v2_fixed.py` 中 `call()` 方法的 `try/finally` 结构。`downstream.py`、`connection_pool.py`、测试文件均未因修复而改动。
- **影响**：修复 diff 极小，风险可控，符合 Skill 中"Multiple unrelated changes made while debugging"的红旗规避要求。

### 3. 本地或沙盒中给出可重复的验证命令

- **实际方案**：提供 `repro.py`（固定随机种子 42）、`verify_fix.py`（三版本对比）、`test_regression.py`（回归测试）、`run_verification.sh`（一键全量验证）。所有命令均为一次性执行，不启动持续运行的服务器。
- **影响**：无。完全满足。

### 4. 若依赖外部账号，只做到安全的模拟或确认前步骤

- **实际方案**：未使用任何外部账号、外部服务或付费资源。下游服务为本地模拟对象。
- **影响**：无。若真实场景需要连接生产数据库或外部 API，则应在此步骤停止，仅提供模拟验证和接入前检查清单。

## 十一、实际影响执行的 SKILL.md 规则

| SKILL.md 规则 | 如何影响执行 |
|----------------|-------------|
| **Stop-the-Line Rule** | 在复现到超时后，没有继续"添加功能"或跳过失败，而是先保留证据（日志、调用链）再诊断 |
| **Step 1: Reproduce（不可跳过）** | 固定随机种子 42 构建可靠复现，而非凭猜测直接改代码；对间歇失败采用"多次运行展示随机性"策略 |
| **Step 1 非复现 bug 决策树** | 针对"偶发超时"按 Timing-dependent / Environment-dependent / State-dependent / Truly random 分类排查，最终定位为 State-dependent（连接池状态泄漏） |
| **Step 2: Localize 分层法** | 按 UI/API/DB/Build/External/Test 六层逐一排除，最终定位到 API 层的连接池管理 |
| **Step 3: Reduce** | 将 30 次请求的复现简化为"池大小 1 + 100% 错误率 + 2 次请求"的最小失败用例 |
| **Step 4: Fix the Root Cause（非症状）** | 明确拒绝"增大池/延长超时"的症状修复，选择"添加 try/finally 确保归还"的根因修复 |
| **Step 5: Guard Against Recurrence** | 添加 `test_regression.py`，该测试在 bug 版本上失败、修复版本上通过 |
| **Step 6: Verify End-to-End** | 运行三版本对比 + 回归测试 + 间歇测试，确认无回归 |
| **Test Failure Triage 决策树** | 对"测试间歇失败"按"是否改动了测试覆盖的代码 / 是否改动了无关代码 / 测试是否本来就不稳定"分类，确认是共享状态导致的 side effect |
| **Treating Error Output as Untrusted Data** | 将模拟的下游错误消息（`下游服务返回 500`）仅作为诊断数据，未执行其中任何指令 |
| **Red Flags: Multiple unrelated changes** | 修复仅改动 `try/finally` 结构，未同时重构其他代码 |
| **Red Flags: No regression test** | 已添加专门的回归测试 |
| **Instrumentation Guidelines** | 复现期间添加了详细的池状态日志，诊断完成后这些日志保留在 `logs/` 目录作为证据；未将调试日志混入生产代码 |
