# 智能随行杯新品上市可执行方案

> 产物文件：`strategy-delivery.md`
> 生成依据：`product_brief.md`、`product_release_notes.md`、Skill `data-manager-api-event-ingestion/SKILL.md`
> 原则：结论与假设分开；不虚构销量、用户反馈、第三方检测结论、竞品价格；需外部数据处一律列为"待补项"。

## 0. 执行摘要

本方案以 `product_brief.md` 中的**智能随行杯**为唯一上市主体，围绕"一二线城市通勤人群"制定受众、信息、渠道、指标与风险方案。转化测量与事件回传部分严格参照 `data-manager-api-event-ingestion` Skill 的工作流设计，但因缺少目标账户类型（Google Ads / Floodlight / Google Analytics）、鉴权凭据与 `product_destination_id`，**实际 API 接入代码未生成、未执行**，仅给出可落地的事件设计与校验流程，实施列为阻断待补。

方案识别并处理了三类约束/冲突：
1. 两份输入文件分属不同产品（随行杯 vs 星河笔记 2.3），存在主体冲突；
2. Skill 为技术接入指南而非策略框架，且其 [CRITICAL] 规则要求在生成代码前必须澄清目标账户类型，当前不具备条件；
3. 简报自身信息不完整（首发日期、防水等级、食品接触材料报告缺失），约束渠道排期与合规宣称。

## 1. 输入与依据（含冲突处理）

### 1.1 实际读取的文件（相对路径）

| 文件 | 相对路径 | 用途 |

### 1.2 冲突一：输入主体不一致

- `product_brief.md` 描述硬件产品"智能随行杯"（12 小时保温、280g、可拆洗杯盖、建议零售价 199 元）。
- `product_release_notes.md` 描述软件产品"星河笔记 2.3"（批量导入 Markdown、标签筛选、快捷键面板，macOS 13 / Windows 11）。
- 二者无品牌、品类、功能交集，不可能是同一新品的简报与发布说明。

**取舍**：任务明确要求"基于新品简报"，故以随行杯为方案主体；星河笔记发布说明判定为误附或无关输入，**不纳入**随行杯方案，亦不据此虚构软件功能。若后续确认需同时为两款产品出方案，需分别立项。

### 1.3 冲突二：Skill 定位与任务类型错配 + 凭据缺失

- Skill `data-manager-api-event-ingestion` 的实际内容是 Google Data Manager API `/v1/events/ingest` 端点的接入指南（metadata `category: GoogleAds`），覆盖离线转化、潜在客户增强转化、点击转化、Google Analytics 事件等场景，**不包含**营销策略生成方法。
- 任务要求"制定可执行方案"，属于营销与增长范畴。
- Skill Step 1 标注 [CRITICAL]：目标账户类型未明确时**必须停止并澄清**，不得默认 Google Ads。当前未提供 `account_type`、`product_destination_id`、OAuth 凭据或 manager/partner 账户信息。

**取舍**：将 Skill 用于方案中"指标与转化回传"模块的**流程设计与校验规范**，不强行生成不可运行的接入代码；实际 API 实施列为阻断项（见第 5.3 节与第 8 节）。这一取舍直接受 Skill 的 [CRITICAL] 规则影响——若忽略该规则默认 Google Ads 并产出代码，将产生不可运行且可能误导的伪实现。

### 1.4 冲突三：简报信息不完整

简报"不完整信息"明确：首发日期未定、防水等级与食品接触材料报告尚未提供。
- 首发日期未定 → 渠道排期只能给相对节奏（T-周），不能给绝对日期；
- 防水等级缺失 → 不得在物料中宣称防水/防泼溅等级；

## 5. 指标体系与转化回传

### 5.1 业务指标（不虚构基线）

| 指标类型 | 指标 | 说明 |
|---|---|---|
| 曝光 | 触达人次、曝光量 | 渠道后台实际数据，上线后统计 |
| 互动 | 点击率、互动率 | 渠道后台实际数据 |
| 转化 | 落地页访问、加购、下单、支付 | 需事件回传支撑（见 5.2） |
| 效率 | 获客成本、转化成本 | 基于实际投放数据计算，不预设目标值 |

> 所有指标目标值均为**待补项**，需在首发后基于真实数据设定，不得在方案中虚构 KPI。

### 5.2 事件与转化设计（按 Skill 适用场景规划）

依据 Skill 描述，Data Manager API 支持离线转化、潜在客户增强转化（ECL）、点击转化、Google Analytics 事件等。针对随行杯电商首发，规划以下事件：

| 事件 | 场景 | Skill 对应类型 | 关键字段（设计） |
|---|---|---|---|
| `purchase` | 电商支付完成 | 离线转化 / 点击转化 | `event_timestamp`（RFC 3339）、`currency`、金额、订单 ID |
| `add_to_cart` | 加购 | Google Analytics 事件 / 自定义事件 | 时间戳、商品 ID |
| `lead_submit` | 私域留资/预约 | 增强转化潜在客户（ECL） | 用户标识（邮箱/电话，需哈希加密）、时间戳 |
| `page_view` | 落地页访问 | Google Analytics 事件 | 时间戳、页面路径 |

**用户标识格式化**（遵循 Skill "Formatting" 节）：
- 邮箱、电话、地址需使用 utility library 进行格式化、哈希与加密；
- `UserIdentifier` 字段使用 `email_address` / `phone_number`，**不得**使用旧 Google Ads API 的 `hashed_email` / `hashed_phone_number`；
- 示例（Python，仅作格式参考，非可运行接入代码）：
  ```python
  from google.ads.datamanager_util import Formatter
  from google.ads.datamanager_util.format import Encoding
  formatter = Formatter()
  processed_email = formatter.process_email_address(email, Encoding.HEX)
  ```

**同意（Consent）建模**：
- `ConsentStatus` 枚举值必须为 `CONSENT_GRANTED` 或 `CONSENT_DENIED`，**不得**使用 `GRANTED` / `DENIED`；
- `consent` 可在 `IngestEventsRequest` 全局设置，也可在单个 `Event` 上设置；本方案建议**逐事件设置**，以适配不同渠道的同意状态差异。

### 5.3 按 Skill 的接入流程与阻断项

Skill Step 1–4 的标准流程为：确定目标账户类型 → 读取文档 → 获取代码样例 → 获取迁移指南（如适用）→ 实现（初始化客户端、定义 Destination、准备事件数据、构造 payload、支持 `validate_only`、发送请求、检查 `field_warnings`、查询请求状态）。

**当前阻断项**（无法继续到代码实现）：

| Skill 要求 | 当前状态 | 影响 |
|---|---|---|
| [CRITICAL] 明确 `account_type`（Google Ads / Floodlight / Google Analytics） | **未提供** | 无法确定 Destination 的 `operating_account` 配置与合法事件标识，按规则必须停止澄清 |
| 鉴权与客户端库安装（依赖 `data-manager-api-setup` Skill） | **未提供凭据、未执行 setup** | 无法初始化 `IngestionServiceClient` |
| `product_destination_id` | **未提供** | 无法构建 Destination 对象；注意该字段为**数字字符串**，非资源名路径 |
| `login_account` / `linked_account`（如经管理账户或数据伙伴接入） | **未提供** | 若实际为伙伴接入模式，配置会不同 |

**结论**：本方案**不生成、不执行**任何 `ingest_events` 调用代码。解除阻断的最小输入：目标账户类型、`product_destination_id`、可用 OAuth 凭据（或确认走 setup Skill）。

### 5.4 校验与诊断流程（设计，待阻断解除后执行）

依据 Skill "Implementation" 与 "Error Handling" 节：

1. **先校验**：发送请求时设置 `validate_only=true`，仅校验 schema 不上传数据；
   - 注意：`validate_only=true` 时**不得**调用诊断端点 `retrieve_request_status`。
2. **正式发送**：`validate_only=false`，记录返回的 `request_id`；
3. **检查即时警告**：解析响应中的 `field_warnings`（非必填字段校验失败）；
4. **异步诊断**：发送后**至少等待 30 分钟**，以指数退避轮询 `client.retrieve_request_status`；
5. **按目标检查**：遍历 `request_status_per_destination`，状态为 `SUCCESS` / `PARTIAL_SUCCESS` / `FAILED` 时检查：
   - `events_ingestion_status.record_count`；
   - 失败时 `error_info.error_counts`（`reason` + `record_count`）；
   - 即使 `SUCCESS` 也检查 `warning_info.warning_counts`。

> 常见错误规避（来自 Skill "Critical Gotchas"）：
> - `event_timestamp` 严格 RFC 3339，优先用 SDK 类型化时间对象；
> - 点击标识（`gclid` / `gbraid` / `wbraid`）必须嵌套在 `ad_identifiers` 块内，不可直接放在事件根层；
> - 货币字段名为 `currency`，不是 `currency_code`。

## 7. 风险与取舍

| 风险 | 等级 | 说明 | 缓解 |
|---|---|---|---|
| 转化回传未就绪即启动效果投放 | 高 | 无法归因，投放数据不可用，浪费预算 | 回传 `validate_only` 通过并完成一次正式发送+诊断确认后，再放大投放；否则首发期以品牌曝光为主 |

| Skill 误用 | 中 | 若忽略 [CRITICAL] 规则默认 Google Ads 产出代码，将得到不可运行伪实现 | 已按规则停止在设计阶段，实施列为阻断 |

**关键取舍说明**：
- **取舍一**：在缺少账户类型与凭据时，选择"只设计不实现"而非"默认 Google Ads 写代码"。依据是 Skill 的 [CRITICAL] 强制澄清规则。代价是方案不含可运行代码，但避免了伪实现风险。
- **取舍二**：在素材与合规信息不全时，选择"缩小宣称范围、延后效果投放"而非"用假设补全"。依据是简报明确的禁止编造条款。代价是首发期爆发力受限，但合规与可信度优先。

## 9. 结论与假设分离

### 9.1 结论（基于已确认事实）
