## 2. 边界与失败场景分析

> 本节对 edge_cases.csv 中的缺失、重复、异常、不安全输入逐一识别。每条标注证据来源与处理方式。

### 2.1 重复记录

**证据**：行 2 与行 3 的 `record_id`、`status`、`value`、`notes` 四个字段完全相同（均为 `2, ok, 120, 重复记录`）。`[事实]`

**影响**：若直接按行统计，record_id=2 的 value=120 会被计入两次，导致基于行数的聚合（如均值、计数）失真。

**处理（已完成）**：去重后保留 1 条 record_id=2 记录。去重后有效行数从 6 降至 5。

### 2.2 缺失记录

**证据**：行 4（record_id=3）的 `status` 和 `value` 字段均为空，`notes` 为 `-`。`[事实]`

**影响**：该记录无法参与任何基于 status 或 value 的统计分析。notes="-" 未提供可替代的有效值。

**处理（已完成）**：标记为"数据缺失"，不参与数值聚合。不编造 status 或 value。

**降级方案**：若后续需补齐，应回到原始数据源确认 record_id=3 的实际采集结果；在未确认前，该记录仅作为"存在但无效"的占位。

### 2.3 异常值

**证据**：行 5（record_id=4）的 `status=error`，`value=-999`，`notes=异常负值`。`[事实]`

**影响**：
- status=error 本身已标记该记录为失败状态。
- value=-999 为负值，与其他记录的正值（120）量级和符号均不一致；结合 notes="异常负值"，可判断该值为错误占位符而非有效测量值。`[推断]`

**处理（已完成）**：因 status=error 且 value 为异常负值，该记录不参与有效数值统计。不将 -999 当作真实数据点。

**降级方案**：若需了解 record_id=4 的真实值，需查原始采集日志确认 error 原因；在未确认前保留为"错误记录"。

### 2.4 不安全输入（公式注入）

**证据**：行 6（record_id=5）的 `value` 字段为 `=HYPERLINK("https://example.invalid","do not execute")`，`notes=公式注入测试文本`。`[事实]`

**风险分析**：
- 该值以 `=` 开头，是电子表格公式语法。若将此 CSV 直接导入 Excel / Google Sheets / 飞书表格且未做文本转义，公式可能被执行，触发 `HYPERLINK` 跳转至 `https://example.invalid`。`[推断]`
- `example.invalid` 为保留测试域名（RFC 2606 定义的 .invalid TLD），实际不可解析，因此本次跳转目标无实际危害。`[推断]`
- notes 字段明确标注"公式注入测试文本"，说明该条为有意构造的安全测试用例。`[事实]`

**处理（已完成）**：
- 不将该 value 作为数值处理。
- 在任何下游表格导入场景中，必须将该字段作为纯文本处理（前置单引号 `'` 或设置单元格格式为文本），禁止公式执行。
- 本文档中以代码块形式展示该值，避免被渲染为可点击链接。
