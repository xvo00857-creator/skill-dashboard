### 3.2 风险发现

#### 风险 INC-01：令牌越权后数据外泄攻击链（严重 / Critical）

- **证据**：
  - 09:04:02 — IP `203.0.113.8`，用户 `service-a`，API 系统触发 `token_scope_mismatch`（high）。表示服务账户使用了超出授权范围的令牌。
  - 09:07:30 — 同一 IP `203.0.113.8`，用户变为 `unknown`，数据库系统触发 `unexpected_export`（critical）。表示发生了未授权的数据导出。
  - 两事件间隔 **3 分 28 秒**，源 IP 完全一致，系统从 api 横向移动到 db，用户身份从可识别的 `service-a` 变为 `unknown`。
- **攻击链推断**：攻击者可能利用 `service-a` 的令牌进行范围越权操作（token_scope_mismatch），随后在同一 IP 上以未知身份执行数据库导出（unexpected_export），符合"令牌滥用 → 权限提升/横向移动 → 数据外泄"的攻击路径。
- **影响**：敏感数据可能已被外泄；`service-a` 服务账户可能已被攻陷。
- **修复建议**：
  1. 立即吊销 `service-a` 的所有活跃令牌，强制轮换密钥。
  2. 核查 `203.0.113.8` 在 09:00–09:30 期间的全部网络流量和数据库操作日志。
  3. 确认 `unexpected_export` 导出的数据范围、目标地址和数据量。
  4. 为数据库导出操作增加二次审批和 IP 白名单限制。
  5. 实施令牌范围的最小权限原则，定期审计服务账户的令牌权限。
- **复测方法**：在测试环境中模拟 `service-a` 令牌越权访问数据库导出接口，验证是否被拦截；验证 IP `203.0.113.8`（如为已知恶意 IP）是否在防火墙/IDS 规则中被阻断。

#### 风险 INC-02：admin 账户快速登录失败（中危 / Medium）

- **证据**：
  - 09:03:45 — IP `198.51.100.23`，用户 `admin`，`login_failed`（warning）。
  - 09:03:49 — 同一 IP、同一用户，再次 `login_failed`（warning）。
  - 两次失败间隔仅 **4 秒**，目标为高权限 `admin` 账户。
- **分析**：仅 2 次失败未达常见暴力破解阈值（通常为 5 次/分钟），但快速连续失败 + 管理员账户 = 值得关注的枚举/暴力尝试信号。可能是更大规模攻击的前奏，也可能是脚本化登录的起始。
- **修复建议**：
  1. 对 `admin` 账户启用账户锁定策略（如 5 次失败后锁定 15 分钟）。
  2. 对 `198.51.100.23` 实施速率限制或临时封禁。
  3. 为管理员账户强制启用多因素认证（MFA）。
  4. 检查该 IP 是否在威胁情报库中有不良记录。
- **复测方法**：模拟从 `198.51.100.23` 对 `admin` 进行 5 次快速登录失败，验证账户锁定和 IP 封禁是否生效。

#### 风险 INC-03：畸形日志记录（中危 / Medium）

- **证据**：第 6 行 `2026-08-12T09:09:00Z`，`severity`、`user`、`source_ip` 三个关键字段为空，事件类型为 `malformed_record`。
- **分析**：该记录可能由以下原因产生：(1) 日志采集器解析失败；(2) 攻击者故意注入畸形数据以干扰日志分析或覆盖真实事件；(3) 上游系统发送了不完整的日志。无论原因，关键字段缺失意味着该时间点的安全事件无法被正确关联和分析，存在日志被规避的风险。
- **修复建议**：
  1. 核查 09:09:00 前后 web 系统的原始日志流，确认是否有事件被丢失或篡改。
  2. 在日志采集管道中增加字段完整性校验，对缺失关键字段的记录进行告警而非静默接受。
  3. 实施日志完整性保护（如追加写入、哈希链、远程备份），防止日志篡改。
- **复测方法**：向日志采集端点发送一条缺失 severity/user/source_ip 的测试记录，验证系统是否产生告警并保留原始数据；检查 09:09:00 时间点是否有对应的原始日志条目。

### 4.1 记录概览

| 行号 | record_id | status | value | notes | 问题类型 |
|---|---|---|---|---|---|
| 1 | 1 | ok | 120 | 正常记录 | 无 |
| 2 | 2 | ok | 120 | 重复记录 | 重复 |
| 3 | 2 | ok | 120 | 重复记录 | 重复 |

| 6 | 5 | ok | `=HYPERLINK("https://example.invalid","do not execute")` | 公式注入测试文本 | 公式注入 |

### 4.2 风险发现

#### 风险 EDGE-01：CSV 公式注入（高危 / High）

- **证据**：第 6 行，`record_id=5`，`value` 字段内容为 `=HYPERLINK("https://example.invalid","do not execute")`。该字段以 `=` 开头，是电子表格公式的标准前缀。
- **分析**：当此 CSV 文件在 Microsoft Excel、WPS、LibreOffice Calc 等电子表格软件中打开时，`=HYPERLINK(...)` 会被解析为公式并渲染为可点击链接。虽然 `HYPERLINK` 本身不会自动执行代码，但：
  - 它可以将用户引导至钓鱼网站或恶意下载页面。
  - 若替换为 `=CMD(...)`、`=WEBSERVICE(...)` 或其他可执行函数，可能触发更严重的代码执行。
  - 在配置了自动公式计算的环境中，部分函数可能在打开时自动执行。
  - 这是典型的 **CSV Injection（Formula Injection）** 攻击向量，OWASP 将其列为已知风险。
- **修复建议**：
  1. 在 CSV 导出/生成环节，对以 `=`、`+`、`-`、`@` 开头的单元格值进行转义（在前部添加单引号 `'` 或制表符）。
  2. 在数据入库前对用户输入的 `value` 字段进行公式前缀检测和过滤。
  3. 告知用户不要在不信任的 CSV 文件上启用自动公式计算。
  4. 考虑使用安全的 CSV 库（如 Python `csv` 模块配合自定义转义）而非手动拼接。
- **复测方法**：构造包含 `=HYPERLINK(...)`、`=CMD(...)`、`=1+1` 等公式的测试数据，经过导出管道后检查输出 CSV 中这些值是否被正确转义；用 Excel 打开转义后的文件，验证公式不被执行。

#### 风险 EDGE-02：完全重复记录（中危 / Medium）

- **证据**：第 2 行和第 3 行完全相同，`record_id=2`，`status=ok`，`value=120`，`notes=重复记录`。
- **分析**：重复记录可能导致：(1) 统计指标失真（如计数、求和被放大）；(2) 基于该数据的安全告警阈值计算错误；(3) 数据同步或采集管道存在重复投递问题。虽然 notes 字段已标注"重复记录"，说明这可能是有意的测试数据，但在生产环境中必须去重或标记。
- **修复建议**：
  1. 在数据入库时基于 `record_id`（或复合主键）实施去重约束（如 UPSERT / INSERT OR IGNORE）。
  2. 对数据采集管道增加幂等性设计，确保重复投递不会产生重复记录。
  3. 定期运行数据质量检查，统计重复率并告警。
- **复测方法**：向系统连续提交两条相同 `record_id` 的记录，验证数据库中是否只保留一条（或第二条被标记为重复）；检查数据质量报告中重复率指标是否正确。

#### 风险 EDGE-03：关键字段缺失（中危 / Medium）

- **证据**：第 4 行，`record_id=3`，`status` 和 `value` 字段均为空，`notes` 为 `-`。
- **分析**：`status` 和 `value` 是该数据集的核心分析字段。两者同时缺失意味着该记录无法参与任何基于状态或数值的分析。可能原因：(1) 上游系统未采集到数据；(2) 数据传输中丢失；(3) 记录被部分删除或篡改。
- **修复建议**：
  1. 对 `status` 和 `value` 字段设置非空约束（NOT NULL）或默认值策略。
  2. 在数据采集端增加必填字段校验，拒绝不完整记录入库（或隔离到"待修复"队列）。
  3. 核查 `record_id=3` 对应的上游数据源，确认数据丢失原因。
- **复测方法**：提交一条 `status` 和 `value` 均为空的记录，验证系统是否拒绝或隔离；检查"待修复"队列中是否能看到该记录。

#### 风险 EDGE-04：异常负值（低危 / Low）

- **证据**：第 5 行，`record_id=4`，`status=error`，`value=-999`，`notes=异常负值`。
- **分析**：`-999` 是常见的哨兵值（sentinel value），用于表示缺失、错误或不适用。但如果该字段的业务语义应为非负数（如计数、时长、金额），则 `-999` 可能：(1) 被误当作真实数值参与计算，导致统计偏差；(2) 表示上游系统发生错误但未正确标记。当前 `status=error` 已提供上下文，降低了风险等级，但仍需确保下游分析能正确识别和排除哨兵值。
- **修复建议**：
  1. 明确 `value` 字段的取值范围和哨兵值约定，并在数据字典中文档化。
  2. 在数据分析/可视化环节，对 `status=error` 的记录进行过滤或单独处理。
  3. 考虑使用 `NULL` 而非哨兵值表示缺失/错误，避免数值计算污染。
- **复测方法**：在包含 `-999` 哨兵值的数据集上运行统计计算（均值、总和），验证哨兵值是否被正确排除；检查数据字典中是否有哨兵值说明。
