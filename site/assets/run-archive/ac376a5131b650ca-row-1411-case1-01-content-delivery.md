## 三、推断（基于事实的合理演绎）

> 以下为推断，非研究原文结论。每条均标注所依据的事实编号。

1. **【推断】** 导入可靠性可能是产品差异化的关键切入点——依据：46% 受访者将其列为最关心项（§2.2），在三个发现中占比最高。
2. **【推断】** 自动摘要具备潜在付费转化空间——依据：31% 受访者表示愿意付费（§2.2），但比例不足三分之一，需验证付费强度而非仅付费意愿。
3. **【推断】** 目标用户可能以中小团队为主——依据：10-200 人团队合计 96 人，占样本 80%（§2.3）。
4. **【推断】** 协作工具已有较高使用基础——依据：78% 每周使用（§2.2），说明不是从零教育市场，而是在已有使用习惯中寻找差异化。

## 七、转（落产出）

### 7.1 简单 task：导入可靠性与团队协作场景验证

> 判型：一个版本能交付完 → 简单 task → 一段话 + 3~5 条验收点，标 📋

**task 描述**：
基于 120 人演示数据中"46% 最关心导入可靠性"的发现，设计并执行一轮最小验证：明确"导入可靠性"在目标用户中的具体定义（V2），选取 1-2 个典型团队协作场景做可用性测试，验证导入失败率、用户操作路径和痛点严重程度。此 task 不做产品开发，只做验证——输出验证结论，为是否进入 v1.0 规划提供依据。

**验收点**：
1. "导入可靠性"的定义已明确到具体场景（文件导入 / 数据迁移 / 第三方接入，至少锁定 1 个），不再是模糊概念。
2. 至少完成 1 个团队协作场景的可用性测试，有真实用户反馈记录（非自评）。
3. 输出验证结论：导入可靠性是否确为目标用户的核心痛点（是 / 否 / 需更多样本），结论可追溯到测试记录。
4. 样本代表性偏差已说明（V1 至少部分回答），结论不外推到未覆盖人群。
5. 验证产出已回填到 Issue 池，#1 状态更新为对应结果（可开工 / 继续 pending / 关闭）。

**指路**：此 task 可直接开工（v3），不需要先走 v2 三件套——它是验证类任务，验收点已足够。

### 7.2 复杂 plan（pending）：轻量协作软件 v1.0 产品框架规划 — Stage 1 卡住，待补信息

> 判型：一个版本交付不完 → 复杂 plan → 应走 references/plan-writing.md 七步流程。
> 但 Stage 1 硬门未过：无法用 3 行话回答"现状是什么 / 能拿到什么 / 有哪些硬约束 / 谁会消费"。
> 按 plan-writing.md Stage 1 Step 3，正确产出是"卡住状态说明"，**禁止硬开篇、禁止用"据我理解"凭空补全**。

#### 已收集信息

- **项目背景**：轻量协作软件方向，基于 2026 年 6 月 120 人演示数据（【事实】），当前处于立项前验证阶段，无上层架构基线。
- **现状**：无已有代码、无已有系统、无可运行的原型。能拿到的数据仅限 market_research.md 中的三个百分比和分组数据（【事实】）。
- **目标消费方**：【待核实】V4——不确定是内部团队使用、跨团队协作还是对外客户。
- **硬约束**：【待核实】V6——无已知技术约束、业务约束、组织约束。

#### 还需要补充的 7 个具体问题

1. **V2**：用户说的"导入可靠性"具体指什么？是从其他工具迁移数据？是上传文件时的解析成功率？还是第三方 API 数据接入的稳定性？请给出 1-2 个用户原话场景。
2. **V4**：这个产品第一版打算给谁用？是我们自己团队、公司内其他团队，还是外部客户？使用人数量级是 30 / 300 / 3000？
3. **V1**：120 人样本是怎么选的？是随机抽样、特定渠道招募，还是内部员工？样本偏差有多大？
4. **V5**：目标用户现在用什么工具满足协作需求？最不满的点是什么？有没有已经在考虑切换的？
5. **V3**："自动摘要"用户期望的是哪种摘要？会议录音转文字摘要？长文档一键总结？还是群聊消息精华提取？
6. **V6**：有没有已知的硬约束？比如必须兼容某个现有系统、数据不能出域、上线 deadline、客户量上限？
7. **V7**：31% 愿意付费的用户，期望的价格区间是多少？是按月订阅、按次付费，还是团队席位制？

#### 进 Stage 2 的最低标准

收到上述问题的回答后，要保证能用 3 行话回答：
- 现状是什么（有什么数据 / 系统 / 用户反馈）
- 能拿到什么（可验证的资源、可接触的用户、可获取的数据）
- 有哪些硬约束 + 谁会消费这份计划

在此之前，**不进入 Stage 2（定文档类型）、不搭骨架、不写框架计划正文**。
