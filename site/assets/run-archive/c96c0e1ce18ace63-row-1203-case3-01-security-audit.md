## 四、安全日志分析（incident_log.csv）

### 4.1 事件时间线

| 序号 | 时间 (UTC) | 系统 | 级别 | 事件 | 用户 | 源 IP |
|---|---|---|---|---|---|---|
| 1 | 09:00:12 | web | info | login_success | alice | 192.0.2.10 |
| 2 | 09:03:45 | web | warning | login_failed | admin | 198.51.100.23 |
| 3 | 09:03:49 | web | warning | login_failed | admin | 198.51.100.23 |
| 4 | 09:04:02 | api | high | token_scope_mismatch | service-a | 203.0.113.8 |
| 5 | 09:07:30 | db | critical | unexpected_export | unknown | 203.0.113.8 |
| 6 | 09:09:00 | web | *(空)* | malformed_record | *(空)* | *(空)* |

### 4.2 风险发现

#### 发现 F-01：管理员账号暴力破解尝试（中危）

- **证据**：09:03:45 与 09:03:49，同一 IP `198.51.100.23` 对 `admin` 账号连续两次 `login_failed`，间隔仅 4 秒。
- **分析**：短时间内针对高权限管理员账号的连续失败登录，符合暴力破解/撞库特征。当前窗口仅观测到 2 次，可能为更大规模攻击的片段。
- **风险等级**：**中危** — 目标为管理员账号，但观测样本量有限，未确认是否成功。
- **关联**：源 IP `198.51.100.23` 与后续高危事件 IP 不同，暂视为独立攻击源。

#### 发现 F-02：令牌越权 + 未知身份数据导出链式事件（严重/高危）

- **证据**：
  - 09:04:02，`api` 系统产生 `high` 级别 `token_scope_mismatch`，主体为 `service-a`，源 IP `203.0.113.8`。
  - 09:07:30（3 分 28 秒后），`db` 系统产生 `critical` 级别 `unexpected_export`，用户为 `unknown`，源 IP **同为 `203.0.113.8`**。
- **分析**：同一源 IP 在 API 层出现令牌作用域不匹配后，短时间内在数据库层发生未预期的数据导出，且导出操作的用户身份为 `unknown`（未捕获到有效身份）。这构成一条完整的攻击链假设：**被窃取/滥用的服务令牌 → 越权访问 → 数据外泄**。`unknown` 身份可能意味着令牌未绑定用户主体、身份日志被篡改，或导出操作绕过了认证层。
- **风险等级**：**严重** — 涉及 `critical` 级数据导出事件，存在数据泄露的现实可能，且身份缺失阻碍归因。
- **需进一步调取**：`service-a` 令牌的签发与审计日志、`203.0.113.8` 的全量会话记录、数据库导出的目标地址与数据量。

#### 发现 F-03：畸形日志记录（中低危）

- **证据**：09:09:00 记录 `2026-08-12T09:09:00Z,web,,malformed_record,,`，`severity`、`user`、`source_ip` 三个字段为空。
- **分析**：事件名自描述为 `malformed_record`，且关键字段缺失。可能原因包括：(a) 日志采集管道解析失败；(b) 攻击者尝试日志注入以掩盖痕迹；(c) 应用层异常导致结构化日志损坏。无论何种原因，关键字段缺失会削弱事件响应能力。
- **风险等级**：**中低危** — 单条记录影响有限，但如果是日志注入的前兆，需警惕后续更大规模的日志污染。

## 五、边界与失败场景分析（edge_cases.csv）

### 5.1 发现 E-01：重复记录（低危，数据完整性）

- **证据**：`record_id=2` 出现两次完全相同的行：
  ```
  2,ok,120,重复记录
  2,ok,120,重复记录
  ```
  `sort edge_cases.csv | uniq -d` 确认该行为精确重复。
- **影响**：聚合统计（计数、求和、平均值）会被重复记录扭曲；若 `record_id` 应为主键，则违反唯一性约束。
- **风险等级**：低。

### 5.2 发现 E-02：缺失字段（低危，数据完整性）

- **证据**：`record_id=3` 行为 `3,,,-`，`status` 和 `value` 均为空，`notes` 为占位符 `-`。
- **影响**：下游依赖 `status` 或 `value` 的分析/告警会跳过或误判该记录。
- **风险等级**：低。

### 5.3 发现 E-03：异常负值（低危，数据有效性）

- **证据**：`record_id=4` 行为 `4,error,-999,异常负值`，`value=-999`，`status=error`。
- **分析**：`-999` 是常见的哨兵错误码。若 `value` 字段语义为计数、时长或其他非负量，则负值为非法输入；若为错误码，则不应与正常值混排在同一字段。可能导致除零、图表异常、告警阈值误触发。
- **风险等级**：低。

### 5.4 发现 E-04：CSV 公式注入（高危，CWE-1236）

- **证据**：`record_id=5` 的 `value` 字段内容为：
  ```
  =HYPERLINK("https://example.invalid","do not execute")
  ```
  `notes` 字段标注为"公式注入测试文本"，确认该条为有意构造的注入测试。
- **分析**：当该 CSV 被 Excel、LibreOffice Calc、Google Sheets 等电子表格软件打开时，以 `=` 开头的单元格内容会被识别为公式并执行。`HYPERLINK` 公式可将用户诱导至钓鱼页面；更危险的载荷（如 `=CMD|' /c calc'!A0`、`=IMPORTXML(...)`、动态数据交换 DDE）可导致数据外泄或命令执行。这属于 **CWE-1236：CSV 公式注入**，根因是未对写入 CSV 的不可信数据做公式前缀净化。
- **风险等级**：**高危** — 任何打开该文件的人员均可能受影响，且该条记录证明数据管道缺乏公式注入防护。

## 七、修复建议

### 7.1 针对 F-02（严重）

1. **立即封禁/隔离**：对源 IP `203.0.113.8` 执行临时封禁，吊销 `service-a` 当前令牌并强制轮换。
2. **身份归因**：调取 `service-a` 令牌的签发记录、使用审计，确认 `unexpected_export` 操作的实际认证主体；排查 `unknown` 身份是日志缺失还是认证绕过。
3. **数据泄露评估**：核查数据库导出操作的目标地址、导出数据量与数据分类，判断是否构成实际数据泄露并启动应急响应流程。
4. **令牌治理**：收紧 `service-a` 令牌的作用域（最小权限），为高敏操作启用二次审批与短时令牌。

### 7.2 针对 E-04（高危）

1. **输入净化**：在所有写入 CSV/Excel 的数据管道中，对以 `=`、`+`、`-`、`@` 开头的单元格内容前置单引号 `'` 或制表符，使其被视为纯文本。
2. **下游告警**：在日志采集/ETL 层增加公式注入特征检测规则，命中即告警。
3. **用户教育**：提醒分析人员不要直接双击打开来源不可信的 CSV 文件，优先使用纯文本查看器或禁用公式自动执行的配置。

### 7.3 针对 F-01（中危）

1. 对 `admin` 账号启用登录失败阈值锁定（如 5 次失败锁定 15 分钟）与验证码。
2. 对 `198.51.100.23` 执行速率限制或临时封禁。
3. 排查 `admin` 账号在该时段前后是否有成功登录，确认是否已被攻破。

### 7.4 针对 F-03（中低危）

1. 修复日志采集管道，确保 `severity`、`user`、`source_ip` 为必填字段，缺失时拒绝写入并告警。
2. 排查该条记录是否为日志注入尝试，审计同一时段的原始日志流。

### 7.5 针对 E-01/E-02/E-03（低危）

1. 对 `record_id` 施加唯一约束，写入前去重。
2. 对 `status`、`value` 字段施加非空与值域校验（如 `value` 非负）。
3. 将错误码（如 `-999`）与正常值分离到独立字段，避免语义混淆。
