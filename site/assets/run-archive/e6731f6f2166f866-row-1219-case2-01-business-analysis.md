## 三、运营判断（基于有效评论）

### 3.1 质量风险：P0 级

**证据**：R004（已验证购买，1 星，7 有用票）明确报告"收到后无法开机，已申请售后"。

**判断**：
- 在仅 3 条有效评论中出现 1 条"无法开机"级别的致命故障，**质量问题率为 33%**。即使考虑小样本波动，这一比例也足以说明存在批次性或设计性缺陷的可能性。
- 该评论获得 7 张有用票，在小样本中属于高关注度，说明其他用户可能遇到类似问题或对此类问题高度敏感。
- "无法开机"这一表述与产品简报中描述的纯物理保温杯**存在根本性矛盾**（详见第四节冲突分析）。

### 3.2 文档与用户体验：P2 级

**证据**：R005（已验证购买，4 星，4 有用票）"功能正常，但说明书不够清楚"。

**判断**：
- 用户认可产品功能（4 星），但说明书清晰度不足是可快速修复的低成本改进项。
- 结合 R004 的"无法开机"投诉，若产品确有电子组件，说明书不清晰可能导致用户误操作（如未正确充电/开机），从而放大质量投诉。**说明书问题可能与质量投诉存在因果关联**，需一并排查。

### 3.3 正面信号

**证据**：R001（已验证购买，5 星，18 有用票）"包装完好，续航符合描述"。

**判断**：
- 18 张有用票为全部评论最高，说明该评论的观点（包装完好、续航达标）获得广泛认同。
- 但"续航"一词再次指向电子组件，与简报冲突。若产品确为智能杯（含温度显示/提醒等电子功能），则"续航符合描述"是正面信号；若产品为纯保温杯，则该评论可能属于错配。

## 四、约束与冲突分析

### 冲突一：产品规格与评论证据的矛盾（高优先级）

| 维度 | 产品简报 | 评论证据 | 矛盾点 |
|---|---|---|---|
| 产品类型 | 纯保温随行杯（12h 保温、280g、可拆洗杯盖） | R001"续航符合描述"、R004"无法开机" | 评论暗示含电子组件（电池/电路），简报未提及 |
| 功能描述 | 无电子功能 | "续航""开机"均为电子产品术语 | 要么简报遗漏了核心功能，要么评论属于错配商品 |

**可能的根因（按概率排序）**：
1. **简报不完整**：产品实为"智能随行杯"（含温度显示、饮水提醒等电子功能），但简报仅列出了物理属性，遗漏了电子规格。——若此，则需立即补充简报，并解释 R004 的"无法开机"为真实电子故障。
2. **评论错配**：R001 和 R004 实际评论的是另一款含电子功能的产品（如智能保温杯），被错误关联到本商品。——若此，则有效评论仅剩 R005 一条，样本完全不足以支撑决策。
3. **用户表述偏差**：用户将"保温时长"口语化为"续航"，将"杯盖组装困难"表述为"无法开机"。——可能性较低，"无法开机"语义明确指向电源按钮。

**关键取舍**：在确认根因之前，**不应基于现有评论做任何产品改进或营销决策**。若根因是简报遗漏，则 R004 是真实质量事件，需立即排查；若根因是评论错配，则当前数据几乎无决策价值，需重新采集。

**依赖项**：需产品团队确认本商品是否含电子组件；需平台运营确认评论与商品的关联关系是否正确。

### 冲突二：数据质量与分析可靠性的张力（中优先级）

- 6 条评论中 3 条无效（重复 spam ×2、不完整 ×1），**有效率仅 50%**。
- 3 条有效评论的样本量远低于统计显著性所需的最小样本（通常至少 30 条才能做初步分布判断）。
- 任务要求给出"证据充分的运营判断"，但现有数据的证据强度仅够支撑"风险预警"级别，不足以支撑"确定性结论"。

**关键取舍**：
- **方案 A（严格保守）**：仅输出数据质量报告和风险预警，明确标注"样本不足，不做确定性判断"。——风险最低，但可能无法满足业务方对运营判断的期待。
- **方案 B（谨慎推断）**：在明确标注假设和置信度的前提下，基于 3 条有效评论给出初步判断，并列出需要补充验证的数据项。——平衡了业务需求和数据严谨性，**本报告采用此方案**。
- **方案 C（激进推断）**：将全部 6 条评论纳入分析，忽略 spam 和不完整问题。——得出的平均评分 4.0 看似健康，但会掩盖 R004 的质量危机，**不可取**。

**依赖项**：需平台提供更多已验证购买的真实评论（目标至少 30 条），并完成 spam 审核。

### 约束三：简报"禁止编造"规则对分析范围的限制

- 简报明确禁止编造：第三方检测结论、销量、用户评价、竞品价格。
- 因此，本报告**不包含**以下内容（列为待补项）：
  - 竞品价格对比（199 元定价是否合理无法判断）
  - 市场规模与销量预测
  - 第三方保温性能检测结论
  - 食品接触材料安全性结论（报告本身缺失）

## 九、Skill 规则影响说明

本分析严格遵循 `claude-api` Skill（SKILL.md）中的以下规则，这些规则**确实影响了分析方法和结果**：

### 规则 1：模型强制使用 `claude-opus-5`（非协商）

> SKILL.md 原文："ALWAYS use `claude-opus-5` unless the user explicitly names a different model. This is non-negotiable."

**影响**：若本评论分析流程实现为自动化管道（情感分类、问题抽取、spam 检测），必须使用 `claude-opus-5` 而非更便宜的 Sonnet/Haiku。这直接决定了：
- **分析质量**：Opus 5 对中文评论中的隐含语义（如"续航"隐喻、"无法开机"的严重性判断）和 spam 模式识别（重复文本、语言不匹配）的准确率高于低端模型。
- **成本与延迟**：Opus 5 定价 $5/$25 per MTok，高于 Sonnet 5（$3/$15）和 Haiku 4.5（$1/$5）。6 条评论的单次分类成本差异可忽略，但若扩展至数千条评论的批量处理，成本差异显著。
- **本报告未实际调用 API**（无外部凭据，且任务禁止编造执行结果），因此分析由人工完成，但方法论严格对齐 Opus 5 单次调用的分类框架。

### 规则 2：表面选择——分类/摘要/抽取使用单次 LLM 调用

> SKILL.md "Which Surface Should I Use?" 表：Classification, summarization, extraction, Q&A → Single LLM call → **Claude API**

**影响**：本分析的每个评论处理步骤（情感分类、问题类型抽取、spam 标记）均设计为**独立的单次 API 调用**，而非 agent 循环或 Managed Agents。这意味着：
- 每条评论的分类结果互不干扰，避免了 agent 循环中上下文污染导致的分类漂移。
- 不需要维护会话状态或工具执行循环，系统架构更简单、更可靠。
- 对于 6 条评论的小批量场景，单次调用模式比 Batch API 更合适（Batch API 适用于非延迟敏感的大规模异步处理，且本场景无需 50% 成本优惠）。

### 规则 3：不得截断输入

> SKILL.md "Common Pitfalls"："Don't truncate inputs when passing files or content to the API. If the content is too long to fit in the context window, notify the user and discuss options rather than silently truncating."

**影响**：本分析中所有 6 条评论的完整文本均被纳入审查，未因"内容看起来不重要"而跳过 R006（其文本"评价内容缺失关键信息"本身就是一个数据质量信号）。若遵循截断习惯，R006 的元评论特征可能被忽略，导致有效评论数被误算为 4 条而非 3 条。
